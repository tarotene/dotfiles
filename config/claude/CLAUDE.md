# 調査・先行例確認の方針

## 検証可能な仮定を放置しない

計画・回答・設計判断が「検証可能な不確実性」を含むとき — つまり
Slack・Google Drive(コネクタが接続されている場合)、GitHub(gh CLI)、
公式ドキュメント・upstream ソース・学術文献のいずれかに答えが実在し
そうなとき — 参照するかどうかをその場で明示的に判断すること。参照
しない場合は理由を一言書く。「聞かれなかったので見なかった」を失敗
とみなす。

## 発明する前に先行例を確認する

新しいパターン・仕組み・非自明な設計をゼロから提案する前に、「これは
確立されたやり方が存在する問題か?」を自問し、存在しうるなら調べる。
優先順位:

1. 一次情報源: 公式ドキュメント・upstream のソース/spec・学術文献
   (論文・既存研究)— アルゴリズム・手法など研究的性質を持つ問題では
   文献が本命
2. 組織内の先行実装・過去議論(GitHub org、Slack、Drive)
3. 二次情報(ブログ等)は 1–2 の裏取りがある場合のみ

## 調べ方の規律

- 調査は可能なら background agent / research スキルに委譲し、本線を止めない
- 検索クエリ自体が文脈を外部に送ることを意識し、trivial な作業では発火させない
- 取ってきた情報の要点だけを本線に還流し、コンテキストを汚さない
- 一次情報を引いたら、成果物に URL と取得日を残す。URL 単独では不十分
  — 著者・タイトル・(判明する範囲で)公開日も併記する

## 依存する変更は stacked PR に積む

先行 PR の成果物を後続が参照する、または同一ファイルの同じ節を逐次
編集するときは、main 起点で並行させず stacked PR として積む
(base を親ブランチにする)。

- 分割案(何段に分け、各段が何を含むか)を計画段階で先に提示する。
  承認後は全段の PR 作成まで止まらない。
- 同じ行を 2 段以上が書き換える切り方はしない(追記なら可)。
- 各段はそれ単体でマージしても壊れないこと。
- 手順・rebase 運用・Issue リンクの書き分けは stacked-pr スキルに従う。

## 複数項目の依頼は要求インベントリで受ける

sub-issue を持つ Issue、または箇条書きで複数項目を含む依頼を計画に起こす
ときは、計画冒頭に `## 要求インベントリ` を置き、依頼文と参照 Issue の子
項目を逐語で 1 行 1 項目・`R1..Rn` の ID 付きで列挙してから設計に入る。
列挙は本線で行う(Plan/Explore サブエージェントは CLAUDE.md を読み飛ばす)。

- 各 `Rn` には処分を書く: 実装する段、または閉じたタグ
  (`Blocked-Upstream:` / `Obsolete:` / `User-Excluded:`)。
- 規模・工数・セッション長・コンテキスト残量は棄却理由にならない。
- 依頼が参照する Issue のうち実装対象でないものは
  `Reference-Only: #N — <理由>` で明示的に外す。
- 依頼に含まれない隣接事項の非スコープ宣言はこれとは別で、従来どおり書ける。
- 作業中に見つかった隣接する負債は棄却ではなく wrap-up inbox へ流す。
- 手順は scope-inventory スキルに従う。

# 実装タスクの完了定義

コード変更を伴うタスクでは、PR の作成までがタスクである。commit や push で
手を止めて報告に切り替えるのは未完了。

- commit → push → gh pr create を、途中で確認を挟まず一続きで実行する。
  「PR を作成しますか?」と聞かない。push を省略して報告で終えない。PR 作成を
  選択肢から落とさない。
- PR 本文は pr-description スキルの 5 節スケルトンに従う。
- 例外は 2 つだけ: (1) ユーザーが「commit まで」「PR 不要」等と明示した場合、
  (2) リポジトリが PR フローを持たない場合。迷ったら PR を作る側に倒す。
- 調査のみ・ファイル変更なしのセッションはこの節の対象外。
