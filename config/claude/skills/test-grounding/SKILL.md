複数の実コンポーネントが絡む検証項目・試験手順は、書く前に「機種の一次文書」と「層別の状態機械+状態組合せ×コマンド→副作用の突合表」を用意し、ドラフト内の各 assert をそのモデルに対して検算してから確定する。モデルを作らずに手順だけ書くと、結線・実装・上位仕様のどこかの食い違いが手順の中に埋め込まれたまま検証項目として確定してしまう。

## 1. なぜモデルを先に作るか

検証項目・試験手順のドラフトは、たいてい次の3つの層の情報を暗黙に混ぜて書かれている:

1. 上位の設計文書・要求文書が「こう動くはず」と書いている内容
2. 実装（ファームウェア・ドライバ）が実際にコード上でどう動くか
3. 機器の一次文書（メーカー提供のデータシート・ユーザーガイド）が規定する仕様値

この3層は互いに独立に更新されるため、食い違いが生じる。ドラフトを書いた本人がその食い違いに気づかないのは、3層のうち手元にある1層（たいてい上位の設計文書）だけを読んで書いているから。**モデルを作る作業＝3層を実際に読みに行って突合する作業**そのものが、食い違いを発見する主な機会になる。

## 2. モデルの最小構成

検証対象のドラフトを書く前に、次の2種類の文書を用意する（規模に応じて1文書にまとめてよい）:

### 2.1 機種ごとの facts 文書

- 出典はメーカー提供の一次文書（データシート・ユーザーガイド・リファレンスマニュアル）のみ
- **規範文書ではなく事実の抽出**であることを冒頭に明記する
- 記載は「(a) 一次文書からの事実抽出」「(b) その組み合わせによる計算（明示）」「(c) 一次文書から導いた解釈・設計上の注意（明示）」の3種を混在させず区別する
- 全記載に出典（文書名・版・章・ページ）を付す
- 一次文書内・文書間に不整合がある場合は両方残し、独自判断で一方を採用しない
- 一次文書に記載が無い事項は「記載が無い事項」として明記する（無いことの確認自体が成果）
- ミッション固有の実装解釈（このプロジェクトでの使われ方）は、一般仕様と混在させず別ブロックに分離する

### 2.2 層別の状態機械 + 突合表

- 環境／機器（一次文書の状態名）／各ファームウェア層、それぞれの状態を**実装の変数名・実際の状態名**で並べる（文書内の略記や独自の記号を使わない）
- 検証対象のドラフトが実際に操作・観測する範囲に絞った「状態組合せ × 発行コマンド → 各層の副作用」の表を作る。全組合せの網羅を謳うなら、その宣言した範囲内で本当に揃っているか確認する
- 動作が同じ組合せの行は1行に統合する

## 3. 検算の手順

モデルができたら、ドラフト内の assert / 判定条件を1つずつ次の観点で検算する:

- **フィールド・レジスタの実在確認**: assert が参照する名前は、現行ビルドのテレメトリ/レジスタ定義に本当に存在するか（存在しない名前が「先行事例」等の伝聞で紛れ込むことがある — 実装まで遡って確認する）
- **閾値の過剰・不足確認**: assert の判定値は、実装が実際に要求する有効範囲と一致するか（実装より厳しい固定値になっていないか、逆に緩すぎないか）
- **層間の状態整合確認**: 上位の設計文書が前提とする状態（enum値・状態名）が、実際にそれを生成する下位の実装の状態機械に存在するか（上位が4値を前提に分岐を書いているのに、下位の実装が3値しか持たない、といった食い違いが典型）
- **結線・経路の完全性確認**: 検証対象のドラフトが「Aから来る信号」と書いている経路が、実際の結線図・IF文書と一致するか（分岐先が1つ欠けている、逆方向の経路が抜けている等）

## 4. 完了条件

検証項目定義は、次を満たすまで完成と呼ばない:

- ドラフト内の全ての状態名・enum値が、モデル文書の表のどこかに出典付きで存在する（存在しないなら「未確定」と明記されている）
- ドラフト内の全ての assert が参照するフィールド・レジスタ名について、実在確認の結果（一致／不一致／要確認）がモデル文書に記録されている
- 発見した食い違いのうち、当該検証項目のスコープ外のもの（上位設計文書側の誤り等）は、その場で直さず別途記録し、検証項目定義自体の訂正だけをその場で反映する
