## 事例1: 複数ファームウェアが絡む受け入れ試験の項目定義で、モデル作成が4種の食い違いを発見した

**状況**: 組み込みシステム（複数の実時間ファームウェアが通信で連携する構成）の受け入れ試験項目を、既存の起票済みチケットに沿って `.ops` 形式の手順ドラフトへ落とし込む作業。ドラフトはすでに一定の完成度があり、担当者はレビュー依頼のつもりだった。

**発動判断**: レビュー依頼の前に「このドラフトが前提とする結線・状態遷移は正しいか」を確認する必要があると判断し、手順を書く前に facts 文書とモデル文書を先に作る方針に切り替えた。

**モデル作成の過程で見つかった食い違い（4種）**:

1. **結線記述の欠落**: チケット本文が「センサXはセンサYを介して制御コンピュータAに接続される」と書いていたが、実際のボード結線図を確認すると、センサXの信号は制御コンピュータAと制御コンピュータBの両方に直接ファンアウトしていた。センサYは経路上の1構成要素にすぎず、チケットの記述は分岐の半分を見落としていた。
2. **実在しないレジスタ名を参照する assert**: ドラフトの手順が `IF.RECEIVED` という名前のテレメトリフィールドを判定に使っていたが、現行ビルドのテレメトリ定義にその名前は存在しなかった。出典を遡ると、別チケットのコメントに書かれた実装シンボル名（`xxx_info->received`）を、実際のテレメトリ定義を確認せずにフィールド名としてそのまま流用していたことが分かった。実体は別の名前を持つビットパック済みフィールドの1ビットだった。
3. **判定閾値が実装より過剰に厳しい assert**: ドラフトは「ステータス値が特定の1値と等しいこと」を判定条件にしていたが、当該値を消費する側の実装を確認すると、実際の有効判定は「一定の範囲に含まれること」であり、ドラフトの単一値判定はその範囲の一部でしかなかった。名目上その1値に落ち着くことが多いだけで、判定条件としては過剰に狭かった。
4. **上位仕様と下位実装の状態機械の不一致**: 上位の設計文書は、ある層の状態遷移に4値の enum（3つの通常状態＋1つの障害時退避状態）を前提として、復帰時の分岐ロジックを規定していた。しかし実際にその値を生成する下位ファームウェアの実装を確認すると、状態機械は3値のみで実装されており、上位が前提とする4番目の状態（障害時退避状態）は存在しなかった。上位仕様の分岐ロジックの一方の経路は、実機では原理的に到達し得ないことが判明した。

**結果**: 4件のうち、検証項目定義そのものに影響するもの（2, 3）はその場でドラフトを訂正した。スコープ外の設計文書側の問題（1, 4）は、検証項目定義のチケットには反映せず、それぞれ別のチケットとして起票し、検証項目定義のチケット側からは「別チケットで追跡中」という参照のみを残した。

**教訓**: 4件のうち3件（1, 2, 4）は、モデルを作らずに「ドラフトを読んで気づく」方式では発見できなかった可能性が高い。いずれも一次資料（結線図・レジスタ定義・下位実装のコード）に実際に当たらないと見えない食い違いで、上位のチケット本文や設計文書だけを読んでいては「一貫していて正しそうに見える」文章として通り過ぎてしまう。**モデルを作る行為自体が、一次資料に当たることを強制する**ことが効いていた。
