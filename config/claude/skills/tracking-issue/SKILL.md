複数の子作業を束ねる親 Issue は、本文に子の一覧を手書きすると GitHub ネイティブ sub-issues の自動集計と二重管理になり、どちらかが更新を止めた瞬間に腐る。このスキルは「親に何を書き、何を書かないか」を固定し、更新すべき箇所そのものを最小化する。

## 1. 発火条件: 事後昇格

最初から親として起票しない。普通の Issue として起票し、実作業が **2 つ以上の子に割れた時点** で親に昇格させる。1 件で終わる仕事のために空の傘を先に立てない。

## 2. 実装方式: ネイティブ sub-issues

親子関係は GitHub の sub-issues 機能で表現する。

- 子を作りながら紐付ける: `gh issue create --parent <親番号>`
- 既存 Issue を後から紐付ける: `gh issue edit <親番号> --add-sub-issue <子番号>[,<子番号>...]`
- 親を外す: `gh issue edit <子番号> --remove-parent`
- 進捗確認: `gh issue view <親番号> --json subIssuesSummary,parent`

GraphQL の `addSubIssue` mutation を直接叩く必要はない(`gh` 2.94.0 以降で上記フラグが使える)。

階層は親→子の 2 段までに自主制限する(GitHub 上限は 8 段だが使わない)。子が 1 親あたり 100 件に近づいたら、傘を分割する。

## 3. 本文スケルトン

子の一覧を本文に重複させない(sub-issues 機能に委ねる)。本文に書くのは、機能では表現できない文脈だけ:

```
## 目的 / スコープ
## 完了定義
## 傘の外への依存
## スコープ外

_この本文は現状の合意状態を表す正本。方針・スコープ・完了定義が変わった時点で更新する。_
```

- **目的 / スコープ**: この傘が何のためにあるか、一文で。
- **完了定義**: 「全 sub-issue クローズ = 何が達成されたことになるか」を一文で。機械検査可能な条件(テストが通る・selftest が全経路 PASS 等)があれば具体的に書く。
- **傘の外への依存**: ある子が傘の外の Issue にブロックされている場合、その旨を明記する。
- **スコープ外**: 似ているが束ねなかった Issue を明示し、なぜ含めなかったかを一言添える(未然に「なぜあの Issue が入ってないのか」と聞かれるのを防ぐ)。
- 末尾の維持義務の一文は削らない。更新契機を「方針・スコープ・完了定義が変わったとき」に限定する宣言そのものであり、これが無いと「可能な限りリアルタイムに更新する」が実質「頻繁に手で触る」に読み替えられて腐敗源に戻る。

設計文書(ADR 等)がある場合は、その文書と親 Issue を相互リンクする(親からは文書パスを、文書からは親の Issue 番号を)。

## 4. 禁止事項

- **子 Issue を指すチェック(`- [ ] #NN` 形式)を本文に書かない。** 子の一覧・進捗・残数は sub-issues の自動集計に委ねる。これは唯一の絶対禁止で、腐った tracking Issue の主因(子が全クローズなのに本文チェックが未更新のまま残る)を構造的に断つ。
- **期日を本文に書かない。** Milestone に置く。書く場所を 1 つに固定する。
- **親を議論の場にしない。** コメントで裁定が決まったら即本文へ反映し(`living-description` の一種)、未決着の設計論点はコメントに残さず子 Issue に切り出す。コメントは途中経過であって正本ではない。正本が本文とコメントに分裂すると、どちらを読めばいいか誰にも分からなくなる。

## 5. 許可されるチェックボックス

Issue 化しない粒度の受け入れ条件・作業ステップ(手順の各段)には `- [ ]` を使ってよい。禁止は「子 Issue への参照」に限定されるので、これらは対象外。

ただし機械検査に乗せたい場合は注意が要る: sub-issues が 1 件以上ある親では、本文のチェックボックスは要求インベントリ抽出経路(`scope-inventory` / `plan-scope-gate.sh`)から読まれない(sub-issues が優先され、本文は無視される)。抽出させたい要件は `## 完了定義` に文章で書く。

## 6. findability: `tracking` ラベル

親には `tracking` ラベルを付ける。リポジトリにまだ無ければ `gh label create tracking` で作る。sub-issues の親子構造は SessionStart の Issue 索引(タイトル・ラベルのみを表示する軽量索引)には現れないため、ラベルが唯一の一覧上の目印になる。

## 7. クローズ条件

- **完了**: 全 sub-issue が closed かつ `## 完了定義` の一文が満たされている → `completed` 理由でクローズ。
- **放棄**: スコープを諦めた場合 → `not planned` 理由でクローズし、本文に一言(いつ・なぜ諦めたか)を残す。

腐って放置された傘の清算手順・定期衛生管理は `issue-hygiene` スキルが持つ(このスキルは書く/更新する側、`issue-hygiene` は事後の棚卸し・清算側)。

## サニタイズ

このスキル自体をリポジトリ間で使い回す前提のため、本文に固有のリポジトリ名・Issue 番号・URL を書き込まない。追記する事例やチェックリストの拡張時のサニタイズ規則は `skill-gardening` を参照する。
