# diagramming 失敗事例集

作図で実際に起きた失敗と、その正解パターンを貯める。追記するときのサニタイズ規則(固有名詞・URL・実物持ち込み禁止など)は `skill-gardening` を参照し、ここには繰り返さない。

各事例は次のフォーマットで1事例1節にする:

```
## 事例 #N: <一言タイトル>

- 状況(抽象化): 何をドキュメント化しようとしていたか
- 何を描いたか: 選んだジャンル・技術
- 何が失敗だったか: 具体的な症状
- 根本原因: なぜその失敗に至ったか
- 正解パターン: 次からどうするか
```

---

## 事例 #1: 位置模式図に手続きを矢印+番号で重ねた

- **状況(抽象化)**: 組み込みフラッシュメモリの消去・書き込み・読み戻し検証という一連の手続きを、CLIツールのドキュメントに図解しようとした。
- **何を描いたか**: メモリの内部構造(バッファとアレイの位置関係)を表す静的な模式図の上に、①〜⑤の番号付き矢印を重ねて手続きの順序を表現する手書きSVGを描いた。
- **何が失敗だったか**: 矢印が縦横に何本も交錯し、どの矢印がどの順番でどこからどこへ向かうのか一目で読み取れない図になった。図中に「これは実際のレジスタではなく進行状況を示す色分けです」という注釈を書く必要が生じ、模式図というジャンル自体が手続きの表現に向いていないことの証拠になっていた。
- **根本原因**: 内容の型(時間発展・手続き)とジャンル(静的な位置模式図)が最初から食い違っていた。技術選定(SVGで描く)を先に決めてしまい、ジャンル選択の検討を経ずに描き始めた。
- **正解パターン**: 手続き・時間発展の内容は、Nコマ(各ステップを1コマとして並べる)+差分ハイライト(そのコマで変化した要素だけを色や枠で強調する)で描く。全コマで同一レイアウトを維持し、視線が迷わないようにする。

## 事例 #2: 手書きSVGの矢印端点を絶対座標でハードコードした

- **状況(抽象化)**: 事例#1と同じ図の中で、2つのボックス(バッファとメモリの1ページ)を結ぶ矢印を描いた。
- **何を描いたか**: 矢印の始点・終点をSVGの `line` 要素に絶対座標として直接書き込んだ。ボックス自体の座標とは別に、目分量で「だいたいこのへん」という座標を矢印側に置いた。
- **何が失敗だったか**: 矢印の端点がボックスの辺から数px〜数十pxずれ、宙に浮いているように見えたり、ボックスの中に食い込んだりした。
- **根本原因**: ボックスの位置とサイズを変更した際、矢印側の座標を追随して直さなかった(あるいは最初から目分量でずれていた)。ボックスの定義と矢印の定義が独立していて、両者を結びつける仕組みがなかった。加えて、完成した図をレンダリング・視認するステップを踏まずに「描けたはず」で終えていた。
- **正解パターン**: 矢印の端点はボックス定義(辺の座標)から導出する(変数・テンプレートの共有、またはレイアウトエンジンに任せる)。描いたら必ずPNG化してRead(画像として確認)し、接続のずれがないかを目視するまで完成と呼ばない。
