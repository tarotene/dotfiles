description: Draw a diagram (architecture, sequence, flow, state, procedure, spatial layout) for docs, READMEs, or artifacts. 図解・diagram・SVG・mermaid・模式図・シーケンス図・アーキテクチャ図・フローチャート・READMEに図を追加、といった作図全般で使う。技術選定より先に「この内容にはどのジャンルの図が正しいか」を判断する。
---

作図は「内容の型に合うジャンルを選ぶ」→「そのジャンルに合う技術を選ぶ」→「描いたら必ず自分の目で確認する」の3段階。技術選定を先に決めると、内容とジャンルが食い違ったまま描き進めてしまう。

## 1. 内容の型からジャンルと技術を選ぶ

| 内容の型 | 図のジャンル | 第一候補の技術 |
|---|---|---|
| 時間発展・手続き・状態変化(「まずA、次にB、するとCが起きる」) | Nコマ+各コマの差分ハイライト | SVGテンプレート複製、または画像の列 |
| フロー・依存関係・木構造 | グラフ | mermaid(スタイル指定込み) |
| プロトコルの往復・呼び出し順序 | シーケンス図 | mermaid |
| 位置関係・静的構造(「何がどこにあるか」に変化がない) | 模式図 | 手書きSVG可(§3の原則を守る) |

**判断の第一歩**: 描きたい内容を一言で言い直したとき、動詞(「〜する」「〜が変わる」)が主語ならNコマかグラフかシーケンス図。名詞(「〜がどこにある」)が主語なら模式図。ここを取り違えると、静的な模式図の上に手続きを無理やり矢印+番号で重ねる失敗になる(→ `cases.md` の事例参照)。

## 2. 技術の3段構え

1. **GitHubでソースごと見せたい軽い図 → mermaid**。ただし生の既定設定のまま出さない。frontmatter configで整える:
   ```
   ---
   config:
     layout: elk
     look: classic
     theme: neutral
   ---
   ```
   `layout: elk` は交差・重なりを減らす配置(現時点でフローチャート・状態遷移図が対象)。`themeVariables` で色・フォント・間隔も調整できる。**GitHubのネイティブmermaidレンダラーはバージョン・設定サポートが限定的**なので、ローカルの `mmdc`(mermaid-cli)でレンダリングして確認し、push後にGitHub上でも実際の見た目を目視する。
2. **凝った図・見栄えを優先したい図 → D2などレイアウトエンジン系ツールでSVGを生成してコミット**。ELKレイアウト+テーマ+スタイル分離が可能で、mermaidより仕上がりが良い。GitHubネイティブレンダリングはないので、生成したSVGファイルをリポジトリにコミットする運用にする。
3. **レイアウトエンジンで表現できない図(Nコマ差分ハイライト等)のみ、手書きSVG**。これが最後の手段であることを意識する — 「手書きSVGで済ませよう」が最初の選択肢になっていたら一度立ち止まる。

いずれのツールも導入されていない環境では、導入するか(パッケージ管理に追加を検討)、代替手段(ASCII図、複数の静止画像など)を検討する。無理に生SVGへ倒れない。

## 3. 技術非依存の原則(手書きSVGに落ちた場合は必須)

- **1枚の空間図に時間軸を押し込まない。** 位置の模式図の上に番号付き矢印を何本も引いて手続きを表現するのは失敗パターン。図中に「これは実際のレジスタではなく進行状況を示すための色分けです」のような言い訳キャプションを書きたくなったら、それはジャンル選択ミスのサインなので§1に戻ってNコマ方式に切り替える。
- **矢印の端点を人手の絶対座標で置かない。** ボックスの位置を変数/定数として定義し、矢印の端点はそのボックス定義(辺の座標)から導出する。座標を独立してハードコードすると、レイアウトを直したときに矢印だけ古い位置を指したまま数px〜数十pxずれる。
- **完成の定義に視認を含める。** SVGは `rsvg-convert file.svg -o file.png`(または `resvg`)でPNG化し、mermaidは `mmdc -i file.mmd -o file.png` でレンダリングしてから、画像としてRead(または開く)して次を確認するまで、その図は完成していないと見なす:
  - 矢印がボックスの辺に正しく接続しているか(ずれ・空中浮遊がないか)
  - テキストがボックスからはみ出していないか
  - 要素同士が重なっていないか
  - 意図したジャンル(表・グラフ・模式図)として一目で読めるか
- **Nコマ方式の作法**: 全コマで同一レイアウトを維持し、そのコマで変化した要素だけを色や枠でハイライトする。コマ間でレイアウトが動くと、どこが変わったのかを目で追えなくなる。
- **cases.md を確認する**: 描き始める前に、同じ型の失敗が事例集にないか目を通す。
