wrap-up inbox と起票済み wrapup 由来 Issue を 1 件ずつ Issue → PR で回すのは
摩擦が大きい。このスキルは収集 → 粗振り分け → 裁定 → Plan → 一括対処 → 消化を
定式化する。**確認の総数ではなく位置を変えるのがこのスキルの核**: 確認は
triage フェーズ(§2〜§4)に全部前倒しし、`ExitPlanMode` が GO を兼ねたあとは
一切止まらない。除外は閉じたタグでしか成立しないので、「規模が大きい」
「よく分からない」は agent が独断で母集団から落とす理由にならず、必ず
ユーザーへの問いに変換される。

## 1. 候補収集

- **inbox**: パスは SessionStart 注入(`additionalContext`)に出ているものを使う。無ければ `bash ~/.claude/hooks/wrapup-stop-gate.sh --inbox-path "$PWD"` で解決する(slug の計算方法は gate 側に一本化されている — 原則リポジトリ単位、remote なし・git repo 外はプロジェクト絶対パス由来にフォールバック)。読むのは `cat` + `jq` で構わない — 禁止されているのは書き込みで、変更は `--add` / `--mark-filed` 経由に限る(この制約はこのスキルでも不変)。
- **母集団は open Issue 全件 + inbox 行全件**: 起票済み Issue の発見は wrap-up フッター一致に頼らない — 実測(2026-09-21)で本文フッター一致は open Issue のごく一部にしか当たらず、汎用の attribution フッターのみを持つ Claude 起票 Issue の大半が発見漏れになっていた。`blocked-by-upstream` ラベルはクエリ段階で機械除外し、残りを §2 の粗振り分けで判定する:
  ```
  gh issue list --state open --limit 500 --json number,title,body,labels \
    | jq '[.[] | select(([.labels[].name] | index("blocked-by-upstream")) | not)]'
  ```
  **取得件数が `--limit` と一致したら打ち切りの可能性がある**ので、その場合は limit を倍にして再実行する。wrap-up フッター regex(統合形 `Filed from [Claude Code](...) wrap-up inbox` と旧 2 行形式の両方にマッチする `test("Filed from \\[?Claude Code.*wrap-up inbox")`)は廃止しない — マッチする Issue は粗振り分けを経ずに無条件で候補に含める**ヒント**として使う。

## 2. 粗振り分け(本線・title + body だけで判断)

4 レーンに振る。判断は title + body だけで済む粒度でよい(本文を読んでも方針が
定まらないものは無理に決めず L2 に落とす):

| レーン | 条件 | 行き先 |
|---|---|---|
| L1 裁定不要 | やり方が一意で、選択肢の提示が発生しない | そのまま段1 |
| L2 裁定要 | 実装方針が分岐する、または情報が足りない | §3 の起草へ |
| L3 大物 | chores PR に物理的に入らない規模(設計判断・ADR 起草を要する、または変更が広範) | §4 の一括問いへ |
| L4 外部ブロック | `blocked-by-upstream` ラベル、または本文で **リポジトリ外**の事情(upstream の未修正・未 GA、他者のマージ待ち)が明示されている | `Blocked-Upstream:` |

明示的に禁じる規律を 3 つ書く:

- **「規模が大きい」は L4 にならない。** 必ず L3 に入れ、刈り取るかどうかは
  ユーザーが決める。規模・工数・セッション長・コンテキスト残量を理由にした除外は
  誤用であり、書いてはいけない(`scope-inventory` §2 と同文)。
- **「よく分からない」で母集団から落とさない。** 分からなければ L2 に入れ、
  §3 のサブエージェントに調べさせる。
- **同一母集団内の Issue 待ちは L4 にならない。** `Blocked-Upstream:` は
  `scope-inventory` §2 の定義どおり**リポジトリ外**の事情に限る。母集団の中に
  先行 Issue が居るなら、今回それを刈れば後続も着手可能になるので、後続は
  L2 または L3 に入れて**裁定に載せる**。

依存を持つ項目の扱い:

- §3 の起草では、先行 Issue の番号と「先行を今回刈った場合/刈らなかった場合」の
  両方を選択肢に含めさせる
- §4 の裁定で先行・後続の両方が選ばれたら、ADR-0027 の単一チェーン上で
  **先行を段 k、後続を段 k+1** に置く(依存の向きがそのまま段の順序になる)
- 先行が選ばれず後続だけ残った場合の処分は `User-Excluded: 先行 #N が今回対象外`
  であって、`Blocked-Upstream:` ではない

## 3. 選択肢の起草(L2 の各件に 1 サブエージェント、並列、read-only)

L2 に振った項目ごとに background subagent へ起草を委譲する(`github-audit-triage`
§2 と同じ型)。本線のコンテキストを個別の起草で焼かないためで、これをやらないと
「情報が足りないから要判断」を本線が言い出し、現行版と同じ日和りに戻る。

subagent への指示・返値の契約:

- `gh` と読み取り専用ツールのみ。**実装はしない**、案の比較だけ行う
- 実装案を 2〜4 個。各案に「変更するファイルと行数の概算」を付ける
- 推奨 1 つと、推奨理由 1 行
- 先行例: 出典(URL・`#N`・パス)+ 取得日、または `先行例なし:` + 探した範囲
- 軸: `表現不可能` / `還元` / `検出のみ` のいずれか + 1 句
- 対処が PR の外(ホストローカルファイル・GitHub 設定等)に出る項目では、
  **「宣言化して正本に取り込む案」を必ず 1 案に含める**(ADR-0001: home-manager
  が正本 / ADR-0034: 実値は private wrapper flake)。実値を含むものは public
  リポに書けないので、private wrapper flake 行きの案として立てる
- 依存を持つ項目(§2 末尾)は「先行を刈った場合」「刈らなかった場合」を別案として出す

先行例と軸をここで取らせることで、§5 の Plan の `## 先行例との対比` がほぼ
組み立て済みになる。

## 4. 裁定(`AskUserQuestion`、triage フェーズ内で完結)

- **L2**: 1 件 1 問。§3 の返値をそのまま選択肢にし、「今回は除外」を必ず加える。
  1 回の呼び出しで最大 4 問(`AskUserQuestion` の上限)なので、件数が多ければ
  複数回に分けて呼ぶ
- **L3**: `multiSelect` で一括。「今セッションで着手する大物を選ぶ」。各選択肢に
  **「→ 段N になる」コストを明記する**
- L3 で選ばれなかったものは `User-Excluded: 裁定で今回対象外` になる

これが完了すると、母集団全件が次のいずれかに確定している: L1(裁定不要)/
L2 の裁定結果(実装する案 or 除外)/ L3 の裁定結果(着手する段 or 除外)/
`Blocked-Upstream:`。

## 5. Plan を書く(このスキルは plan mode で走る)

plan mode でなければ `EnterPlanMode` を呼ぶ。Plan には:

- `## 要求インベントリ` — 母集団の**全件**を `R1..Rn` で列挙する(open Issue +
  inbox 行)。各 `Rn` の処分は `段N で実装` / `Blocked-Upstream:` / `Obsolete:` /
  `User-Excluded:` のいずれか 1 つ
- `## 先行例との対比` — §3 の返値から `Dn` 行を組み立てる
- 自己検査 2 本を走らせて指摘ゼロを確認してから `ExitPlanMode`:
  - `~/.claude/hooks/plan-scope-gate.sh --check-plan <プランファイル>`
  - `~/.claude/hooks/plan-precedent-gate.sh --check <プランファイル>`

**`ExitPlanMode` が GO を兼ねる。** 個別の裁定は §4 で既に済んでいるので、
Plan 提示後に会話上で改めて表を出して GO を取り直すことはしない。

## 6. 段の構成

分割の軸は **「レビューが 1 本で成立するか」**。

- 段1 = chores PR。L1 と、裁定済みだが局所(数ファイル・独立に読める)な項目
- 段2 以降 = 非局所な裁定済み項目と、裁定で選ばれた大物を 1 件 1 段。依存を
  持つ組は §2 の規律どおり先行 → 後続の順で連続する段に置く

ADR-0027 に従い単一チェーンに積む。手順・`Stack:` 行・段ごとの `Closes` の
書き分けは `stacked-pr` スキルに委譲する(ここでは再掲しない)。

## 7. 一括対処(GO 後は止まらない)

- 最新の default branch から作業ブランチを切る(`Closes` が効くのは default
  branch 向き PR だけなので、ベースブランチを必ず確認する)。
- 項目ごとに 1 commit。Issue に対応する項目は commit message に `#N` を含める。
- 各段の PR 本文はリポジトリの `pr-description` スケルトンに従う:
  - その段で対処した Issue はすべて `Closes #N` として列挙する
  - inbox 由来で対応する Issue が無い項目は、**新たに起票しない**(起票して
    即クローズする churn を避ける)。代わりに「課題」節に「inbox 直接消化分」
    として title / detail を列挙し、何を直したかを本文で監査できるようにする
  - その段の対処項目が inbox 直接消化分のみ(Issue が 1 つも無い)の場合に限り、
    `No-Issue:` で理由を明記する
  - Before/After は視覚的な変更があれば証跡を、無ければそのリポジトリの規約に
    沿って明示する

実装中に §5 で想定していなかった分岐が判明した場合の規律:

> 推奨案で進め、**PR 本文の `## 要確認` に「分岐があった / こちらを採った /
> もう一方はこう」を必ず書く**。`AskUserQuestion` で止まらない。完了定義は
> PR 作成までで merge しないので、レビューが安全網になる。

## 8. inbox の消化タイミング

その項目を含む**段**の PR 作成(`gh pr create` 成功)の直後に、対処済みの
inbox 行を 1 行ずつ `--mark-filed` で削除する。行は完全一致で渡す(inbox の
直接編集は不変で禁止)。

- **commit 直後ではなく PR 作成直後**にする理由: セッションが PR 作成前に
  終了しても inbox はそのまま残り、既存の収集・起票の仕組みが自己修復的に
  拾い直せる。commit しかしていない段階で inbox から消してしまうと、push 前に
  セッションが落ちた場合に気づきそのものが失われる。
- **merge 後ではなく PR 作成直後**にする理由: PR 作成から merge までの間、
  対処済みの項目が inbox に残っていると、その間に走る別セッションの Stop
  ゲートが同じ項目を再び起票しようとする。merge を待って消すと「merge 後に
  inbox を消す主体」がこの機構には存在しない。PR 作成直後に消しておけば、
  記録は PR 本文と commit に恒久的に残るため、PR が閉じられても気づきの内容
  自体は失われない。

## 9. 完成の定義

次をすべて満たすまで完成と呼ばない:

- 母集団の全件が `## 要求インベントリ` にちょうど 1 回ずつ現れ、処分を持つ
  (発見漏れゼロ)
- `plan-scope-gate.sh --check-plan` と `plan-precedent-gate.sh --check` が
  指摘ゼロ
- 全段の PR が作成済み(`stacked-pr` の完了定義に従う)
- 対処した項目の `Closes #N` が段ごとに 1:1 対応している(inbox 直接消化分は
  本文の列挙で代替)
- 対処済みの inbox 行が inbox から 0 件になっている
- リポジトリ標準の検証(selftest / lint / ビルド等)が段ごとに green
- 実装中に生じた分岐が該当段の PR 本文の `## 要確認` に列挙されている

事例が積み重なったら `cases.md` を新設して追記する。サニタイズ規則は `skill-gardening` を参照。
