Issue/PRのDescriptionは書いた瞬間で固定されるスナップショットではなく、現在の合意状態を表す正本として扱う。

## 1. コメントで決まったら、その場で本文を直す

議論・裁定・仕様変更がコメント上で確定した時点で、本文(Description)を編集して反映する。コメントは経緯ログとして保存しておけばよく、消す必要はない。しかし本文は「今読んだ人に今の状態を伝える」ものでなければならず、「詳細はコメント参照」で済ませるのは、後から読む人(将来の自分・別のレビュアー・別のエージェント)がコメント全部を読み返さないと現在の仕様が分からない状態を作ってしまう。

「合意前の設計提案です」のような警告バナーも、合意が取れた時点で除去し、裁定へのリンク(または裁定内容そのもの)に差し替える。バナーだけ残して下の本文を書き換えると、警告と内容が矛盾したまま残る。

## 2. 複数箇所に重複した仕様は、横断的に同期する

同じ仕様(数値・命名・状態遷移・バイト配置など)が複数の関連Issue/文書に重複して書かれている構成では、1箇所の裁定が変わったら全ての重複箇所を洗い出して同期する。1箇所だけ直すと、リポジトリ内に矛盾する複数の「正本」が残ってしまう。

- 更新前に、古い値・古い表現をキーワードにして重複箇所を横断的に検索する(grep等)
- 見つかった全箇所を同一の裁定内容に揃えてから完了とする
- 各箇所を編集する直前に、その時点の最新本文を再取得する(並行して他者・他エージェントが編集している可能性を踏まえる)

## 3. 完成の定義

「本文を裁定内容に合わせて編集した」と言えるのは、次を満たしたときだけ:

- 古い値・古い仮の記述(暫定コード、旧数値、旧方式名、既に不要と判明した論点など)が、対象範囲の本文から検索して0件になっている
- 直近の裁定コメントの差分が、本文の対応する箇所すべてに反映されている
- 複数のIssue/文書に渡る場合、grep等で横断的に確認している

議論の過程をすべて本文に残そうとしない。特に「後から不要と判明した論点」(例: 一時的に検討していたが、別のプロセスに委ねるべきと分かった話)は、本文からきれいに落とす。過程を残すほど、後から読む人に「まだ未確定なのか」という誤解を与える。
