技術・仕組みの選択における「クリーンかつ先進的でありたい」という気分を、
検証可能な 3 軸の辞書式順序に変換する。詳細な設計動機と証拠は
`docs/adr/0035-selection-grounding.md` と
`docs/claude/selection-grounding.md` を参照。

要点: 新しさそれ自体を採否の理由にしない。表現不可能性(不正な状態を
検出でなく表現不可能にするか)を最優先し、次に還元性(その仕組みは
より安い手段では担えない仕事をしているか)を見て、先進性は前二者が
無差別なときの同順位破りとしてのみ使う。この節は `precedent-grounding`
が確立した `## 先行例との対比` 節を共有し、`Dn` 行に `軸:` トークンを
1 つ足すだけで書く。新しい plan 節・新しい gate は使わない。

`軸:` トークンそのものは precedent-grounding が拾う**全ての** `Dn`
(命名・機構の置き場所・プロトコル・アルゴリズムを含む)に必須 —
precedent-grounding スキル §3 参照。このスキルが担うのは (a) 軸の定義・
duality 閉集合の中身(§2)と、(b) 技術・仕組みの選択に限って発火する
重い欄(本命/対抗馬/外した候補、§3)の 2 点。

## 0. 前提: 白紙から選ぶ(ADR-751)

3 軸で評価する**前**に、入力から歴史的経緯と作業量を除く。判定質問は
「コード 0 行の白紙から選ぶとしたら、3 軸で何を採るか」。現職も白紙の
上では候補の 1 つ。

- **0 とみなす**: 書き直し・波及する編集・レビュー量・テストの移し替え。
  「すでにこうなっている」「移行が大変」は理由にしない。
- **数える(戻せないもの)**: 失うと戻せないデータ、自分では管理できない
  外部の利用者との契約、人手でしかできない作業。書き方は閉じた 1 行:
  `戻せない: データ | 外部契約 | 人手 — <何が戻せないか>`。
- **完全に同点なら現職を維持**する。理由は「乗り換えてもどの軸も良く
  ならない」ことだけ。変更を提案するなら、どの軸がどう良くなるかを示す。
- **裁定と実行は分ける**。乗り換えるべきという裁定が出たら Issue に
  「意図は決まっていて未着手」と残す。いつ移行するかは自由で、既存の
  選択を自分から棚卸しする義務はない(ADR-0035 D5)。「コストが高いから
  移行しない」という裁定は書けない。
- **手順の設計には使わない**。いつ問うか・どう組むかでは作業量の現実を
  数えてよい(ADR-543 の前倒しがその例)。

LLM が考えずに Python 等へ倒れる癖は、新しい道具・単位の実装言語を選ぶ
`Dn` に対抗馬を立てさせて潰す(§1)。Python を選んでよいが、白紙で同じ
軸の上で比べた記録を残す。

gate は `Dn` 内の閉語彙のコスト語(書き直しコスト・移行コスト・撤収コスト・
波及コスト・battle-tested・歴史的経緯 等)を deny する。バッククォートで
囲んだ語は引用として数えない。`戻せない:` 行では書ける。

## 1. 重い欄の発動条件

「妥当な代替が複数ありうる技術・仕組みの選択」のうち、外部依存の新設・
置換・撤去、新しい道具・単位の実装言語の選択、または戻せないもの
(データの損失・外部契約・人手の作業)が生じるものだけ、`本命:`/
`対抗馬:`/`外した候補:` を追加で書く(§3)。典型例:

- ツール・ライブラリ・言語・フレームワークの新規採用または置き換え
  (例: `esa.io → Obsidian`、`bash → Rust`、`pip → uv`)
- 新しい機構(hook・skill・gate・設定ファイル)を追加するかどうかの判断
- 既存の機構を残すか撤去するかの判断(死んだ機構・重複した機構の疑い)

これに当たらない `Dn`(例: 命名規約への追従、stacked PR の段の切り方)は
`軸:` だけを書けばよく、重い欄は不要。

## 2. 軸の定義と duality 閉集合

判定質問はどの軸も同じ形: 「この選択は不正な状態を*表現不可能*にするか、
それとも*検出可能*にするだけか」。

1. **表現不可能性。** 採択側の duality(閉集合):
   宣言 > 手続き / 単一正本 > 複写+同期 / 閉語彙 > 自由記述+事後 lint /
   型・コンパイル時 > 実行時検査 / pin 固定 > 浮動 / upstream 正本 > fork。
   この 6 種以外の duality を見つけたら、リストにない新種として
   `軸: 表現不可能` の理由に書けばよい(閉集合はこのスキルの改訂でのみ
   増やす)。
2. **還元性。** その仕組みは、より安い手段(既存の語彙・既存のフィールド・
   何もしないこと)では担えない仕事をしているか。死んだ機構・重複した
   機構は残すより消す(消す作業量は数えない)。
3. **先進性。** 1・2 が無差別なときの同順位破りとしてのみ使う。新しさが
   1 を弱めるなら、その候補は採らない。採用したら追従した理由を pin 地点
   (バージョン制約のコメント等)に残す。

衝突時は必ず上位の軸が勝つ。3 軸の判定が割れていない(1 つしか埋まらない)
`Dn` は、埋まった軸だけを書けばよい — 3 つ全部を毎回埋める必要はない。

## 3. 候補集合の誠実さ(重い欄)

外部依存の新設・置換・撤去、新しい道具・単位の実装言語の選択、または
戻せないものが生じる選択のときだけ、`軸:` に加えて次の欄を書く:

```markdown
- D2: <採った設計判断を 1 文で>
  本命: 憧れ駆動 | なし — <理由>
  対抗馬: <候補> (<本命と共通の評価軸>)
  外した候補: <候補> — 感触で外した(<感触>)。分析ではない。
  既存手段: <path> — 採用: <ツール名/URL> | 拡張: <既存パス> | 自前 — 却下: <候補> (<理由>) | 探索: <どこを・何のキーワードで>
  先行例: <著者/組織, タイトル> <URL | パス | #N> (取得 YYYY-MM-DD)
  差分: 一致 | 異なる — <理由>
  戻せない: データ | 外部契約 | 人手 — <内容。無ければ行ごと省く>
  軸: 表現不可能 | 還元 | 検出のみ — <1 句>
```

- `本命: 憧れ駆動` は、調査を始める前から結論が決まっていたことを隠さず
  書く。恥ずかしいことではない — 隠すと追認調査(結論に合わせて証拠を
  選ぶ)が起きても検出できなくなる。
- `対抗馬:` は本命と**同じ評価軸**で戦わせた本気の候補。名前だけ挙げて
  比較していないものは対抗馬に数えない。
- `外した候補:` は感触・好みで外した候補を隠さず書く欄。「感触で外した」
  という文言をそのまま使い、分析の結論であるかのような理由を後付けしない。
- 発火条件に当たらない `Dn` はこの重い欄を書かなくてよい(節内整合性は
  gate が見る: `本命:`/`対抗馬:`/`外した候補:` のどれか 1 つでもあれば
  `本命:` と `対抗馬:` は揃っていること)。

## 4. `既存手段:` — 自前で作る前に既存手段を問う(ADR-543)

重い欄が発火する `Dn`(§1 の 3 類型)は、`既存手段:` 行も必須になる。
判定は 3 値の閉語彙:

- `採用: <ツール名/URL>` — 既存のツール・ライブラリをそのまま使う。
- `拡張: <既存パス>` — このリポジトリ内の既存の仕組みを拡張する。
- `自前 — 却下: <候補> (<理由>)` または `自前 — 探索: <どこを・何の
  キーワードで>` — 既存手段を検討した上で自前実装を選ぶ。「簡単だから」
  だけを却下理由にしない。

これは precedent-grounding の「発明する前に先行例を確認する」と同じ
判断を、技術・仕組みの選択という具体的な発火条件に絞って検証可能にした
もの。`先行例:` が「この設計は文献・過去の決定と整合するか」を問うのに
対し、`既存手段:` は「そもそも自前で作る必要があるか」を問う、別の軸の
質問。

## 5. `軸:` を書けない・書きたくないとき

`軸: 検出のみ` は禁止ではなく正直な申告欄。表現不可能化を採らなかった
(採れなかった)ときに使い、なぜ表現不可能にできないかを一言添える
(例: 「nix 評価時に外部状態を読めないため」)。「面倒だったから」を
理由にしない — それは precedent-grounding の `先行例なし:` の
アンチパターンと同じ扱いになる。

## 6. アンチパターン

- データモデル案(外部キーで結ぶ／統合して1ファイルにする、等)の比較で
  「変更量が小さいから」を推奨理由にする。変更量・実装コストの大小は
  この3軸のいずれにも属さない — 還元性の「より安い手段で足りるか」とは
  別物で、「その仕組みが必要な仕事をしているか」を問うものであり、
  「実装が大きいから採らない」という判断そのものとは違う。変更量を
  主軸に使いそうになったら、まず表現不可能性(参照整合性を型で表現
  できるか、検査スクリプトに委ねるしかないか)・還元性(正規化されて
  重複が無いか)で比較し直す。
- 新しさそれ自体を `軸: 表現不可能` や `軸: 還元` の理由に書く。先進性は
  軸 3 でのみ評価する独立の理由であり、他の 2 軸の代用にしない。
- 本命が明らかなのに対抗馬を立てず `Dn` を書き切る(発火条件に当たる
  選択で)。追認調査を隠す最も典型的な形。
- `外した候補:` に分析的な理由(パフォーマンス・機能不足等)を書いて
  実際には感触で外していたことを隠す。感触なら「感触で外した」と書く。
- 「移行コストが高い」「すでに使っている」「battle-tested」を現職を残す
  理由に書く。白紙の評価に持ち込めるのは `戻せない:` だけ(§0)。
- 遡及して既存の非適合な選択を書き直す義務があるかのように振る舞う。
  ADR-0035 D5 により新規の判断のみが対象。
- `既存手段:` の `自前` を選びながら `却下:`/`探索:` を書かない。「時間が
  なかったから」を理由にしない — それも精査せず自前に倒したことを
  隠す形になる。

## 7. 提出前の自己検査

precedent-grounding と共有の gate をそのまま使う:

```bash
~/.claude/hooks/plan-precedent-gate --check <プランファイル>
```

`OK:` が出るまで修正してから ExitPlanMode を呼ぶ。gate は `軸:` の
形式(必須トークンか)、重い欄の節内整合性(本命/対抗馬が揃っているか)、
`既存手段:` の有無(ADR-543)、閉語彙のコスト語と `戻せない:` の値
(ADR-751)だけを見る — 3 軸の判定内容が妥当かは lens A
(copilot-plan-review)が監査する。
