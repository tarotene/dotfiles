# talk-script 事例集

追記型。気づいたときに、skill-gardening のサニタイズ規則に従って抽象化してから足す。

## 事例 1: 見た目先行のスライド生成ツールを、そのままは採らなかった

状況: 「スライドを作るときは、見た目に凝った HTML を作る公開スキル
(zarazhangrui/frontend-slides)に振り分けたい」という依頼。ただし本人は
構成・ストーリーを見た目と不可分に重視し、究極的にはスピーカーノート
(単独で練習でき、ホワイトボードでも話せるプレインテキスト)が主で、
スライドは補助資料にしたい、という方針だった。

そのツールの `SKILL.md` と周辺ファイルを一次ソースで読んで確かめたこと
(取得 2026-10-19):

- スピーカーノートを出力に載せる機構が無い。言及は、PPTX 変換時に抽出した
  ノートを HTML コメントとして残す 1 行のみ。プレゼンタービューも、ノートの
  書き出しも無い。
- 構成を先に固める工程が無い。最初の質問は目的・枚数・素材の有無・密度の 4 つ
  だけで、アウトラインの確認は画像を渡したときにしか走らない。
- 主従が逆。スライドが主でノートは付属。担うのは見た目の層(スタイル選択から
  単一 HTML の生成まで)だけ。

判断: 丸ごとのルーティングはしない。正本は Marp の Markdown 1 ファイルに置き、
各スライド末尾のコメントに語りを書く。練習用の原稿は `marp --notes` で導出する。
動かして確かめた結果(nixpkgs の marp-cli、2026-10-19): 3 枚のデッキで、
コメントの語りがスライド順に連結され、境界は `---` 1 行のプレインテキストとして
書き出された。非対話で動かすには `--no-stdin` が要る。

見た目に凝った HTML が欲しいと明示されたときだけ、そのツールを rev 固定で
スキル走査の外に置いた配備先から呼ぶ。スキルとして置くと、description が
「スライドを作るとき」に反応して、構成より先に見た目の工程へ入ってしまう。

一般化: 見た目の生成ツールを選ぶ前に、「そのツールは語りを持てるか」
「構成を先に固める工程があるか」を確かめる。どちらも無ければ、
そのツールは描画層の 1 候補にとどめ、主従を決める正本は別に置く。

## 事例 2: 商談用スライドへの外部レビューを、規則に分けて採否した

状況: 面談の画面共有用に作った 4 枚のスライド(自己紹介、提供できる支援、実績、
条件)を、外部の人にレビューしてもらった。返ってきたのは、4 枚を組み替えた全文の
案だった。案には良い点と、素材に無い内容が混ざっていた。

やったこと: 案を丸ごと採否せず、各変更の背後にある規則を 12 個に分けて取り出し、
1 つずつ素材と既存の方針に突き合わせた(取得 2026-10-19)。

| 規則(案から逆算) | 採否と理由 |
|---|---|
| 構成を、誰か → 何を → なぜできるか → どう関わるかの一本道にする | 採用。構成を先に固める §2 の具体形 |
| 見出しは主張の 1 文。小見出しに役割を添える | 採用。英語の併記は、読み手が国内の 1 人なので不採用 |
| 最初のスライドで、何の専門家で何が解けるかを伝える | 一部採用。強みを掛け算で示す原則は採るが、素材が看板に上げない分野を足す文は採らない |
| 発表者ノートにしか無い具体語を面に出す | 採用。画面共有は口頭で通じないときに使うので、語りに頼る語は面にも要る |
| 実績の各項目に「取り組み」と「言えること」を付ける | 一部採用。素材に無い標語(「壊れにくい設計プロセスの型化」など)は不採用 |
| 困りごと → 支援 → 変わること の表に番号と方法を足す | 採用 |
| 条件を、相手が案件を当てはめられる形で示す | 採用。ただし出典に定義の無い換算語と、理由の明示は不採用 |
| 関与の進め方を時系列の段階で示す | 不採用。素材に無い創作 |
| 最後に、相手の判断に要る情報と、こちらから聞くことで締める | 採用 |
| 年数・年月を明示する | 採用 |
| 強い動詞(主導、確立)を避け、固有名詞を伏せる | 採用(既存の方針) |
| 各セルの要点を太字にする | 採用。1 セル 1 か所まで |

暗黙の規則のうち、1 つがこのスキルの講演型と真っ向から対立した。案は「話しながら
画面を見せるだけで成立するように、スライドを単体で読める資料にし、表と情報量を
増やす」。講演型は 1 枚 1 証拠で箇条書きを既定で禁じるので、逆向きになる。

判断: 場で分ける。単体で読む場面を §4a の資料型とし、講演型は変えない。見出しが
主張の 1 文であること(Alley らの assertion-evidence の見出し規則)は両方で保つ。
資料型の先行例は、読まれる視覚的な文書としての Slidedocs(Duarte)。定義と、発表
される資料との対比までを確かめた。設計規則の全文は未確認。

一般化:

- 外部のレビュー案は、規則の出力として読む。案を丸ごと採否せず、規則に分けて
  素材と突き合わせると、採る部分と採らない部分が理由つきで残る。
- 良い案ほど、素材に無い具体(時系列、数値、標語)を足しやすい。聞こえの良さで
  採らず、素材にあるものだけを載せる。
- 規則が既存のスキルと対立したら、どちらかを曲げず、適用する場面で分ける。
- スキルができる前に作った資料は、派生先の HTML が正本になっている。そのときは
  送ったファイルと同じものを git に控えとして残す。
