追記型。気づいたときに、skill-gardening のサニタイズ規則に従って抽象化してから足す。

## 事例 1: 見た目先行のスライド生成ツールを、そのままは採らなかった

状況: 「スライドを作るときは、見た目に凝った HTML を作る公開スキル
(zarazhangrui/frontend-slides)に振り分けたい」という依頼。ただし本人は
構成・ストーリーを見た目と不可分に重視し、究極的にはスピーカーノート
(単独で練習でき、ホワイトボードでも話せるプレインテキスト)が主で、
スライドは補助資料にしたい、という方針だった。

そのツールの `SKILL.md` と周辺ファイルを一次ソースで読んで確かめたこと
(取得 2026-10-19):

- スピーカーノートを出力に載せる機構が無い。言及は、PPTX 変換時に抽出した
  ノートを HTML コメントとして残す 1 行のみ。プレゼンタービューも、ノートの
  書き出しも無い。
- 構成を先に固める工程が無い。最初の質問は目的・枚数・素材の有無・密度の 4 つ
  だけで、アウトラインの確認は画像を渡したときにしか走らない。
- 主従が逆。スライドが主でノートは付属。担うのは見た目の層(スタイル選択から
  単一 HTML の生成まで)だけ。

判断: 丸ごとのルーティングはしない。正本は Marp の Markdown 1 ファイルに置き、
各スライド末尾のコメントに語りを書く。練習用の原稿は `marp --notes` で導出する。
動かして確かめた結果(nixpkgs の marp-cli、2026-10-19): 3 枚のデッキで、
コメントの語りがスライド順に連結され、境界は `---` 1 行のプレインテキストとして
書き出された。非対話で動かすには `--no-stdin` が要る。

見た目に凝った HTML が欲しいと明示されたときだけ、そのツールを rev 固定で
スキル走査の外に置いた配備先から呼ぶ。スキルとして置くと、description が
「スライドを作るとき」に反応して、構成より先に見た目の工程へ入ってしまう。

一般化: 見た目の生成ツールを選ぶ前に、「そのツールは語りを持てるか」
「構成を先に固める工程があるか」を確かめる。どちらも無ければ、
そのツールは描画層の 1 候補にとどめ、主従を決める正本は別に置く。
