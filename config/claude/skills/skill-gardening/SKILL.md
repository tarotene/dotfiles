作業セッションで得た知見を、このリポジトリ(公開)に固定化するときの手順。「何に貯めるか」「どう配線するか」「どう書けば社内情報が漏れないか」の3点を毎回検討し直すのは無駄なので、ここにまとめる。

## 1. 器を選ぶ

| 知見の種類 | 器 |
|---|---|
| モデルが読んで従うべき判断知識(「こう考えろ」) | スキル。既存スキルの守備範囲に収まるなら、そのスキルの事例集(`cases.md` 等)に追記。新しい領域なら新設 |
| 機械的に検査・強制できる違反(「このパターンのファイル操作をしたら止める」) | フック(`config/claude/hooks/`) |
| ほぼ全セッションで常に必要な、ごく短い原則 | グローバル `CLAUDE.md`(コンテキスト税が全セッションにかかるので最終手段) |

判断の目安:
- 発動すべき場面を `description` のキーワードで具体的に言い切れるか(言い切れないなら発動精度が出ない)
- 本文が肥大しないか(不変の原則と、増え続ける事例は別ファイルに分離する)
- 機械的に検査できるなら、判断をモデルに委ねずフックに落とす方が確実

## 2. dotfiles への配線チェックリスト

1. `config/claude/skills/<name>/SKILL.md` を作成(frontmatter は `name` / `description` のみ。既存スキルの形式に合わせる)。事例集を持つなら同じディレクトリに `cases.md` 等の補助ファイルを置く。
2. `home/modules/claude.nix` に `home.file.".claude/skills/<name>/<file>".source = repoConfig + "/claude/skills/<name>/<file>";` を追加する。ファイル冒頭の機能一覧コメントにも1項目追記する(既存のフックの説明スタイルに合わせ、動機と設計意図を書く)。
3. `docs/claude/<name>.md` に設計ドキュメントを添える: 動機(どの失敗・不便から生まれたか)、器をスキルにした理由、内部構成の意図、運用(いつ・どう追記するか)。
4. home-manager switch して配備を確認し、新しいセッションで `skills 一覧` にあることと、想定した場面で自動発動することを確認する。

## 3. サニタイズ規則(公開リポジトリの正本 — 各スキルはここを参照し、重複させない)

このリポジトリは公開なので、社内固有の情報は一切載せない。知見を書くときは次を満たす:

- **固有名詞ゼロ**: 社名・製品名・機体名・プロジェクト名・リポジトリ名・人名・Issue/PR番号を書かない
- **URLゼロ**: 社内リソースへのURLは書かない(公式ドキュメントなど一般に公開された参照先は例外)
- **実物の持ち込み禁止**: スクリーンショット・実ファイルのコピー・実データを貼らない。構造を抽象化して書き直した再現のみ可
- **数値・識別子の出自を確認する**: 座標・アドレス・容量・パラメータ値などが社内の設計を特定しないか確認する(公開データシートに載っている値は可)
- **書き方は「抽象化した実話」**: 失敗の因果関係(何をしようとして、何が起きて、なぜ起きたか)はそのまま保存し、文脈だけを一般名詞(「組み込みファームウェアの手順書」「Webアプリのデプロイ手順」等)まで抽象化する。完全な作り話に差し替えると因果関係が歪みやすいので避ける
- **コミット前の最終確認**: 追記した差分を、固有名詞とURLの観点で読み直す。迷ったら書かない側に倒す

## 4. スキル設計の作法

- `description` に発動キーワードを具体的に列挙する(日本語・英語の両方を含めておくと拾われやすい)
- 不変の原則(本文)と、増え続ける事例(別ファイル)を分離する
- 「〜するとよい」という推奨表現より、「〜するまで完成と呼ばない」のような検証可能な条件として書く方が実効性が高い
