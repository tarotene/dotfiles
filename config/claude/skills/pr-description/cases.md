# 事例集

## ターミナルのプロンプト表示を変える変更が、証跡なしでマージされた

シェル起動時のプロンプト(カレントディレクトリの省略表示ロジック)を変更するPRで、本文には変更点の説明はあったが、実際の表示例(Before/After)は一切載っていなかった。差分はロジックのコードだけを見ても、実際にどう見た目が変わるのか判断しづらい種類のものだった。

レビュー時点では変更者が直近の記憶を頼りに承認したが、数か月後に別の不具合調査でこのPRの履歴を追った際、コードを読んでも「変更前は実際どう表示されていたのか」が分からず、再現に別途手間がかかった。

**教訓**: GUI/Webの画面変化だけでなく、ターミナル/TUIの見た目の変化も、後から見て伝わる証跡が必要になる点は同じ。「コードを読めば分かるはず」は、レビュー直後の記憶がある間しか成立しない。

## マージ後の残作業を全部「要確認」に書いてしまった

外部 MCP サーバーのトークン供給経路を切り替える PR で、「登録の適用」「動作
確認」「旧リポジトリの archive」を含む残作業リストをそのまま「要確認」に
列挙した。実際にはこのうち Claude 自身が実行できるものが大半で、真に
ユーザーでなければ実行できないのは「外部サービスでの資格情報発行」1件
だけだった。ユーザーから「これは私がやることですか」と指摘され、
再仕分けした上で本文を書き直した。

指摘を受けて分かったのは、「要確認」を書く前に一度「この項目は Claude が
実行できないのか、それとも単に後回しにしただけか」を自問していなかった
ということ。後者であれば、PR 作成を待たずその場で実行すべきだった(実際、
`hms .` を PR 作成後に実行し、動作確認まで済ませてから「検証」節に書き足す
形で修正した)。

**教訓**: 「要確認」に何か書く前に、それが本当にユーザーでなければ実行
できないのか(資格情報発行・ハードウェア操作・secrets 衛生・GUI操作・
人間の判断のいずれかか)を毎回問い直す。実行できるものは今すぐ実行する。
詳細は `SKILL.md` の「6. 要確認の粒度とブロッキング判定」。

## 「要確認」のブロッキング理由は正しかったが、手順が接地されていなかった

ある API キーを発行する PR で、鍵の受け渡しを唯一のブロッキング項目
(secrets 衛生)として正しく1件に絞れていたが、その手順は「取り出した値を
クラウド環境の credentials に登録する」とだけ書かれ、どの画面のどの項目に
何を入れるか、完了をどう確認するかが無かった。登録先の値(宛先ホスト・
ヘッダー名など)は別の追跡 Issue に既にあったが、そちらへの参照も無かった。

修正では、値の取得コマンドをクリップボードへ直接パイプする形にして生値を
端末やセッションログに残さないようにし、公式ドキュメントで確認した正確な
UI 導線(設定画面名→項目名)を番号手順として書き、実際に API を叩いて疎通を
確認するコマンドを完了確認として添えた。

**教訓**: ブロッキング理由の絞り込み(tarotene/dotfiles#239 の教訓)と、
手順自体の具体性は別の失敗軸。理由が正しく1件に絞れていても、手順が
「後は任せます」型の丸投げでは読み手が迷う。詳細は `SKILL.md` §6「手順を
接地する」。この教訓を機に、閉語彙のブロッキング理由・番号手順・完了確認の
3要素が揃っているかを `pr-confirm-guard.sh`(PreToolUse gate)が機械検査
するようになった。

## 実機確認を未チェック task list として PR に残した

ある機体のホスト側テストコード修正 PR で、ホスト側の `cargo test` は
通したものの、実機での受入確認は担当者の予定に依存するため `## Test
plan` に `- [ ] 実機(実機名)での確認は担当者の受入試験実施時に確認`
という未チェック項目を残したままマージした。この形はレビュアーに
「担当者の確認が終わればチェックが埋まってマージできる」という運用に
見せてしまい、PR の寿命が確認者の予定に紐づいてしまった。base が進むほど
rebase 負債が積み、確認が遅れるほど PR が古くなっていく。

**教訓**: 人の確認が要る残作業は「未チェックの task list をマージまで
残す」形にせず、後続 Issue へ払い出す。PR 本文には払い出した Issue への
ポインタ(`- #N — <一言>`)だけを `## 要確認` に書き、マージ可否は CI と
レビューで決める。詳細は `SKILL.md` §6「要確認の粒度と後続 Issue への
払い出し」。

## gh heredoc の裸バックティックが GitHub 上でエスケープ付きのまま描画された

`gh pr create --body "$(cat <<EOF ... EOF)"` のように delimiter をクオートしない heredoc(`<<EOF`)の中で、本文の Markdown コードスパン `` `code` `` をエスケープして `` \`code\` `` と書いてしまい、GitHub 上にバックスラッシュ付きの可視文字としてそのまま描画される事故が繰り返し起きた。

原因は heredoc の delimiter の扱いの取り違え: `<<EOF`(クオートなし)は `$VAR` 展開・コマンド置換・バックティック解釈が有効なヒアドキュメントで、この中のバックティックは本来シェルに解釈されてしまう。それを避けようとして手動でエスケープすると、今度は Markdown レンダラ側がエスケープごと文字として表示してしまう。

**教訓**: `<<'EOF'`(delimiter をシングルクオートで囲む)を使えば `$VAR` 展開・コマンド置換・バックティック解釈のいずれも発生しないため、本文中の Markdown バックティックはエスケープなしでそのまま書ける。

**規律**:
- heredoc の delimiter は必ずシングルクオート付き(`<<'EOF'`)にする。
- 本文中の Markdown バックティックを `` \` `` でエスケープしない。
- 投稿・編集の直後に次のコマンドで検証し、`OK` が返らなければ同じ heredoc を再投稿して修正する。
  ```bash
  gh pr view <N> --json body --jq .body | grep -F '\`' && echo BAD || echo OK
  ```
  (検出したいのはバックティック単体ではなく、エスケープされた `\`` 列 — 正常なコードスパンのバックティックまで誤検出しないよう、検索パターンにバックスラッシュを含める。)
