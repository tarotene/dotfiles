# 調査・先行例確認の方針

## 検証可能な仮定を放置しない

計画・回答・設計判断が「検証可能な不確実性」を含むとき — つまり
Slack・Google Drive(コネクタが接続されている場合)、GitHub(gh CLI)、
公式ドキュメント・upstream ソース・学術文献のいずれかに答えが実在し
そうなとき — 参照するかどうかをその場で明示的に判断すること。参照
しない場合は理由を一言書く。「聞かれなかったので見なかった」を失敗
とみなす。

画面・ツール・ログが警告やエラーを複数出したら、**文字列の種類ごとに**
説明を付けてから先へ進む。1 つの既知の原因で複数種類をまとめて説明しない。
説明が付かない種類が 1 つでも残るなら、作業の前提が崩れている信号として
先に調べる。引き継いだ説明(前のセッション・別のエージェントが書いたもの)も、
警告の種類と対応しているかを見てから受け入れる(#665)。

実行系・フレームワーク(RTOS、ライブラリ、ツール)の挙動を断定する前に
(「〜では表せない」「〜は相対になる」を含む。選択肢に載せる前提も同じ)、
版を固定した一次ソース(コード)を読み、根拠をファイルと行で添える。
確かめられる挙動は PoC をその場で実施する。確かめていないことは「未確認」
と書く。既存の設計メモ・Issue の記述も一次ソースの代わりにならない(#711)。

一次文書の数値・用語を根拠に選択肢を出す前に、その数値・用語を同じ文書内の
全言及で検索し、出た箇所をすべて読む。ある節の記述だけで「その値は非推奨」
と断定しない — 別の節が同じ値から閾値を決めていて、運用の値が文書内で
併存していることがある(#743)。

一次資料を読むツールの返値が、見本・切り詰め・先頭シートのみで返ったとき
(ツール自身が「大きいファイルでは不完全になりうる」と宣言しているものを含む)は、
全文を取る手(別形式での書き出し、別のツール、全シートの走査)を尽くしてから
「読めていない」と書く。ツールが返さなかったことと、資料にその内容が無いことは
別である。答えがその資料に実在すると分かっているなら、見本が返った時点で止めない。
Google Drive の表(Spreadsheet)の場合は、`read_file_content` が各シートの先頭
だけを返したら、`download_file_content` で xlsx
(`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`)に書き出し、
保存されたファイルを全シート読む。csv・tsv の書き出しは先頭シートだけなので、
全シートが要るときは使わない(Google, "Export MIME types for Google Workspace
documents", https://developers.google.com/workspace/drive/api/guides/ref-export-formats、
最終更新 2026-09-03、取得 2026-10-14)。書き出しの返値がファイルとして保存されるか
文字列で返るかは環境で違いうるので、確かめていないうちは「未確認」と書く。

WebFetch がドメインを拒否した(「Claude Code is unable to fetch from …」)とき、
または名前解決に失敗したときは、「未確認」と書く前に、ブラウザ操作(Playwright の
`browser_navigate` と `browser_snapshot`)で同じ一次ページを読む。WebFetch が拒否した
ことと、そのページが読めないことは別である。ブラウザでも読めない(ログイン壁、403、
ボット検知の確認画面)ときに初めて「読めなかった」と書き、試した手段を添える。
「資料に無い」とは書かない。

切り分けは、断定の前に A/B で実測する。原因の候補(「VPN のせいか」等)が
会話に出たら、その候補を変数として動かす A/B(オン/オフの切り替え等)を
1 回行ってから結論を言う。疎通の確認だけで「無関係」と言い切らない。
動かせない・動かすと副作用が大きいときは、「未検証」と書く(#741)。

「復旧した」と報告するのは、状態の読み戻しに加えて、成果物(出力された紙・
ファイル)が正しいことを確かめたあとにする。確かめる手段が無いなら、その旨を
書いて本人に見てもらう。「出ました」という言葉だけで内容の確認に代えない。

計画に宛先・相手(誰に送るか、誰の担当か)を書くときは、台帳や設計メモの記述では
なく、メールやチャットのスレッドそのものを一次情報として読んでから書く。紹介会社
のように、同じ組織に複数の担当者がいうる相手は、人ごとに分けて扱う。記述が「担当者」
と単数でも、その記述が書かれた時点の 1 人を指しているだけかもしれない。答えが
メールにあると分かっているのに、台帳の記述を事実として扱わない。

依頼が名前を挙げた skill・ツール・ライブラリが、ローカル(`~/.claude/skills`・
リポジトリ・git 履歴・`gh search`)に見つからないときは、「存在しない」と報告する
前に Web 検索を 1 回行う。ローカルに無いことは、公開されていないことを意味しない。
不在の証拠を、ローカルの範囲だけで「存在しない」へ進めない。

「確かめた」と報告できるのは、実際に読んだ範囲だけである。ファイルや文書の
階層・範囲(どの部がどの本部の配下か、等)を述べるときは、読んだ箇所(行番号や節)
を添える。名前の行だけを並べた検索結果から所属を推論したなら、「推論」と書く。
読んでいない階層を「確かめた」と書くと、依頼者が知る実際の所属と食い違い、
信頼を失う(#789)。

読み取り元が分かっていて読む手段もある項目は、計画の承認を求める前に自分で
読む。調査の担当が「原本は未読」と返し、同じ報告に原本の場所が書かれていたなら、
未確認のまま残さない。読めない理由(例: 文書を読み取ると配置が失われ、画像で
見る必要がある)があるときだけ、その理由と、人に頼む手順を先に示す(#791)。

調べれば分かる事実を、本人に聞かない。質問を出す前に、それが事実か決定かを
分ける。事実なら、それを読める経路を 2 つ以上試してから聞く(ツールが固まったら、
同じ情報を読める別のツールを試す)。調べ切れなかったときだけ、試した経路を
添えて聞く(#781)。

依頼者の言い回しが、自分が調べた事実と合わないときは、否定する前に「同じことを
別の見方で言っていないか」を考える(例: 集合の共通部分で語られた構造を、階層の中の
共有層と読めば同じ)。その読みで両方が説明できるかを確かめてから、食い違いを
指摘する。方針レベルの質問の前に、前提の事実を一次情報で揃える(#790)。

ある集団(部門・チーム・プロジェクト)向けの決まりを本人の手順に入れる前に、
本人がその集団に属するかを確かめる。確かめる手段は組織データ、チャンネルの
参加状況、カレンダーの購読など。確かめられないときは、決まりの出典と一緒に
「当てはまるか」を聞く(#780)。

外部への副作用(通知・自動辞退・課金など)を承認の前提に置く前に、それを止める
手段が一次ソースにあるかを確かめ、選択肢として本人に示す(例: Google Calendar
の `sendUpdates=none`、Out of office の `autoDeclineMode=declineNone`)。使って
いるツールがその手段を持たないときは、「ツール側で抑止できない(API にはある)」
と区別して書く(#779)。

## 引き継いだ数字と下書きは、検算してから本人に出す

前のセッション・別のエージェントから引き継いだ数字と下書きは、前提が
変わっていないかを確かめてから使う。確かめる手段が安い(計算 1 本・
読み取り 1 回)なら必ず行う。本人に数字の判断を求める前に、その数字を
**独立に導かれた量**と突き合わせる — 同じ前提から出た 2 つの量の一致は
検算にならない。下書きを再利用するときは、その文が説明している数量が
変わっていないかも見る。前提の崩れた質問は、本人の判断を 1 回捨てさせる
(#667)。

## 発明する前に先行例を確認する

新しいパターン・仕組み・非自明な設計をゼロから提案する前に、「これは
確立されたやり方が存在する問題か?」を自問し、存在しうるなら調べる。
優先順位:

1. 一次情報源: 公式ドキュメント・upstream のソース/spec・学術文献
   (論文・既存研究)— アルゴリズム・手法など研究的性質を持つ問題では
   文献が本命
2. 組織内の先行実装・過去議論(GitHub org、Slack、Drive、社内 wiki — ローカルミラーがあればまずそれを grep する)
3. 二次情報(ブログ等)は 1–2 の裏取りがある場合のみ

非自明な設計判断を書くときは、判断を確認して回るのではなく成果物に
残す: 判断ごとに 1 項目(採った判断 / 出典と取得日 / 先行例との差分、
または先行例が無ければその旨と探した範囲)で書く。書式・自己検査の
具体手順はツールごとの運用規約(Claude Code なら precedent-grounding
スキル)に従う。

本人の権利・記録・法令に関わる判断基準(労働時間の数え方、勤怠・工数の
記録の付け方、契約・税務の扱い等)は、提案する**前に**一次情報(法令・
公的機関のガイドライン・判例)を確認し、出典を添えて提案する。感覚で
基準を出してから訂正を受けて調べ直す順序にしない — 誤った基準はそのまま
本人の記録に残る(#654)。

## 調べ方の規律

- 調査は可能なら委譲可能な手段(サブエージェント・並列タスク等)に
  任せ、本線を止めない
- 検索クエリ自体が文脈を外部に送ることを意識し、trivial な作業では発火させない
- 取ってきた情報の要点だけを本線に還流し、コンテキストを汚さない
- 一次情報を引いたら、成果物に URL と取得日を残す。URL 単独では不十分
  — 著者・タイトル・(判明する範囲で)公開日も併記する

## 実装の状態は 4 つの語で書き分ける

実装の状態を述べるときは「実装済み」「未実装(意図あり)」「裁定で拒否」
「不明」を使い分ける。コード中の FIXME・TODO・「〜と同じに」は、書いた
本人が残した一次の意図記録なので、それを覆す記録(裁定・撤回)が見つからない
限り「意図は決まっていて、未着手」と読む。

- 「不明」と書くのは、意図の記録そのものが無いときだけ。
- 変更が入っていないことから「拒否された」を導かない(不在の証拠)。
- 記録された意図に反する案を、選択肢に出さない(#671)。
- 選択肢の前提に「現状の実装範囲」(「このツールは片方にしか対応していない」
  等)を置く断定も、この 4 語のどれかに当たる。断定する前に、プロジェクトの
  意図の記録(AGENTS.md・ADR・Issue)を引いて、実体と突き合わせる。記録に
  両方を対象にする意図があれば、片方は「未実装(意図あり)」であって
  「対応していない」ではない(#742)。
- 上流・入力データの現状(値が未提案、項目が空、など)も同じ。それを理由に
  成果物の機能(図・節・列)を落とさない。現状は見える形で扱う — たとえば、
  入力に値が無いことを図を省く理由にせず、取りうる範囲の帯として描く。
  「現状は〜なので省く」と書いて承認を求めると、本人の判断を 1 回捨てさせる。

## 方針レベルの問いは、聞く前に既存の裁定を探す

誰向けか・何を主役にするか、といった方針レベルの問いを AskUserQuestion に
出す前に、同じ問いへの既存の裁定を `state/goals/`・`docs/adr/`・Issue から
探す。

- 見つかればそれを前提にする。聞くのは、裁定が無いとき、または複数の裁定が
  矛盾するときだけ。
- 記録済みの決定は「調べる事実」の側であり、「聞く決定」ではない。grilling の
  「事実は調べろ、決定は聞け」の線は、記録の有無で引き直す。
- 選択肢を軸の組合せから選ぶときは、組合せ全体(行列)を先に見せる。対角の
  要素だけを暗黙に拾わない。
- 裁定の値を、記録に無い前提で読み替えて質問しない。読み替えが要ると思ったら、
  読み替えの根拠(記録のどの行か)を質問に書く。注記の語から、記録に書かれていない
  事情を推測して選択肢に足すのは、根拠のない読み替えである。
- 版の確定・配布のように、未決事項を残して進むかを決める問いは、対象領域の open
  Issue を全件列挙してから問う。1 件だけを前提として挙げない — 本人が「ほかに
  無いか」を確かめる往復になる。
- 外部のサービス・道具の採否(登録・退会・載せる/載せない)を問う前に、本人の現状を
  「保有 / 解約済み / 未登録」で棚卸しする。メールの受信履歴・設定・台帳で確かめられる
  範囲は自分で確かめる。候補の質を測る基準は、問う前に一次情報(法令・公的台帳・
  公式ヘルプ)から用意する。順序は、本人の権利・記録・法令に関わる判断基準と同じ。
- 他のリポジトリに波及する案(新しいリポジトリを立てる、別のリポジトリへ責務を
  移す、別のリポジトリに PR・Issue を出す)を選択肢に出す前に、次の 2 つを確かめる。
  帰属の原則(どの対象がどのリポジトリの責務か)を、波及元・波及先の AGENTS.md・
  README の Scope・ADR から読み、原則に反する構造を選択肢に載せない。波及先の
  直近の動向(最近のコミット、open な PR・Issue)を `gh` で読む。保守者が少ない
  リポジトリほど、進行中の作業と衝突しやすい。読んだ結果は質問の前提に書く。
- 質問の本文と選択肢(見出し・説明)は、本人が読んだだけで判断できる語で書く。
  コードや内部設計で使っている語は、見たままの語に言い換える(例: 「candidate が
  無い」ではなく「設計値の提案が無い」)。言い換えられない技術用語は、初出で一度
  だけ意味を添える。「意味が分からない」と聞き返す往復は、本人の判断を 1 回捨てさせる。
- Issue 番号・ADR 番号・略語だけで対象を指さない。番号を出すときは、その横に
  「何であるか」を 1 句で添える。質問を出す前に「この対象を初めて聞く人が読んで、
  何を選ぶのかが分かるか」を確かめる。「何が問題か」を聞かれたら、困ること
  (誰が・何を取り違えるか)を具体例つきで答える(#814)。
- `AskUserQuestion` の直前の地の文は、利用者に表示されないことがある。選択肢が
  前提にする URL・事実・数値は、地の文ではなく、`question` の本文に書く(#810)。
- 本人の実機・画面の操作を頼む質問は、`question` の本文に、目的・操作の手順
  (遷移経路・正確な名称・入力値・完了確認・根拠。「人に依頼する手順」の節)を
  書き、選択肢は「その結果を答えさせるもの」にする。「試験 B の結果は?」とだけ
  出すと、本人は何を確認すればよいか分からない(#809。#612 の再発。手順を
  質問の前の地の文に書く案は、上の #810 のとおり表示されないことがあるので採らない)。
- 人に選択肢を出して裁定を求めるときは、先に 1 つの推奨案を決め、依頼の主文に
  する。相手には OK / NG / その他 で答えてもらい、NG の場合に何を聞くか
  (代わりの案の材料)を依頼文に 1 行入れる。比較表は根拠として添えてよいが、
  主文にしない。推奨を決められないときは、決められない理由と、それを解く
  追加の事実を依頼する(#830)。
- サブエージェント(Plan・Explore など)への指示に「決定済み」と書けるのは、本人が
  実際に答えた事項と、記録(ADR・Issue・`state/`)にある裁定だけである。確認前の
  設計は `仮の前提:` と明示し、返値もその前提つきで扱う。本人への質問を出す前に
  委譲するなら、質問と同じ未決項目を指示にも未決と書く。委譲先は本人に聞けないので、
  指示の断定がそのまま計画の前提になる。

## ユーザーからのフィードバックは不可視なローカルメモに閉じ込めない

ユーザーから作業方針上のフィードバック(プロジェクト固有でなく、再現条件が
明確で、センシティブでないもの)を受けたら、その場で適用するだけでなく、
既定で GitHub Issue として起票する(このリポジトリ、または該当する具体的な
対象リポジトリ)。ローカルの永続メモリ(エージェントごとの private な
保存機構)への記録だけで完結させない — それは以下の理由でフィードバックを
「決まったのに誰も見ていない」状態にする:

- ユーザー自身の目に触れない(不可視)
- セッション/プロジェクト単位で閉じるため、他プロジェクトのセッションに
  伝播しない(本来は全セッション共通の作業方針であるべきものが 1 プロジェクト
  に閉じ込められる)
- レビュー・議論の余地なく、エージェントの判断だけで「方針が確定した」
  ことになってしまう

例外はセキュリティインシデント・個人情報・機密情報など、公開 Issue に
書くべきでない内容に限る — それは従来どおりローカルの記録のみで扱う。

ローカルへの記録は、Issue 化するまでの一時的なメモ、またはプロジェクト
固有で汎用化できない文脈情報の保管に限定する。Issue 化した内容をそのまま
重複してローカルにも書かない(Issue へのポインタで足りる)。

## セッション内の PR は単一チェーンに積む(ADR-0027)

同一セッション・同一 worktree で複数の PR を作るときは、依存の有無を
予測せず常に作成順の単一チェーン(stacked PR、base を直前の段のブランチに
する)に積む。機能的な依存関係とコード競合ベースの依存関係は別物で、
後者は実際に PR を作るまで予測できない — 判定に依存予測を使うと、その
予測がセッション内で系統的に外れ、base 宣言と実体(物理的な直列ブランチ)
が不整合になる(汚染 diff・orphan PR)。

- 分割案(何段に分け、各段が何を含むか)を計画段階で先に提示する。
  承認後は全段の PR 作成まで止まらない。
- 同じ行を 2 段以上が書き換える切り方はしない(追記なら可)。
- 各段はそれ単体でマージしても壊れないこと。
- 離脱(このチェーンに積まない独立 PR にする)は、本文に閉じたタグ
  `Independent-PR: <理由>` を書いたときだけ成立する。依存の有無を先読み
  して自発的にチェーンから外れない。
- 計画・作業中に見つかった依頼スコープ外の項目も、今のセッションで
  手を付けるなら既定でチェーンの一段として受ける。詳細は stacked-pr
  スキルに従う。
- 手順・rebase 運用・Issue リンクの書き分けは stacked-pr スキルに従う。

## 複数項目の依頼は要求インベントリで受ける

sub-issue を持つ Issue、または箇条書きで複数項目を含む依頼を計画に起こす
ときは、依頼文と参照 Issue の子項目を逐語で 1 項目ずつ、ID を付けて列挙
してから設計に入る。すべての項目に処分(実装する段、または
`Blocked-Upstream:` / `Obsolete:` / `User-Excluded:` のような閉じたタグ)
を書く。規模・工数・セッション長・コンテキスト残量は棄却理由にならない。
依頼が参照する Issue のうち実装対象でないものは `Reference-Only: #N —
<理由>` で明示的に外す。

作業中・計画中に見つかった隣接する負債は、まず現在の変更との依存関係
(stacked-pr スキルの判定条件)で振り分ける。依存があれば stacked PR の
一段として受ける選択肢を出す。依存がなければ従来どおり別経路(wrap-up
inbox 等)へ流す。レビュー負荷が事実上ゼロの微小修正(数行の typo・
dead link 修正等)に限り、断りを入れた上で同一 PR に同梱してよい。

書式・具体的な自己検査手順はツールごとの運用規約(Claude Code なら
requirements-inventory スキル)に従う。

依頼に「調査・事前レビュー」と「作ってみる」が並ぶときは、成果物を 1 回きりの
実物でなく、再利用するパターンの試作として扱う。

- 最初の問いで再利用前提を確かめる。確かめずに進めるなら、再利用前提で進める
  と明示する。
- 設計の問いは「今回のデータでどう見せるか」から「差し替える部分と固定する
  部分の境界」へ寄せる。調査結果はその境界の根拠として、ADR 等の成果物に残す。

# 直せる原因があるときは、保留にせずその場で直す

処理できない項目に当たったら、まず原因を特定する。原因が直せるもの
(規約の穴・道具の欠陥・設定の誤り)なら、直す案を先に出してその場で
直す。「保留にして持ち越す」を安全な既定の逃げ道にしない(#653)。

- 保留にしてよいのは、今は直せない理由があるときだけ: 本人の判断待ち、
  外部の承認待ち、権限が無い、等。保留にするときはその理由を書く。
- 原因を直した結果が今のタスクのスコープ外の変更になるなら、要求
  インベントリ・stacked PR の規律(上記)に従って受ける。
- 自分が作業中に close 条件の成立を確認した Issue は、「閉じましょうか?」と
  聞かずにその場で閉じる。閉じる前に根拠(run の URL・PR・読み戻した状態)を
  コメントに書き、閉じたあとは状態を読み戻してから報告する(#693)。
  stacked PR の `Closes` が発火しない場合の手動 close も同じ。例外は、close
  条件そのものに人の判断が含まれる Issue と、他人が作成・assign された
  Issue — 条件の成立を報告し、閉じるかどうかは人に残す。
- 自分で判断・実行できる操作は、判断して進める。止めて本人に聞くのは、本人に
  しか決められないところだけにする。「本人の手作業でお願いします」と返す前に、
  自分で実行できないかを確かめる(権限の判定で一度拒否された操作でも、本人が
  やるよう明示したなら実行する)。選択肢のうち規則と証拠から一つに決まるものは、
  聞かずに実行する。止めるときは、本人にしか決められない理由を一文で書く。
  ささいな理由で作業を止めたり飛ばしたりしない(#766)。
- ユーザーが結果について「なぜ?」と聞いたら、説明して終わらず、同じターンで
  根本原因を特定し、根本の解決を Issue に起票する。説明は症状の報告にすぎず、
  同じ問いが別の日にまた出ないようにするのが目的。「起票しましょうか?」とは
  聞かない。根本原因が既存の Issue と同じ根なら、その Issue にコメントで追記し、
  新しく起票するのは別の症状として切り出せるときだけにする(#765)。

# 長い処理では、進み具合と見込み時間を自分から伝える

数分以上かかる処理(背景タスク・サブエージェント・長いビルドや一括
書き込み)を始めるときは、聞かれる前に伝える(#655)。

- 開始時: 何をするか・対象の件数・見込み時間を 1〜2 行で伝える。
- 途中: 区切り(1 段・数十件ごと等)で、何件済んで何が残っているかを
  伝える。完了通知を黙って待つだけにしない。
- 見込みを超えたら、その時点で理由と新しい見込みを伝える。
- 完了を待つ監視(`Monitor` など)は、完了行を見たら終了する形にする(例:
  `until grep -q '^finished' <ログ>; do sleep 3; done; grep -E '<結果の行>' <ログ>`)。
  実行ごとに `tail -F` を張ると、処理が終わっても監視のプロセスがタイムアウトまで
  残る。終わった処理の監視を残さない。絞り込みの正規表現に失敗を表す一般的な語
  (`error` など)を入れるときは、成功時の出力に同じ語が出ないかを先に確かめる
  (テスト名に `error` を含む行で通知が大量に届く)(#853)。

# 実装タスクの完了定義

コード変更を伴うタスクでは、PR の作成までがタスクである。commit や push で
手を止めて報告に切り替えるのは未完了。

- commit → push → PR 作成を、途中で確認を挟まず一続きで実行する。
  「PR を作成しますか?」と聞かない。push を省略して報告で終えない。PR 作成を
  選択肢から落とさない。
- PR 本文は pr-description スキルの 5 節スケルトンに従う。`gh` の投稿は、本文を
  Write でファイルにしてから `-R OWNER/REPO` と `--body-file <絶対パス>` で渡す
  (bleep が正準形以外を deny する)。
- 例外は 2 つだけ: (1) ユーザーが「commit まで」「PR 不要」等と明示した場合、
  (2) リポジトリが PR フローを持たない場合。迷ったら PR を作る側に倒す。
- 調査のみ・ファイル変更なしのセッションはこの節の対象外。
- PR 本文に未チェックの task list(`- [ ]`)を残さない。チェックボックスは
  実施済みの列挙にだけ使い、全て埋まった状態で出す。
- 人の確認(実機・GUI・資格情報・判断)が要る残作業はマージの条件にせず、
  後続 Issue として払い出す。`## 要確認` にはその Issue へのポインタ
  (`- #N — <一言>`)だけを書き、手順・完了条件は Issue 側に書く。マージ
  可否は CI とレビューで決める — 人待ちの PR は base が進むほど rebase
  負債になり、確認者の予定が PR の寿命を決めてしまう。

# 承認済み計画から規則を差し替えたら、適用するゲートの前に申告する

承認済みの計画に書いた規則・判定条件・手順を実装段で差し替えたら、
それを適用するゲート(セッション内の承認・外部システムへの書き込み)の
**前に**差し替えを申告する。申告には、計画に書いた文・実際の規則・差し替えの
理由を含める。作業後の報告で初めて書くのは不可。判断の基準は「本人が承認した
文と違うか」で、影響の大小で変えない(#666)。

# 決定成果物は執行点と同じ PR に出す

ADR・設計文書・skill のような決定成果物を追加するときは、その決定を執行する
実体(コード・hook・CI・宣言的設定)を同じ PR に含める。実装を後続 Issue に
分離して決定成果物だけを先に出さない。

- ADR には `## 執行点` を置き、その決定を執行する実ファイルのパスを列挙する。
  箇条書きは **1 行 1 パス**(カンマ・読点で複数並べない)。
  未来の Issue 番号は書けない — 執行点は今ある実体に限る。
- 部分実装は可。執行点が 1 つでもあればよく、残余の後続 Issue 化は自由。
- 実在するが変更していない既存ファイルの併記だけでは足りない。列挙した
  執行点のうち少なくとも 1 つは、この PR で実際に新規追加または変更されて
  いること — 「既存の何かが執行する」という主張は、それを検証する変更を
  伴わなければ自己申告と区別できない。
- ADR の番号は PR 番号に合わせる規約を持つリポジトリ(`scripts/adr-number-check`
  がある)では、起草時の番号を全桁 0 の仮値にし、PR を作った後に
  `scripts/adr-number-check --fix <PR番号>` で改番する。最大番号 + 1 や、Issue・
  PR の最大番号からの推測で番号を書かない — 欠番があり、確定値ではない
  (2026-10-04 に 255 と推測して外れた)。
- 起草中の ADR を、コード・コメント・文書から参照するときは、題名でなく、
  `--fix` が書き換える仮番号の形式で書く(形式は `docs/agents/adr-numbering.md`)。
  題名での参照は改番で直らず、番号のない参照が残る(2026-10-20 に実際に
  起きた)。
- 第三者製 skill の「最大番号を探して +1」という指示(domain-modeling の
  ADR-FORMAT.md)より、この規約が優先する。
- 裁定を要する変更(上位文書の改訂を含む)は、案を出した人(Responsible)が
  PR まで作り、議論の場を PR の一点に集約する。依頼用の Issue を別に立てて
  承認待ちを挟む、といった中間ステップを作らない(#710)。
- 責任分担(RACI)を示すときは、決定の Accountable を本人 1 人に集約する。
  他の関係者は Consulted(意見を聞く)兼 Informed(結果を知らせる)とし、
  承認を他者に委ねる形にしない(#709)。

# トピックブランチを最新化するときは merge ではなく rebase を使う

トピックブランチ(自分が今作業中のブランチに限らず、他セッション・他人が
作成したブランチを含む)を最新の main/base コミットへ追従させる必要が
あるときは、`git merge origin/main` ではなく `git rebase origin/main` を
使い、push は `git push --force-with-lease --force-if-includes` で行う。
これは原理原則であり、コンフリクトが複数コミットに跨りそう・force-push
自体を避けたい等の理由で merge を選びたくなる場面でも優先する。

- merge は余計な merge commit を残す。squash-merge 運用のリポジトリでは
  ブランチ内部のコミット履歴は最終的に潰れるため、履歴をきれいに保つ
  merge のメリットが無い。
- `--force-with-lease` は「自分が最後に見た状態からリモートが動いて
  いないこと」を、`--force-if-includes` は「自分の rebase がリモートの
  最新到達点を祖先として含んでいること」を検証してから push するため、
  素の `--force` より安全 — 他人の未取得の作業を上書きする事故を防げる。
- セッション内の PR チェーンそのものの rebase 運用(積み直し等)は
  stacked-pr スキルに従う。この節は「他ブランチを最新化する」という
  より一般的な場面を対象にする。

# 本物の checkout は変更せず、作業単位は worktree で切る

どのリポジトリでも、本物の checkout(main worktree。`git rev-parse` の
`--git-dir` と `--git-common-dir` が一致するもの)には変更を入れず、
作業単位ごとに worktree を切って、その中で作業する。自リポジトリとよその
リポジトリを区別しない。作業の途中で別のリポジトリへ移るときも、セッション
を本物の checkout で始めてしまったときも同じ。

- 理由: 独立した作業単位を切るとき、herdr は親 checkout の HEAD を土台に
  使う。親 checkout が main でクリーンであることを保証できる場が、この
  前提を支える。本物の checkout で編集や `git switch -c` をすると、その
  保証が失われる。
- worktree は `herdr worktree create --cwd <repo> --branch <name>` で作り、
  以降は worktree の絶対パス、または `git -C <worktree>` で操作する。
- 読み取り(Read/Grep/Glob、`git log` `git status` など)、`git fetch`、
  `git pull --ff-only` は本物の checkout に対してやってよい。
- 本物の checkout を直接変更したいときは、本人が `!` 付きのコマンドで
  操作する。エージェントが自分で抜ける手段は設けない。

形式検査は `main-checkout-guard`(PreToolUse の deny + Stop の事後検出)が
担う。gate に当たる前に自発的に worktree を切ること — gate は漏れを拾う
ためのもので、一次的な手段ではない。設計は
`docs/agents/main-checkout-guard.md`。

# GitHub に投稿するテキストには生成元を明示する

GitHub に書く外向きのテキストには、経路を問わず末尾に次の形式で
1 行を置く。

```
🤖 Generated with [<自分自身のエージェント名>](<自分自身の URL>)
```

自分自身のエージェント名と URL は、その場で動作しているツールが何かに
従う(例: Claude Code なら `Claude Code` / `https://claude.com/claude-code`)。
他のエージェント名を騙って表示しない。

対象は PR / Issue の本文(`create` / `edit`)、Issue / PR のコメント、
`gh pr review` のレビュー本体。`gh` でも `gh api` でも MCP tool 経由でも同じ。
コメントに mention が付くかどうかで判断を変えない — mention が無くても
watcher / assignee には通知が飛ぶ。

- 本文が自分(AI エージェント)の生成でないとき(ユーザーが書いた文章を
  そのまま代理投稿する等)は `No-Attribution: <理由>` を本文に書いて
  明示的に抜ける。理由は必須。読者にとっても「これは AI が書いたのでは
  ない」という正しい情報になる。
- 別の目的を持つフッター(出自を grep で絞るためのタグ等)が自分自身への
  リンクを含む形で生成元も表示できるときは、それ 1 行で足り、上記フッターを
  重ねて付ける必要はない。
- コード行に対するインラインレビューコメントは対象外(1〜2 行が典型で、
  フッターが本文より長くなる)。

# 技術・仕組みの選択は表現不可能性 → 還元性 → 先進性の順で決める

新しいツール・ライブラリ・機構を選ぶとき、既存のものを置き換えるとき、
または新しい仕組み(hook・skill・設定ファイル等)を追加するかどうか
迷うとき — 妥当な代替が複数ありうる場面全般 — は、次の 3 軸をこの
優先順位で評価する。上位の軸が同点でないときは、下位の軸をどれだけ
強く満たしても上位の軸の判定を覆さない。

**評価の前に、入力から歴史的経緯と作業量を除く(ADR-751)。** 判定質問は
「コード 0 行の白紙から選ぶとしたら、3 軸で何を採るか」だけ。今使って
いるもの(現職)も、白紙の上では候補の 1 つにすぎない。書き直し・波及する
編集・レビュー量・テストの移し替えといった**作業量は 0 とみなし**、
「すでにこうなっている」という歴史的経緯は理由にしない。LLM が考えずに
特定の言語(Python 等)へ倒れる癖も、同じ白紙の評価で潰す: 新しい道具・
単位の実装言語を選ぶときは対抗馬を立てて比べる。

- 数えるのは、**戻せないもの**だけ: 失うと戻せないデータ、自分では管理
  できない外部の利用者との契約、人手でしかできない作業。書くときは
  `戻せない: データ|外部契約|人手 — <内容>` の閉じた形に限る。
- 白紙で比べて完全に同点なら現職を維持する。理由は「乗り換えても
  どの軸も良くならない」ことだけで、変更を提案する側がどれかの軸の
  改善を示す。
- 裁定と実行は分ける。裁定はコストを見ずに下し、「意図は決まっていて
  未着手」として Issue に残す。いつ移行するかは自由で、既存の選択を
  自分から棚卸しする義務は課さない(ADR-0035 D5)。「コストが高いから
  移行しない」という裁定は残せない。
- この擬制は**何を採るかの裁定**にだけ使う。いつ問うか・どう手順を組むか
  といった手順の設計では、作業量の現実を数えてよい(下の Q1 の前倒しは
  その例)。

1. **表現不可能性。** 不正な状態を検出でなく表現不可能にする方を採る
   (宣言 > 手続き、単一正本 > 複写+同期、閉語彙 > 自由記述+事後 lint、
   型・コンパイル時 > 実行時検査、pin 固定 > 浮動、upstream 正本 > fork)。
2. **還元性。** その仕組みが、より安い手段では担えない仕事をしている
   ときだけ残す。死んだ機構・重複した機構は消す(消す作業量は数えない)。
3. **先進性。** 1・2 が無差別なときの同順位破りとしてのみ使う。新しさ
   自体を理由に 1 を弱める選択はしない。採用したら追従した理由を
   pin 地点(バージョン制約のコメント等)に残す — 「なんとなく新しい
   方がよさそうだった」は理由にならない。

候補を 1 つしか調べていないと、この 3 軸は候補集合そのものの誠実さを
保証しない。本命が先に決まっている選択は「憧れ駆動」と明示し、同じ
評価軸で本気の対抗馬を立てる(追認調査にしない)。感触で外した候補は
「感触で外した」と正直に書き、分析の結論であるかのように偽装しない。

候補(ライブラリ・ツールなどの依存)を選択肢に載せる前に、候補ごとに一次
ソースを読む。README の保守表示(unmaintained・archived・deprecated など)、
最終コミットの日付、使う API が要件を満たすか、の 3 つである。読んでいない
ものは、選択肢に「未確認」と書き、読んだかのように並べない。保守状況は採否を
決める物差しではなく、本人が選ぶときの入力である。

文書を読むだけでは分からない採否の事実(対象の地域・条件で API が応答するか、
ビルドが通るか)は、承認の前に手元で 1 回実測する。実測できないときは「未実測」と
書き、キーの発行や契約のような人手・戻せない作業より前に、実測を置く。

書式・自己検査の具体手順はツールごとの運用規約(Claude Code なら
technology-selection スキル)に従う。

# 道具を新設する前に既存手段を問い、決定論化は段階で昇格させる

「同じことをフルスクラッチで作らず既存の枯れた技術で実現できないか」
(以下 Q1)と「非決定論的な処理(典型的には LLM による処理)を決定論的な
処理に置き換えられないか」(以下 Q2)は、気付いたとき・思い出したときに
提起するのでは間に合わない。これらは撤収コストの向きが逆(ADR-543
「既存手段の前倒し接地と、決定論への昇格導線」参照)なので、扱い方も
非対称にする。

- **Q1 は前倒し型。** 自前実装は小さく始まって育つほど撤収コストが
  上がるため、新しい道具・単位を作る**着手の瞬間**に必ず問う。「既存の
  ツール・ライブラリ・スクリプトで足りないか」を検討し、`既存手段:` の
  3 値(`採用|拡張|自前`)のいずれかで答える。`自前` を選ぶときは、
  何を検討してなぜ却下したか(または何を探して見つからなかったか)を
  書く。「簡単だから自前で書く」は理由にならない。
- **Q2 は昇格型。** 散文(skill の手順書、LLM に判断させる処理)は
  そのまま仕様書として残るため昇格コストが小さく、探索期には LLM・
  散文による処理を許容してよい。安定の兆候(同じ規範違反が繰り返し
  起きる、同じ手順が何度も逐語で実行される)が出たときに、決定論的な
  スクリプト・gate へ昇格させることを検討する。昇格しても散文は消さず、
  「意図」と「スクリプトが失敗したときのフォールバック手順」として
  残す。
- 段階(散文 / スクリプト化 / gate 化)は宣言させず、実体(スクリプトや
  hook 登録が実在するか)から判断する。宣言欄は実体とズレる二重管理に
  なるため作らない。

運用(確認・報告・追跡の手順)を設計するときは、人が書き足し続ける記録
(タグ・台帳の行・追跡用 Issue)を既定にしない。まず既存の記録(merge 履歴・
Issue・PR)から導出できないかを問い、導出できるなら記録を増やさない。人の
維持作業が要る案を出すときは、その作業が忘れられたときの壊れ方を併記する
(#738)。

共有層(この文書)に新しい規範を足す前に、その規範が当てはまらないリポジトリ
(個人でメンテしている dotfiles、会議体を持たないリポジトリ等)を 1 つ挙げて
確かめる。当てはまらないものがあるなら、共有層には置かず、該当するリポジトリ
側の任意の宣言にする。グリルの途中で合意した配置でも、計画の最終段階で
再確認する(#739)。

書式・自己検査の具体手順はツールごとの運用規約(Claude Code なら
precedent-grounding / technology-selection スキルの `既存手段:` 行)に
従う。

# 外部発信は既定で下書き止まりにする

Slack への返信・GitHub 以外への Issue/PR コメント相当の外部発信を伴う
タスクでは、実際の送信は行わず常に下書き(Slack のドラフト・下書き系
ツール等、相当する下書き手段)に留める。外部発信は取り消しづらく、内容の
最終確認は人間が行うべきである(#463。別プロジェクトでの作業中に受けた
フィードバックを一般化した)。

- 対象は Slack への送信・返信・予約投稿など、取り消しづらい外部宛の発信
  全般。下書き系ツールが接続先に存在しない場合は、送信せず本文をチャット
  に出力し、ユーザー自身が貼り付けて送信できるようにする。
- **GitHub は対象外。** Issue/PR コメント・`gh pr create` 等は、この
  AGENTS.md「実装タスクの完了定義」が確認を挟まず実行することを既に
  要求しており、一律下書き止まりにすると矛盾する。GitHub 側の
  「取り消しづらさ」はレビュープロセス(merge/close されるまで訂正可能)
  に委ねる。ただし**通知は取り消せない**ので、この根拠が当てはまらない:
  Issue・PR の本文とコメントに、ユーザーの依頼なしで `@<login>` や `cc` 行を
  書かない。reviewer の指定も依頼なしには行わない。assignee は、リポジトリの
  規約が要求するときにユーザー本人だけを指定する(他人はユーザーに確認)。
  関係者を示す必要があるときは、名前を出さない記述(「受信側の担当」)かリンク
  で足す(#670)。
- **本人の記録システムへの書き込みは対象外。** 勤怠・工数・本人の
  カレンダーのように本人だけが見る記録は、下書きで止めずに書き込みまで
  行う(#656)。境界は「他人に通知が飛ぶか」で引く:
  - 申請・承認依頼・提出のように、他人へ通知が飛ぶ**最後の確定操作**
    だけを本人に残す。それより前の入力は全部済ませ、確定すれば終わる
    状態にして渡す。
  - 本人以外を招待する予定など、書き込みが他人に通知を飛ばすものは
    外部発信として扱う(下書き止まり)。
- **予約・申込みフォームの送信は、条件を満たせば代行する(#840)。**
  本人から「行けるところまで進めてほしい」と明示された種類の作業では、
  フォームの入力から送信までを本人に任せない。上の「最後の確定操作だけを本人に
  残す」は、次の 3 つを送信前に画面で読んで確かめられる予約・申込みには適用しない:
  - 送信が取り消せる(承認制、または期限までキャンセルできる)。
  - 支払いがその場で発生しない。
  - 入力に使うのが、本人のアカウントに保存済みの値か、既に持っている値である。

  次の場合は止まって本人に渡す: パスワード・認証コードの入力、その場で支払いが
  発生する操作、取り消せない契約、手元に無い個人情報の入力。送信したら、受付メール
  などを読み戻して、予約番号と日時を報告する(下の「読み戻して確かめた状態だけを
  報告する」)。
- Claude Code では、Slack MCP tool の送信系(`send_message` /
  `reply` / `schedule_message` / `post_message`)を PreToolUse hook が
  deny し、draft 系ツールへ誘導することで決定論的に担保する
  (`crates/external-send-guard`、`docs/agents/external-send-guard.md`)。
  この機械強制はツールごとの運用規約側の責務であり、本節はその方針を
  宣言するだけに留める。

# 外部システムへの書き込みは、読み戻して確かめた状態だけを報告する

勤怠・カレンダー・チケット・クラウド設定など外部システムへ書き込んだ
ときは、ツールの戻り値(成功応答)を事実として扱わず、対象システムの
状態を読み戻して確かめた結果だけを報告する(#652。成功応答のまま
「申請済み」と報告し、実際には一部が拒否されていた事故から一般化した)。

- 件数・状態は、読み戻した結果から数える。書き込みの際に手元で数えた
  件数を流用しない。
- 報告には、読み戻しに使った手段(コマンド・画面・API)を添える。
- 読み戻せないとき(読み取り手段が無い・権限が無い)は、その項目を
  「未確認」と書く。確認したかのような書き方をしない。

この規律には形式検査を置かない。チャットへの報告は機械検査できず、
書き込みの経路も MCP・Bash・ブラウザに散らばっていて、どの呼び出しが
書き込みかを名前から推測するしかないため。ADR-543 の昇格型に従い、
同じ事故が再発したら Stop hook 等での検査への昇格を検討する。

# 人に依頼する手順は、場所を問わず「フル」で書く

人間にしかできない作業(ブラウザ操作・資格情報の発行・実機での確認等)を
依頼する手順は、チャットで提示するときも、Issue・PR 本文・docs に書く
ときも、要約形(「project を作成して machine account を発行」のような粒度)
にしない。次の 5 要素を必ず含める。

- 遷移経路: どの画面から、どのメニュー・リンクをたどるか(URL があれば URL)
- 正確な名称: 画面名・項目名・ボタン名を、画面に出る表記のまま書く
- 入力値: 入れる値と、触らずに既定値のままにする項目。「何でもいい」
  「適宜」と書かない — 値を決められない項目は、導出規則(例:
  `docs/personal-cloud-projects.md`)を引いて具体値を出す
- 完了確認: 何が画面やコマンド出力に出れば完了か
- 根拠: 画面名・項目名の出典(公式ドキュメントの URL と取得日、または
  既存の runbook・Issue 番号)

確かめられていない画面名・項目名は推測で書かず「未確認」と書く。値そのもの
が機密で書けない場合は、値を取得するコマンド(生値を端末に残さない形)を
書く。同じ指摘を繰り返し受けた規律(#612)なので、チャット出力は機械検査
できない分、この節を常時読み込まれる正本に置く。

人手の作業が残ったら、手順を一覧にして渡して終えない。既定で**同期的に**
付き合う: 1 回に 1 手順だけを示し(何を・なぜ・どう確かめるか)、本人の
実行結果(`!` 付きコマンドの出力や画面で見えたもの)を読んで判定してから
次の手順へ進む。本人が「あとでやる」と言った場合に限り、Issue に払い出す
(上の「人の確認は後続 Issue へ」は、この同期的な付き合いを本人が断った
場合の経路である。#664)。

人の確認が要る成果物のうち、本人の記述を確かめるもの(経歴・プロフィールの文、
下書きの文面など)は、ファイルのパスを渡して開かせず、チャットに 1 件ずつ出して
聞く。本人の答えは、公開された技術資料や組織論の文献などの一次情報で裏取りして
から次の問いへ進み、裏取りで見つけた本人の記述のずれは、答えを確認するときに伝える。
件数が多く、全体を見渡して 1 件ずつ裁定する形を本人が指示している成果物(メール返信の
下書きは、`inbox-adjudication` のとおり HTML ページにまとめる)は、この限りでない。

計画に `gh repo` 系の操作(unarchive・rename・edit・delete)を含めるときは、対象が
private リポジトリなら、その段を最初から「人の端末で `!` 付きに実行する手順」として
人手の作業の節に書く。PreToolUse の検査(bleep の `repo-ref`)が、コマンド文字列に
含まれる非公開の名前で deny することがあり、その一致はエージェントからは確かめられ
ない。実行段で初めて止まって同期の往復を増やさないよう、実行前に止まることを前提に、
結果の読み戻し(`gh repo view`)までを 1 コマンドに束ねて渡す(#812)。
