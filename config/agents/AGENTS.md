# 調査・先行例確認の方針

## 検証可能な仮定を放置しない

計画・回答・設計判断が「検証可能な不確実性」を含むとき — つまり
Slack・Google Drive(コネクタが接続されている場合)、GitHub(gh CLI)、
公式ドキュメント・upstream ソース・学術文献のいずれかに答えが実在し
そうなとき — 参照するかどうかをその場で明示的に判断すること。参照
しない場合は理由を一言書く。「聞かれなかったので見なかった」を失敗
とみなす。

## 発明する前に先行例を確認する

新しいパターン・仕組み・非自明な設計をゼロから提案する前に、「これは
確立されたやり方が存在する問題か?」を自問し、存在しうるなら調べる。
優先順位:

1. 一次情報源: 公式ドキュメント・upstream のソース/spec・学術文献
   (論文・既存研究)— アルゴリズム・手法など研究的性質を持つ問題では
   文献が本命
2. 組織内の先行実装・過去議論(GitHub org、Slack、Drive)
3. 二次情報(ブログ等)は 1–2 の裏取りがある場合のみ

非自明な設計判断を書くときは、判断を確認して回るのではなく成果物に
残す: 判断ごとに 1 行(採った判断 / 出典と取得日 / 先行例との差分、
または先行例が無ければその旨と探した範囲)で書く。書式・自己検査の
具体手順はツールごとの運用規約(Claude Code なら precedent-grounding
スキル)に従う。

## 調べ方の規律

- 調査は可能なら委譲可能な手段(サブエージェント・並列タスク等)に
  任せ、本線を止めない
- 検索クエリ自体が文脈を外部に送ることを意識し、trivial な作業では発火させない
- 取ってきた情報の要点だけを本線に還流し、コンテキストを汚さない
- 一次情報を引いたら、成果物に URL と取得日を残す。URL 単独では不十分
  — 著者・タイトル・(判明する範囲で)公開日も併記する

## セッション内の PR は単一チェーンに積む(ADR-0027)

同一セッション・同一 worktree で複数の PR を作るときは、依存の有無を
予測せず常に作成順の単一チェーン(stacked PR、base を直前の段のブランチに
する)に積む。機能的な依存関係とコード競合ベースの依存関係は別物で、
後者は実際に PR を作るまで予測できない — 判定に依存予測を使うと、その
予測がセッション内で系統的に外れ、base 宣言と実体(物理的な直列ブランチ)
が不整合になる(汚染 diff・orphan PR)。

- 分割案(何段に分け、各段が何を含むか)を計画段階で先に提示する。
  承認後は全段の PR 作成まで止まらない。
- 同じ行を 2 段以上が書き換える切り方はしない(追記なら可)。
- 各段はそれ単体でマージしても壊れないこと。
- 離脱(このチェーンに積まない独立 PR にする)は、本文に閉じたタグ
  `Independent-PR: <理由>` を書いたときだけ成立する。依存の有無を先読み
  して自発的にチェーンから外れない。
- 計画・作業中に見つかった依頼スコープ外の項目も、今のセッションで
  手を付けるなら既定でチェーンの一段として受ける。詳細は stacked-pr
  スキルに従う。
- 手順・rebase 運用・Issue リンクの書き分けは stacked-pr スキルに従う。

## 複数項目の依頼は要求インベントリで受ける

sub-issue を持つ Issue、または箇条書きで複数項目を含む依頼を計画に起こす
ときは、依頼文と参照 Issue の子項目を逐語で 1 項目ずつ、ID を付けて列挙
してから設計に入る。すべての項目に処分(実装する段、または
`Blocked-Upstream:` / `Obsolete:` / `User-Excluded:` のような閉じたタグ)
を書く。規模・工数・セッション長・コンテキスト残量は棄却理由にならない。
依頼が参照する Issue のうち実装対象でないものは `Reference-Only: #N —
<理由>` で明示的に外す。

作業中・計画中に見つかった隣接する負債は、まず現在の変更との依存関係
(stacked-pr スキルの判定条件)で振り分ける。依存があれば stacked PR の
一段として受ける選択肢を出す。依存がなければ従来どおり別経路(wrap-up
inbox 等)へ流す。レビュー負荷が事実上ゼロの微小修正(数行の typo・
dead link 修正等)に限り、断りを入れた上で同一 PR に同梱してよい。

書式・具体的な自己検査手順はツールごとの運用規約(Claude Code なら
scope-inventory スキル)に従う。

# 実装タスクの完了定義

コード変更を伴うタスクでは、PR の作成までがタスクである。commit や push で
手を止めて報告に切り替えるのは未完了。

- commit → push → PR 作成を、途中で確認を挟まず一続きで実行する。
  「PR を作成しますか?」と聞かない。push を省略して報告で終えない。PR 作成を
  選択肢から落とさない。
- PR 本文は pr-description スキルの 5 節スケルトンに従う。
- 例外は 2 つだけ: (1) ユーザーが「commit まで」「PR 不要」等と明示した場合、
  (2) リポジトリが PR フローを持たない場合。迷ったら PR を作る側に倒す。
- 調査のみ・ファイル変更なしのセッションはこの節の対象外。

# 決定成果物は執行点と同じ PR に出す

ADR・設計文書・skill のような決定成果物を追加するときは、その決定を執行する
実体(コード・hook・CI・宣言的設定)を同じ PR に含める。実装を後続 Issue に
分離して決定成果物だけを先に出さない。

- ADR には `## 執行点` を置き、その決定を執行する実ファイルのパスを列挙する。
  未来の Issue 番号は書けない — 執行点は今ある実体に限る。
- 部分実装は可。執行点が 1 つでもあればよく、残余の後続 Issue 化は自由。
- 実在するが変更していない既存ファイルの併記だけでは足りない。列挙した
  執行点のうち少なくとも 1 つは、この PR で実際に新規追加または変更されて
  いること — 「既存の何かが執行する」という主張は、それを検証する変更を
  伴わなければ自己申告と区別できない。

# トピックブランチを最新化するときは merge ではなく rebase を使う

トピックブランチ(自分が今作業中のブランチに限らず、他セッション・他人が
作成したブランチを含む)を最新の main/base コミットへ追従させる必要が
あるときは、`git merge origin/main` ではなく `git rebase origin/main` を
使い、push は `git push --force-with-lease --force-if-includes` で行う。
これは原理原則であり、コンフリクトが複数コミットに跨りそう・force-push
自体を避けたい等の理由で merge を選びたくなる場面でも優先する。

- merge は余計な merge commit を残す。squash-merge 運用のリポジトリでは
  ブランチ内部のコミット履歴は最終的に潰れるため、履歴をきれいに保つ
  merge のメリットが無い。
- `--force-with-lease` は「自分が最後に見た状態からリモートが動いて
  いないこと」を、`--force-if-includes` は「自分の rebase がリモートの
  最新到達点を祖先として含んでいること」を検証してから push するため、
  素の `--force` より安全 — 他人の未取得の作業を上書きする事故を防げる。
- セッション内の PR チェーンそのものの rebase 運用(積み直し等)は
  stacked-pr スキルに従う。この節は「他ブランチを最新化する」という
  より一般的な場面を対象にする。

# GitHub に投稿するテキストには生成元を明示する

GitHub に書く外向きのテキストには、経路を問わず末尾に次の形式で
1 行を置く。

```
🤖 Generated with [<自分自身のエージェント名>](<自分自身の URL>)
```

自分自身のエージェント名と URL は、その場で動作しているツールが何かに
従う(例: Claude Code なら `Claude Code` / `https://claude.com/claude-code`)。
他のエージェント名を騙って表示しない。

対象は PR / Issue の本文(`create` / `edit`)、Issue / PR のコメント、
`gh pr review` のレビュー本体。`gh` でも `gh api` でも MCP tool 経由でも同じ。
コメントに mention が付くかどうかで判断を変えない — mention が無くても
watcher / assignee には通知が飛ぶ。

- 本文が自分(AI エージェント)の生成でないとき(ユーザーが書いた文章を
  そのまま代理投稿する等)は `No-Attribution: <理由>` を本文に書いて
  明示的に抜ける。理由は必須。読者にとっても「これは AI が書いたのでは
  ない」という正しい情報になる。
- 別の目的を持つフッター(出自を grep で絞るためのタグ等)が自分自身への
  リンクを含む形で生成元も表示できるときは、それ 1 行で足り、上記フッターを
  重ねて付ける必要はない。
- コード行に対するインラインレビューコメントは対象外(1〜2 行が典型で、
  フッターが本文より長くなる)。

# 技術・仕組みの選択は表現不可能性 → 還元性 → 先進性の順で決める

新しいツール・ライブラリ・機構を選ぶとき、既存のものを置き換えるとき、
または新しい仕組み(hook・skill・設定ファイル等)を追加するかどうか
迷うとき — 妥当な代替が複数ありうる場面全般 — は、次の 3 軸をこの
優先順位で評価する。上位の軸が同点でないときは、下位の軸をどれだけ
強く満たしても上位の軸の判定を覆さない。

1. **表現不可能性。** 不正な状態を検出でなく表現不可能にする方を採る
   (宣言 > 手続き、単一正本 > 複写+同期、閉語彙 > 自由記述+事後 lint、
   型・コンパイル時 > 実行時検査、pin 固定 > 浮動、upstream 正本 > fork)。
2. **還元性。** その仕組みが、より安い手段では担えない仕事をしている
   ときだけ残す。死んだ機構・重複した機構は、あとで消すコストより今
   消すコストの方が小さい。
3. **先進性。** 1・2 が無差別なときの同順位破りとしてのみ使う。新しさ
   自体を理由に 1 を弱める選択はしない。採用したら追従した理由を
   pin 地点(バージョン制約のコメント等)に残す — 「なんとなく新しい
   方がよさそうだった」は理由にならない。

候補を 1 つしか調べていないと、この 3 軸は候補集合そのものの誠実さを
保証しない。本命が先に決まっている選択は「憧れ駆動」と明示し、同じ
評価軸で本気の対抗馬を立てる(追認調査にしない)。感触で外した候補は
「感触で外した」と正直に書き、分析の結論であるかのように偽装しない。

書式・自己検査の具体手順はツールごとの運用規約(Claude Code なら
selection-grounding スキル)に従う。
