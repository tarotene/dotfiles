# ブラウザ操作

ログイン引き継ぎ後に限らず、フォーム保存・アクセス障害・代行送信を扱うときに必ず読む。

## フォームへ入力して保存するとき

画面に複数のフォームがあると、保存ボタンを取り違える。画面全体からテキスト(「保存」)で
ボタンを探して押すと、別のフォームのボタンを押すことがある。取り違えは再読み込みで
初めて気づき、保存すると一定期間変更できない欄では、取り消せない。

- 保存ボタンは、入力した欄と同じフォームの中から押す。欄の祖先のフォームにスコープした
  ロケータ(`form` を `has` で絞ってから、その中のボタンを取る)を使い、`evaluate` で
  画面全体のテキスト一致を探して押さない。Playwright は、複数に一致するロケータを
  厳密モードで拒否する(<https://playwright.dev/docs/locators#strictness> 、取得 2026-10-11)。
  `.first()` や `.nth()` で一致を 1 つに絞って回避しない。
- 押す前に、そのボタンが属するフォームの見出しを読み、入力した欄と一致することを確かめる。
- 確認ダイアログが出たら、文面(特に「変更できない期間」)を読んでから確定する。
- 保存のたびに、ページを再読み込みして値を読み戻す。

## 外部サービスが 403 を返したとき

403 を受けたら、ログイン状態やフォームを疑う前に、同じ操作を繰り返さずに次の 2 つを
確かめる。

- 作業中のリポジトリの記録(台帳・runbook・サービスごとの注記)に、そのサービスの
  既知の制約(例: 「この端末の VPN 経由では入れない」)が書かれていないか。サービスを
  初めて開く前に、読んでおく。
- 端末が VPN の出口ノード経由になっていないか。Tailscale なら `tailscale status` で、
  出口ノードを使っているかを読む。サービスが出口ノードの送信元を弾くことがある。
  出口ノードの切り替えは本人の端末設定なので、エージェントは触らず、本人に外してもらう
  (または別の経路で開いてもらう)。外す前後で 1 回ずつ開く A/B で、原因を断定する。

同じ 403 を何度も試さない。1 回目で、この 2 つのどちらに当たるかを絞る。

## 代行送信の前に本人の確認を取る

メールや DM(LinkedIn のメッセージなど)を本人の代わりに送るときは、送信ボタンを押す前に、
本人の確認を挟む。入力欄の内容を機械的に読み戻して一致を確かめるだけでは足りない。改行の
有無のような見た目の誤りは、読み戻しの一致では見えず、送信すると外に出てしまう(#1261)。

### 検査との関係

Gmail の送信ツールは、外部宛の送信を `external-send-guard`
(`docs/agents/external-send-guard.md`)が本人の許可の確認(ask)に回す(#1317。`reply` で `to` を
指定しないときは今も deny で、下書きへ誘導する)。ブラウザ経由の送信
(LinkedIn など)はその検査の外にある。確認の手順の対象には、どちらも含める。散文で始め、
同じ誤りが再発したら、送信ボタンの操作の前に確認の記録を要求する検査へ昇格させる
(ADR-543 の昇格型)。

### 確認の手順

1. **本人に見せるものを 4 つ揃える。**
   - 送信直前の画面のスクリーンショット(入力欄に文面が入り、送信ボタンを押す直前の状態)。
   - 改行を含む全文。改行は、見たままの形で書く。1 行に潰して書かない。
   - 宛先。メールは To と Cc。DM は相手の表示名と、開いているスレッドの URL。
   - 相手の依頼と処分の表(`reply-coverage check` の報告。依頼の引用、答える・断る・保留・先に答え済み・取り下げ済みの別)。
     本人が、答え漏れがないかを画面で確かめる。`check` に合格した本文のまま送る(確認のあとに直したら、`check` からやり直す)。
     ブラウザの入力(`browser_type`)は、どの hook も見ないので、この表と本人の確認が、機械の検査の代わりになる(検出のみ)。
   **`show-image <スクリーンショットの絶対パス>`(単体で呼ぶ)が終了コード 0 で終わるときは、ページも HTTP サーバも立てない。**
   スクリーンショットは手元の別ウィンドウに出し、宛先・改行つきの全文・依頼と処分の表は、手順 3 の質問の本文に書く
   (共有 AGENTS.md「本人にその場で見せる図・画像は…」、`docs/agents/show-image.md`)。終了コード 3(画面がないセッション、ブラウザがないホスト)のときは、次の手順 2 のページへフォールバックする。
2. **確認用の 1 枚のページにまとめ、HTTP サーバで配って、URL を見せる。** ファイルのパスを渡して
   開かせない。ページには、宛先、改行つきの全文、スクリーンショット、依頼と処分の表を載せる。
   - スクリーンショットの保存先は、プロジェクト名を含まない場所にする(`~/.cache/playwright-mcp/`
     の下など)。保存先のパスに非公開のプロジェクト名が入っていると、検査(`bleep`)が拒否する。
   - 配るのは、確認用の 1 ディレクトリだけにする(ホームやリポジトリを配らない)。サンドボックスの外で、
     `python3 -m http.server <ポート> --bind 127.0.0.1 --directory <確認用ディレクトリ>` を背景で実行する。
     サンドボックスの中で立てたサーバは、別のコマンドからも本人のブラウザからも届かない(コマンドごとに
     ネットワークが分かれる。2026-10-30 に実測。立てたあとは `curl` で 200 を確かめる)。
   - `127.0.0.1` に束縛するので、本人の端末が別の機体なら届かない。そのときは本人に、どう見せるかを聞く。
   - 確認が済んだら、サーバを止め、確認用ディレクトリを消す(文面と画面が残らないようにする)。
3. **質問の本文に URL を書き、「これで良いですか？」と聞く。** `AskUserQuestion` の直前の地の文は
   表示されないことがあるので、URL と宛先は `question` の本文に書く(共有 AGENTS.md「方針レベルの
   問いは…」)。OK と答えるまで送らない。答えがない、直すと言われたときも送らない。直したら、
   手順 1 からやり直す。
4. **送ったあとは、送信済みの画面を読み戻して報告する。** 本文と改行は、読み戻した結果から書く
   (共有 AGENTS.md「外部システムへの書き込みは、読み戻して確かめた状態だけを報告する」)。

### LinkedIn のメッセージ欄の改行

貼り付けや一括の入力は、メッセージ欄の内部状態に取り込まれず、キーボード入力した分だけが送られる。
そこで、文面を段落ごとに打ち、段落の間に `Shift+Enter` を押す。段落として改行が入る
(2026-10-30 の実測: 入力欄を読み戻すと、行ごとに別の段落になっていた。10 段落。送信は押さず、
送信済みのメッセージが増えていないことも確かめた)。

`Shift+Enter` が使えず 1 段落にせざるを得ないときは、黙って 1 段落にしない。送る前の確認で、
1 段落になることを本人に見せる。

段落の間に空行を入れたいとき、`Shift+Enter` を 2 回続けても空行にならない(2026-11-08 の実測: 次の段落の
先頭に `&nbsp;` が付き、末尾に空の段落が 3 つできた)。空白を 1 文字打ってから `Shift+Enter` を押す。
欄の中身を全部消すときは `Ctrl+A` のあとに `Delete` を押す。入力中にページを移動すると、
`beforeunload` の警告が出て、打った文面が消える。移動の前に、送るか消すかを決める。

送信ボタンを押す前に、入力欄の段落の数を、下書きの段落の数と突き合わせる(`browser_evaluate` で入力欄の `innerText` を読み、
改行の数を数える)。スクリーンショットの目視だけでは、改行が 0 の 1 塊を見落とす(2026-11-15、送った返信 8 通が、画面上は
改行 0 の 1 塊だった。確認した 1 通は 671 字で、同じ会話の 10-31 の返信は区切りがあった。見落としか入力の脱落かは未確認)。
突き合わせの補助で、本人の確認の代わりにはならない。

### LinkedIn の入力と送信の癖(2026-11-16〜18 の実測)

- **複数のスレッドへ返すときは、別タブに入れてから、送信前の確認を 1 回にまとめる。** 1 スレッドずつ確認すると往復が増える。
- **送信後は、再読み込みして、スレッドの末尾の送信済みを読み戻す**(上の手順 4)。
- **`fill` で本文を入れても、送信ボタンが無効のままのことがある。** キー入力や `input` イベントの合成でも有効にならない。
  `browser_evaluate` で入力欄に focus して、`document.execCommand('insertText', …)` と `document.execCommand('insertLineBreak')` で
  打つと有効になる。エラーは出ず、ボタンの `disabled` を見るまで分からない。送信ボタンを押す前に、`disabled` でないことを確かめる。
  この入力を宛先の URL と文面だけを渡す 1 本の道具にするかは、今回は見送った(新しい道具なので、既存手段との対比が先)。

### 返信を下書きする前に、会話の全文を保存する(#1577)

返信の下書きは、会話の始めからの、相手の未決の依頼すべて(日程の候補・質問・書類)への応答として書く。最後の
メッセージだけを読むと、最初のメッセージの依頼を見落とす(2026-11-15、紹介会社の最初のメッセージにあった電話の日程候補に
触れず、質問にだけ答えた)。

1. 会話を開く(切り替えたあとは、下の節のとおり、切り替わったことを確かめてから)。会話が長ければ、先頭まで
   スクロールして読み込ませる。先頭のメッセージが画面に出ていることを、スナップショットで確かめる。
2. `browser_snapshot` の `filename` に、**絶対パス**(`~/.cache/playwright-mcp/` の下など。プロジェクト名を含まない場所)を
   渡す。ツール自身がファイルに書くので、エージェントが読み取った内容を書き写さない(書き写しの脱落が、今回の失敗を
   再生産する)。
3. `reply-coverage import --id <媒体>:<会話の印> --file <そのファイル>` で取り込む(機体ローカルに、権限 0700 / 0600 で保存する。
   有効期限 60 日)。会話の印は、会話を指す短い名前(URL の会話の部分など)にする。
4. 下書きの最終稿に対して、`reply-coverage check --thread <媒体>:<会話の印> --draft <ファイル> --me "<本人の発言の見分け方>"`
   を実行する。整形していない snapshot では、本人の発言を、画面の名前で見分ける。
5. 保存した全文は取り込んだ時刻から 24 時間までが有効である。それより古いと相手の新しい返信を見落としやすくなるため、取り直す。
6. **Gmail の通知メール(LinkedIn・LAPRAS・Findy などのメッセージの通知)から返すときは、Gmail のスレッドだけで組まない。**
   通知は、同じ件名でも別のスレッドに分かれ、本人が相手の媒体(LinkedIn など)で送った文は Gmail に残らない。ブラウザでその会話を
   開いて、手順 1〜4 で取り込み、その会話に `check` をかける(2026-11-19、新しい通知の Gmail のスレッドだけを読んで返信の下書きを
   作り、`check` も通った。実際には同じ会話の 11-17 に、本人が面談を見送り、相手が承知して「条件に合う求人が見つかり次第」と
   約束していた)。Gmail の下書きの作成口は、通知メールの会話で、24 時間以内のブラウザの取り込みがないと、拒否する
   (`docs/agents/reply-coverage.md`。どの会話に当たるかは結びつけないので、取り違えは塞がない)。チャットで返信案を本人に見せる前は、
   `reply-coverage ready --thread <媒体:id>` で、会話の読み込みを確かめる(機械で止める口はなく、手順書だけが担う)。

保存先は機体ローカルであり、vault や Git には含めない。取り込んだ全文はチャット、Issue、PR、文書に転記しない。

### LinkedIn のメッセージ一覧の切り替え

スレッドを切り替えたあとは、本文を読む前に、切り替わったことを確かめる(スレッドの URL か、画面の
相手の名前が、開こうとしたスレッドと一致すること)。`browser_evaluate` で一覧の項目に `click()` を
呼ぶと、画面が元のスレッドのまま変わらず、名前の違う 7 件で同じ本文が返ったことがある(2026-10-28)。
名前が違うのに本文が同じなときは、その結果を採らず、切り替えを確かめながら 1 件ずつ読み直す。

### LinkedIn の送信直後の「連絡先情報を共有しますか？」

メッセージの送信に際して、「連絡先情報を共有しますか？」という確認が出ることがある。メールアドレスと電話番号を先方に渡す
確認で、同意すると本人の個人情報が渡る。**同意しない。** 実測した挙動が 2 つある:

- 2026-10-30: 送信の直後に出た(メッセージは送信済み)。閉じるだけで足りた。
- 2026-11-16〜18: 送信ボタンを押すと出て、**この確認に答えないと送信されなかった**。「いいえ、共有しません」を押すと送信された。

出た時点で、スレッドの末尾に自分のメッセージがあるかを画面で読み、送信済みかどうかで挙動を見分ける。送信済みなら、閉じるだけにする。送信されていなければ、上の「いいえ」側のボタンを押す。これは本人の裁定である(2026-11-20)。連絡先を渡す判断が必要なときは、押さずに本人に確認する。画面の文言と、押したあとに連絡先が渡らないことは、上の実測の記録によるもので、画面では未再確認である。推測で書き換えず、次に出たときに文言を読んで、この節を直す。出たことは本人に報告する。送る前の確認の説明にも、送信に際して連絡先の共有を求められる可能性があること、こちらでは同意しないことを含める。

日程の候補を出すメッセージでは、仮押さえを先に作る(`slot-availability` の「候補を相手に出すときの順序」)。
確認のページに仮押さえの一覧を載せる。

### 送信済みの誤りは編集で直せる

LinkedIn には、送信後のメッセージの編集がある。書式の誤り(改行が入らなかった、など)は、これで直せる。
ただし、送信済みを直すのも外への操作なので、直す前に上の確認の手順(スクリーンショット、全文、宛先)を
経る。

## 設定画面の項目の読み取り・貼り付け・読み戻し

サービスの設定画面の 1 項目(設定文など)を、読み取り・貼り付け・読み戻しする作業は、毎回その場でスクリプトを書かずに
`browser-settings`(`docs/agents/browser-settings.md`)で行う。専用プロファイルの Chrome を起動のたびに起動して接続し、
普段のブラウザには触れない。`paste` は入力欄に入れて読み戻すだけで、**保存の確定は人が行う**。サービスごとの画面の探索
(選択子)は `config/browser-settings/services.toml` のデータで、画面を実際に読んで確かめてから追加する。
