外部窓口への電話のように、時間帯制約(相手の営業時間・受付時間)を伴い、かつ
Claude 自身が実行できない作業をユーザーに引き継ぐとき、トークスクリプトを
文書に書いて渡すだけでは「ユーザーが忘れずに実行できる」保証にならない。
ユーザーは他の作業に気を取られており、営業時間内に自発的に思い出す確率は
低い。

## 一般の人手タスクも対象にする

電話・窓口だけでなく、handoff で払い出す人手タスクと daily-desk で見つけた未予定の人手タスクにも使う。

## いつ発動するか

- 電話・来店・窓口対応など、Claude が代行できない作業をユーザーに依頼する場面
- その作業の実行可能時間帯が外部要因(相手の営業時間・定休日)で制限されている場面

会話内でトークスクリプトや確認事項を用意して終わりにせず、下記の手順まで
セットで行う。

## 何をするか

1. 対象の営業時間帯・定休日を洗い出す。
2. ユーザーの予定表を参照し、営業時間帯とユーザーの空き時間が重なる枠を探す。
   確定済みの予定(本番・出張・研修等、busy 相当のもの)と衝突しない枠を選ぶ。
   「予定が入っていないように見えるが実際には難しい時間帯」(移動中・休養日
   など)を機械的な空き判定だけで拾わない。
3. 見つけた枠にリマインダー予定を作成する(書き込み先は手順 4)。件名には対応が
   必要であることを一目でわかるマーカーを付け、説明欄には電話番号・確認事項の
   要点をその場で読めるように書く(別ファイルへの参照だけで済ませない)。
4. 確定した予定は、予定データ(私的な person-state リポジトリ側)へ書く PR を出す。
   CI がそれを一方向に、専用の射影カレンダー(自動生成)へ反映する。利用者の
   主カレンダーは本人の手入力の受付箱なので、確定した予定を直書きしない
   (例外は仮押さえの `[hold] ` だけ)。書き込み先が分からないときは、どのカレンダー
   に書き込んでよいかをユーザーに確認してから作成する(個人の主カレンダーに
   無断で書き込まない)。
5. その作業に前提条件(例: 別タスクの結果待ち)がある場合は、予定の説明欄に
   明記し、ユーザーが実行タイミングを自分で判断できるようにする。

## 外部サービスへの書き込みはサニタイズ対象

カレンダー・メール等の外部サービスに送る文章(件名・説明欄を含む)は、
`agent-tooling-authoring` §3.2「外部サービスへ送る文」に従ってサニタイズする。
禁止項目の一覧はそちらが正本で、ここには再掲しない。

## 事例

個人プロジェクトの実務整理タスクで、外部窓口への確認電話をユーザーに依頼する
際、相手の営業時間とユーザーの既存予定(公演・遠征等)を突き合わせて空き枠を
選び、カレンダーに登録した。最初はプロジェクト名や Issue 番号を含めた説明文を
書いたところ、外部カレンダーサービスへの private リポジトリ参照としてガードに
検知され、書き直しが必要になった。カレンダー・メール等、リポジトリの外に出る
文章にはリポジトリ内のドキュメントとは別のサニタイズ基準がかかることを示す
実例。

ユーザーに引き継ぐ手順(電話の段取り・来店前の準備・申込画面での操作等)
は、要約形にせず、共有 `AGENTS.md`「人に依頼する手順は、場所を問わず
『フル』で書く」の 5 要素(遷移経路・正確な名称・入力値・完了確認・根拠)
で書く。

## 軽い人手タスクと待ちの連鎖

電話・窓口対応など営業時間の制約があるものは、Issue を起票するだけで
終わらせず この手順に従い、カレンダーへの
反映まで行う。

**軽い人手タスク(`handoff:light`)は、時間帯制約の有無によらず**、起票した日のうちに予定へ入れる。
**待ち(`blocked_by`)があっても、前段が片付くのを待たない**(ADR-1000)。待ちでつながる連鎖は、最後の段の
日時を先に決め、前の段をそこから逆算して、同じセッションでまとめて予定に入れる。Issue を払い出した
(起票した)セッションが、そのまま予定化まで進める。issue-index が SessionStart で「軽い人手タスク」として
(待ちのあるものは「(待ち N 件)」付きで)出すので、見えて予定が無いものも、そのセッションで同じ手順を行う。
朝の机(`daily-desk`)の人手タスクの段でも、同じ手順を使う。

1. `slot-availability` で、最も早く空く枠を探す(外部の営業時間・受付規則が
   あれば先に当てる)。
2. 外部の承認や予約が要る枠(1 枠を申請して承認を待つもの)は、予定データ
   (私的な person-state リポジトリ側)に承認待ち(`tentative`)として持つ。
   複数の候補日程を出して相手の裁定を待つ候補一覧型の仮押さえだけ、主カレンダーに
   `[hold] ` で直書きする(`slot-availability` スキルの仮押さえと同じ扱い。旧印の
   `【調整中】` は読み取り専用の別名として読まれる)。予約の確定後、
   予定データへ取り込む PR を出して仮予定を消す。取り込む予定には、
   その Issue への参照(`issue`。複数の Issue が 1 枠を共有するなら `issues`)を書く。日付は Issue に
   書かず、予定データだけが持つ(公開リポジトリの Issue に予定を載せない)。
3. 外部へ送る文面は下書き止まりにし、予約の申請などの確定操作は本人と
   同期的に 1 手順ずつ進める。
4. その日のうちに枠が取れない理由があれば、Issue にコメントで残す。


一般の予定は上記「何をするか」の手順 4(予定データへ PR → 射影カレンダー)の規則を使い、主カレンダーに直書きしてよいのは、候補一覧型の仮押さえの `[hold] ` だけとする。
