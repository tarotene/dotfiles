Tracking Issue のような複数項目を含む依頼を丸ごと Plan Mode に投げると、
作業スコープの増大を気にして依頼された範囲を黙って縮小した計画を返すことが
多い。この失敗は「スコープ外」節を書く体裁を取るので、レビューでも気づかれ
にくい。要求インベントリは、落とした項目を機械的に見つけられる形で残すための
手順である。

## 1. インベントリの作り方

計画冒頭に `## 要求インベントリ` を置き、次の順で埋める。

1. 依頼文そのものから、逐語で要求項目を抜き出す。言い換えない。
2. 依頼が参照する Issue について、子 Issue の有無を確認する:
   ```bash
   gh api repos/OWNER/REPO/issues/N/sub_issues --jq 'length'
   gh api repos/OWNER/REPO/issues/N/sub_issues --jq '.[] | "#\(.number) \(.title)"'
   ```
   GraphQL の `subIssues` 照会は使わない: 会社・非公開リポジトリ宛てだと
   bleep の repo-ref denylist が拒否する(#717)。REST の `sub_issues` は
   通り、件数は GraphQL の `totalCount` と一致する。`plan-scope-gate` 自身
   が内部で行う GraphQL 照会は Rust バイナリが直接 `gh` を呼ぶので
   PreToolUse の対象外で、この食い違いは起きない。
   件数が 0 のときだけ、本文の**未チェック** task-list
   (`- [ ]` で始まる行)を子とみなす。チェック済み項目は既に決着済みなので
   拾わない。
3. 各項目に `R1`, `R2`, ... の ID を振る。

## 1a. 計画の事実を取る前に、base を最新にする(#935)

plan mode で長いグリルをすると、計画が依拠する事実(ファイルの path、規約文書、削除済みの仕組み)を、
グリルの冒頭に読んだ古い作業ツリーから取ったまま進みやすい。その間に base の `origin/<default>` が進むと、
`ExitPlanMode` の「参照ファイルが変更された」hook(`plan-fresh-gate`)が出口で初めて検出し、計画が差し戻される
(実例: グリルの途中で `origin/main` が 16 コミット進み、計画が依拠していた検査ツールと宣言ファイルの削除と
文書の改名が、出口で見つかった)。hook は設計どおりに働いている。足りないのは出口より前の検出で、次がその手順である。

- グリルの開始時と、計画ファイルを書く直前に、`git fetch origin` して、作業ツリーの HEAD と `origin/<default>` の差を確かめる
  (`git rev-list --count HEAD..origin/<default>`。`git symbolic-ref --short refs/remotes/origin/HEAD` は `origin/<default>` を返す)。
- 差があるときは、計画が依拠するファイルの内容と有無を、作業ツリーでなく `git show origin/<default>:<path>` で取る。
  差のあるファイルは `git diff HEAD origin/<default> -- <path>` で読む。

## 2. 処分の書き方

各 `Rn` には、次のいずれか 1 つを書く。

- **実装する段**: `R3: 段1で実装` のように、どの段が担うかを書く。
- **閉じたタグでの棄却**(この 3 つ以外は使わない):
  - `Blocked-Upstream: <理由>` — 外部(upstream の未修正・未 GA の機能・
    他者のマージ待ち)にブロックされていて、今書いても実装できない。
  - `Obsolete: <理由>` — 要求そのものが既に無効。別の変更で解消済み、
    または前提が消滅している。
  - `User-Excluded: <理由>` — ユーザーが依頼文で明示的に除外した。

**規模・工数・セッション長・コンテキスト残量は棄却理由にならない。** これらを
理由にした棄却は誤用であり、書いてはいけない。「複雑になりそうだから」
「トークンを消費するから」も同じく誤用。

**処分は、項目と同じ行に書く。** 1 行 1 項目で、逐語の項目と処分を `—` でつなぐ。要求の列挙
(R1〜Rn)と処分を別の箇条書きに分けると、`plan-scope-gate` は「処分が未記載」「複数回処分されて
います」と判定する。項目を折り返して処分が次の行になる書き方も、処分が項目と同じ行に無いと
読まれて未記載になる(#876)。gate が出力する雛形と同じ形は次のとおり(山括弧の中身だけを事実に
置き換える):

```markdown
## 要求インベントリ

- R1: <依頼文からの逐語の要求項目> — 段1で実装
- R2: <逐語項目> — Blocked-Upstream: <upstream 未修正など、外部にブロックされている理由>
- R3: <逐語項目> — Obsolete: <既に別の変更で解消済みである理由>
- R4: <逐語項目> — User-Excluded: <ユーザーが依頼文で明示的に除外した文言>
- R5: #137 <子タイトル逐語> — 段2で実装
```

## 3. 参照 Issue と実装対象の書き分け

依頼文に出てくる `#N` は、実装依頼と参考参照(「#10 の設計を参考に」)の
両方があり得て、機械的には区別できない。参照しただけの Issue は次の 1 行で
明示的に外す:

```
Reference-Only: #10 — 設計パターンの参考として引用しただけで実装対象ではない
```

この宣言がない参照 Issue は「実装対象」として扱われ、その子 Issue 全件が
`Rn` として要求インベントリに載っていることを要求される。**`Reference-Only:`
を実装対象の Issue に対して使うのは、棄却タグの誤用と同じ扱いになる**——
規模を理由に実装対象を参照扱いへ格下げしているだけだから。

## 4. 依頼に含まれない隣接事項との違い

要求インベントリが縛るのは「依頼に含まれていたのに落とした項目」だけである。
依頼に含まれない隣接事項を「今回のスコープ外」と宣言するのは、この repo の
既存の作法であり(`docs/agents/worktree-base-sync.md` 等)、要求インベントリ
とは無関係に従来どおり書いてよい。作業中に見つかった隣接する負債は、
今のセッションで手を付けるかどうかで振り分ける(`stacked-pr` スキル §1、
ADR-0027)。今のセッションでやるなら stacked PR の一段として提案する
(依存の有無は問わない — セッション内の複数 PR は常に作成順の単一
チェーンに積む)。やらないなら棄却タグではなく wrap-up inbox に流す。

## 5. 段割りの規律

分割の粒度(何を 1 段にまとめるか)は `stacked-pr` スキル §2 の目安
(旧判定条件、ADR-0027 により「積むか否か」の判定からは降格した)に従う。
段の数を先に決めてそれに合わせて項目を配分するのではない — 分割そのもの
を既定にすると、本来 1 段で片付く仕事まで分割コストを背負う。分割しても
項目は 1 つも
落とさない。どの段にも入らない項目を残さない。

## 6. 要求同士が両立しないとき

ある `Rn` を実装すると別の `Rm` の前提が壊れるなど、要求同士が技術的に
両立しないと判明したときは、棄却タグで片方を落とさない。`AskUserQuestion`
でその場でユーザーに裁定を求める。棄却タグは「実装しない理由が確立している
項目」のためのものであり、「判断が必要な項目」を隠す手段ではない。

## 7. 提出前の自己検査

プランファイルを書き終えたら、ExitPlanMode の前に必ず:

```bash
~/.claude/hooks/plan-scope-gate --check-plan <プランファイル>
```

`OK:` が出るまで修正してから抜ける(節内整合性=経路Bだけの検査。参照
Issue の子項目カバレッジ=経路Aは gate 本体が ExitPlanMode 時に行う)。
gate の deny を書式検査代わりに使わない(deny 1 往復ごとに並列の Copilot
レビューも巻き添えで走る)。
