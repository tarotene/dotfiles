---
name: inbox-adjudication
description: 溜まったメールの受信箱をまとめて処理する手順。未読を全件読み、Gmail で返せるスレッドは返信形式の Gmail の下書きまで作り、Gmail の外の媒体の下書きと判断の表は HTML ページにまとめて本人が 1 件ずつ裁定し、未裁定の項目を状態機械で追い、予定や台帳に反映し、フィルタにできる差出人は標準ルールとして積む判断知識。メールを処理して・メールが溜まっている・受信箱を片付けて・未読を整理・返信が必要なものを洗い出して・フィルタに突っ込んで・inbox triage・process my inbox・draft replies for my unread mail、といった依頼で使う。既読化や削除を先にやる作業ではない。
---

メールの処理を頼まれたとき、既読化やアーカイブから始めると、返信すべき相手と
期限のあるものが埋もれたまま「処理した」ことになる。既定の順序は、読む →
返信と判断を裁定に出す → 予定と記録に反映する → フィルタにする → 最後に
受信箱を整える、である。送信・削除・退会・迷惑メール報告は本人の操作で、
この手順では行わない。

## 原則

- **完成と呼ぶ条件**: 返信が要るスレッドの全件に、下書きか「返信しない」の理由が付き、
  期限のあるものが予定か記録に載り、実行後の未読数を読み戻して報告するまで完成と呼ばない。
- **未読だけを見ない。** 人からの連絡は、既読になっていたり別のタブにあったりする。
  媒体や相手の種類(求人、予約、請求など)で、直近の期間を既読も含めて検索する。
- **台帳でなくスレッドを読む。** 宛先や相手の人数、送信済みの有無は、台帳や過去の
  メモの記述でなく、スレッド全体(自分の送信、相手の返信、取消)で確かめる。
- **確かめていないことは「未確認」と書く。** 本文が HTML のみで読めない、公開ページが
  途中までしか読めない、といったときは推測で埋めない。

## 手順

0. **処理の前に、未了の項目と記録済みのスレッドを引く。** 未裁定項目の状態機械は `docs/agents/mail-lifecycle.md`。
   1. `worklog mail sweep` を実行する。7 日動きが無い未了に `remind`、`remind` の後さらに 7 日(または期限超過)の
      未了に `stale` が書かれる。書かれた行を本人に見せる(`stale` で閉じた項目は、閉じたと 1 回知らせる)。
   2. `worklog mail check` を実行する。「終端の行が消えた」「解析できない行」が出たら、先に本人に見せる
      (復元は `worklog mail restore <鍵>`、捨てるのは `forget <鍵>`)。
   3. `worklog mail open` で未了の一覧を引く。裁定ページの db に本人の裁定が入っていれば読み(手順 3)、
      `decide`・`pass` を書く。
   4. `worklog list --kind mail --since <日付>`(検索範囲の最初の日)を実行し、鍵 `<媒体>:<スレッド>/<受信>` を控える。
      同じ鍵は、読み直しても項目が増えない(同じ出来事は記録済みになる)ので、読み直さず飛ばしてよい。
   `worklog` が使えない機体(vault を宣言していない)では、この段と手順 8 を省き、省いたと報告に 1 行書く。
1. **集める。** 受信箱の未読を、次ページが無くなるまで全件取得する(件数の見積もりは目安で、
   ページごとに数が合わない)。件名と送信元だけで判断できないものは、スレッドを開く。
   本文が空に近いときは、HTML を含む形式で取り直す。
   **既定の検索範囲は、直近 21 日、既読を含む、受信箱の外とフィルタ済みのラベルを含む。**
   未読の受信箱だけを取得して進めない。人からの個別メールが、既読にされたり、
   フィルタで受信箱の外へ移されたりして未読のまま埋もれていることがある。自動通知の
   大量の差出人は、数えるときに除く。
2. **区分する。** 各スレッドを次のどれか 1 つにする。
   - 返信が要る(人から、または相手が返事を待っている)
   - 判断だけが要る(更新するか、申し込むか、移行するか)
   - 予定か記録に反映する(確定した日程、期限、審査結果)
   - 片付いている(自分が返信済み、相手が了承済み)
   - 標準ルールにする(定常的な通知や販促)
   区分する前に、同じ問いへの既存の裁定を、記録(台帳、決定記録、Issue)から探す。
   見つかれば、それを前提にして下書きと推奨を作る。
   **Gmail の外で返信する経路(LinkedIn、LAPRAS、Findy、転職サービスのメッセージなど)から
   届いた連絡は、返信済みかを Gmail から読めない。** 返信は各サービスの画面で送るので、
   Gmail に送信済みのメールが残らない。「返信が要る」と断定せず「返信済みか未確認」と
   する。本人に聞く前に、ブラウザ(Playwright)で各サービスのスレッドを開き、最後の
   メッセージが先方か本人かを画面で読む(未ログインなら `browser-login-handoff` で
   ログインだけを頼む)。読めなかったとき(ログイン壁、ボット検知)に限り、試した経路を
   添えて本人に聞く。裁定の記録(断る、受ける)は決定の記録で、送信の記録ではない。
   Gmail に送信済みが残る相手(メールで返す相手)は、スレッドで確かめる。
3. **記録を先に書き、下書きを作り、判断の表をページにまとめる。** 項目ごとに、この順で行う。
   1. **記録を先に書く。** 返信の下書きを作るものは `worklog add mail "draft: <要旨> [<鍵>]"`、判断を本人に出すものは
      `ask: …`(`due:YYYY-MM-DD` が分かれば付ける)。同じスレッドに未了があれば、`worklog` が先に古い方を
      `move` で移す。記録にあって下書きが無ければ、次の机で作り直す(下書きが先で記録が無いと、取りこぼしを検出できない)。
   2. **Gmail で返せるスレッドは、元のメッセージへの返信形式(`replyToMessageId`)の Gmail の下書きを作る。**
      日次モードと同じ手順で、一括モードでも HTML のページに止めない。送信は本人が Gmail で押す。最初の使用では、
      下書きが元のスレッドに付いたことを Gmail の画面で確かめ、確かめられなければ「未確認」と書く。
      **宛先は、作った直後に `get_draft` で読み戻し、元のメッセージの送信元(`Reply-To` があればそれ)と
      一字一句同じであることを確かめる。** `to` を手で打たない。綴りの違う宛先の下書きを本人が送ると、
      配信エラーで返信が相手に届かない(2026-10-29、宛先のアドレスが 1 文字違う下書きが送られ、拒否された)。
      一致を読み戻していなければ、報告に「宛先は未確認」と書く。
   3. **HTML のページは、Gmail の外の媒体(求人サービスのメッセージなど)の下書きと判断の表の分だけ。**
      項目ごとに、来た内容、根拠(スレッドの日付と要旨)、既存の裁定、推奨、下書き本文(Gmail の外の分)、
      コピー用ボタンを付ける。下書きは本人がページ上で直せるようにする。送信はページから行わず、本人が元の画面に貼る。
      断りの下書きは、理由を短くし、相手の会社や他社の事情を書かない。
   4. **判断の表のページは、固定の 1 枚(毎回同じ URL を再公開する)にし、本人の裁定を db に保存させる。**
      ブラウザの localStorage にだけ保存すると、裁定が記録に戻らない。実装時は `artifact-capabilities` を読んでから
      書く。保存するのは鍵と裁定の語だけ(要旨や本文は入れない)。コレクション `verdicts`、文書の id は鍵の
      `:` と `/` を `.` に換えたもの、項目は `{key, verdict: decide|pass|later, at}`。`decide`=対応する、
      `pass`=見送る、`later`=あとで。ページには予備として「回答をまとめる」(チャットに貼る文)も残す。
      次のセッションは db を `ArtifactData` で読み、`decide` と `pass` を `worklog add mail` で書く(`later` は書かない。
      時計は動き続け、7 日で `remind` が出る)。終端や `decided` の項目は `worklog` が止めるので二重にならない。
4. **確定したことを正本に反映する。**
   - 予約や面談の確定は、通知の順序でなくカレンダーを正本にして日程を決める。
     取消と再予約が前後して届くことがある。
   - カレンダーに落ちた予定は、記録の正本(データファイル)に採用し、カレンダーに重複して残さない。
   - 期限は、期限の予定として載せる。
   - 相手に取消の通知が飛ぶ操作(予定の削除など)は、本人に決めてもらう。
5. **フィルタにする。** 未読の差出人を集計し、区分ごとの標準ルールを積む。
   フィルタにできる差出人は、返信の裁定と並べて積み、後回しにしない。分類の体系で
   表せない差出人は、フィルタ定義を持つリポジトリの Issue にする。
   **候補の一覧を挙げる前に、既存のフィルタ定義を最後まで読む。** 対象の差出人ごとに、
   既存の規則を検索する。検索語は、差出人のアドレスだけでなく、ドメインとラベル名も使う。
   既存の規則があれば、候補から外して「規則あり」と書く(計画の表と実装がずれて、承認された
   計画の一部を実装で外すことになる)。
   - 人からの連絡、返信が要るもの、判断が要るもの: 受信箱に残す。
   - 取引・予約・請求・ログインの通知: 既読にして保管する。請求書は保持を長くする。
   - 読み物: 週次のまとめで読む層にする。
   - 一過性の販促: ゴミ箱に送る層にする。
   - 同じ差出人から性質の違う通知が来るときは、件名で分ける。ただし件名の文言に頼る規則は
     取りこぼしやすいので、体系へのフィードバックとして記録する。
   - 同じ差出人が、一括連絡(本人は Bcc)と個別の返信(本人は To)の両方を送ることがある。
     差出人だけの規則は個別の返信を digest に振って埋もれさせるので、宛先で分ける
     (個別の返信は受信箱に残し、一括連絡は読み物の層にする)。
   - フィルタは新着にしか効かない。既存の未読に効かせる手順を、規則の追加と一緒に伝える。
   - 反映(apply)は本人が行う。全体を置き換える仕組みなので、追加だけを自動にする場合も、削除を含む変更は人が見る。
6. **受信箱を整える(最後)。** 既読化に使う手段の権限は、計画を承認に出す前(手順 3 の前)に
   確かめておく。道具の一覧に変更系(ラベルや既読の付け外し)があることは、権限の確認に
   ならない(一覧にあっても `Insufficient scope` で拒否される)。確かめるのは、本人が承認した
   1 件だけの試行である。権限が無いとき(例: `Insufficient scope`、必要な権限は
   `gmail.modify`)は、計画の段を最初から「本人が Gmail の画面で行う」か「本人が許可した別の
   手段」に書く。別の手段には、宣言したフィルタの適用のほか、手元の Gmail 用ツールが持つ
   `gmail.modify` のトークンがある。そのツールに「検索で指した未読を既読にする」手段が無い
   ときは、足す(空の検索を拒否し、件数に上限を置き、ドライランで全件を見せ、戻せるログを残す)。
   発行の目的が違う認証情報を、本人の許可なく流用しない。
   規則の反映と既存分への適用が済んだ後に残った未読のうち、
   処分が済んだものだけを既読化する。実行前に件名と送信元の一覧を見せて承認を得て、
   実行後に未読数を読み直して報告する。ゴミ箱、迷惑メール、退会、返信、転送はしない。
7. **報告する。** 下書きの件数と置き場所、反映したもの、本人の操作が残るもの、未確認を、
   短い表にして伝える。
8. **記録する。** 開く出来事(`ask`・`draft`)は手順 3 で先に書いた。報告のあと、残りの出来事を作業ログへ
   1 行ずつ書く(`worklog` の `mail` kind、ADR-1256 と `docs/adr/1259-mail-lifecycle.md`)。

   ```text
   worklog add mail "<出来事>: <要旨> [<媒体>:<スレッド>/<受信> [due:YYYY-MM-DD]]"
   ```

   - 出来事は `read|ask|draft|decide|apply|pass|move`(`remind`・`stale` は `worklog mail sweep` だけが書く)。
     本人が対応すると決めた = `decide`、断る・見送ると決めた = `pass`、正本(予定、フィルタ規則など)へ反映した、
     または送った = `apply`、別の追跡先(Issue、カレンダーの【期限】の予定)へ移した = `move`(`to:<owner/repo#N | cal:YYYY-MM-DD>` が要る)。
     期限のある作業を「やる」と決めたら、期限の予定か Issue に移して `move` にするのが既定。
   - 媒体は `gmail|linkedin|lapras`。鍵の `<スレッド>/<受信>` は、Gmail ならスレッドとメッセージの id
     (`[A-Za-z0-9_=-]+`)、メッセージごとの id が取れない媒体は会話の id と、画面に出る受信日時を分まで
     (`YYYYMMDDTHHMM`)。
   - **Gmail の送信済みスレッドの照合。** `draft` の項目は、Gmail に送信済みのメッセージが付いたら `apply`、
     下書きが消えて未送信なら本人に聞く(書き直すか、`pass` か)。
   - **片付いているスレッドと自動通知は、1 件ずつ書かない。** 集計の 1 行にまとめる:
     `read: <範囲>の約N件を読んだ(自動通知を除く処分M件) [none]`。
   - **書くのは結論だけ。** 要旨は 120 文字まで。相手は組織・サービスの名前か種類で書き、人名、アドレス、
     URL、件名、本文の抜粋は書かない(`@` と `http` を含む要旨はコードが拒否する)。メールの中身は Gmail に残る。
   - 同じ受信は同じ鍵なので、読み直しても二重にならない。今の状態から許されない出来事は、`worklog` が書かずに止める。

## 日次モード(朝の机から呼ばれるとき)

`daily-desk` の机のメールの段から呼ばれたときは、上の手順を次のとおり絞る。依頼文で
「溜まったメールを処理して」と頼まれた一括の処理は、これまでどおり上の手順で行う。

- **検索範囲。** 前回の机の日付から今日まで(最低 2 日)。初回は既定の 21 日。既読と、受信箱の外の
  ラベルを含める点は同じ。
- **カテゴリで絞らない。** 検索に `-category:updates` などを足さない。求人サービスのメッセージ
  (LinkedIn の InMail など)や、人からの連絡の一部は、`updates` のカテゴリに入る。件数が多い自動通知
  (カードの利用通知など)は、送信元ごとに数えて除く。カテゴリの除外で除かない。
- **下書き(手順 3)。** 一括モードと同じ。Gmail で返せるスレッドは、記録(`draft`)を先に書いてから、
  元のメールへの返信形式(`replyToMessageId`)の Gmail の下書きを作る。HTML のページは、Gmail の外の媒体
  (求人サービスのメッセージなど)の分だけ作り、コピー用のボタンを付ける。判断の表が無い日は、裁定ページも作らない。
- **やらないこと。** 差出人の集計とフィルタの追加(手順 5)、既読化(手順 6)は行わない。フィルタの
  見直しは、フィルタ定義を持つリポジトリの週次の見直しが担う。気づいた差出人は、報告に 1 行書くだけにする。
- **Gmail の外の画面を読むとき(手順 2)にログインの壁に当たったら、ExitPlanMode の前に、その場で
  `browser-login-handoff` でログインだけを頼む。** ブラウザでスレッドを開いて読むのは読み取り専用で、
  Plan モードの中でも行える。「ログインは承認後に本人へ頼む」と計画に書いて ExitPlanMode に出すと、
  「Plan モード中にログインを待ってほしい」と差し戻される(`cases.md`)。待ちたくないときは、読めなかった
  項目を「返信済みか未確認」と書いて計画に載せるのではなく、本人に先に頼む。
- **反映(手順 4)と報告(手順 7)** は同じ。報告には、下書きの件数、Gmail の外で返す件数、未確認を書く。
- **記録する(手順 0・8)。** 机の最初に `worklog mail sweep`・`check`・`open` を実行し、`remind` と `stale` を
  本人に見せる(手順 0)。報告のあと、処分を付けたスレッドごとに
  `worklog add mail "<出来事>: <要旨> [<媒体>:<スレッド>/<受信> [due:YYYY-MM-DD]]"` を 1 行ずつ実行する。
  片付いているスレッドと自動通知は 1 件ずつ書かず、`read: <範囲>の約N件を読んだ(自動通知を除く処分M件) [none]` の
  1 行にする。記録は結論と鍵だけで、メールの中身や相手の名前は書かない。

## メール以外の多数項目の裁定にも、手順 3 のページの型を使う

件数が多い(目安 10 件超)、または項目ごとに理由・例外を書き足したくなる裁定は、メールでなくても、
最初から手順 3 のページ(件ごとの選択と自由メモ、確定ボタン、裁定は db に保存)で出す。例は、会議の
分類、Issue の棚卸し、候補の採否。チャットの質問に番号つきの一覧を載せて「OK / 直す」を聞くと、本人が
項目ごとに書き足したいときに往復が増える(#1255)。チャットの質問は、1 つの推奨案への OK / NG を
聞く場合に限る(共有 AGENTS.md「方針レベルの問いは、聞く前に既存の裁定を探す」)。

## 代行送信の前に、本人の確認を取る

本人が、メールや DM(LinkedIn のメッセージなど)の代行送信を明示して頼んだときだけ、この段に入る。
既定は、下書きで止めて送信を本人に任せること(手順 3)。代行で送るときは、送信ボタンを押す前に、
次の 3 つを本人に見せて「これで良いですか？」と聞き、OK と答えるまで送らない(#1261)。

- 送信直前の画面のスクリーンショット
- 改行を含む全文
- 宛先(メールは To と Cc)

スクリーンショットは、ファイルのパスを渡さず、宛先・全文・スクリーンショットをまとめた 1 枚のページを
HTTP サーバで配り、URL を質問の本文に書いて見せる。サーバの立て方、LinkedIn のメッセージ欄の改行
(段落ごとに打ち、間に `Shift+Enter`)、送信済みの編集、`external-send-guard` との関係は
`reference/browser-operations.md`「代行送信の前に本人の確認を取る」を必ず全文読む。Gmail の送信ツールは
`external-send-guard` が外部宛の送信を止めるので、メールの代行送信はブラウザ(Gmail の画面)経由になる。
ブラウザ経由の送信はその検査の外にあるので、メールも DM も、この確認の対象に含める。

## 他の skill との境界

- 候補日程の当たり判定は slot-availability、会場探しは venue-search、
  演奏本番の付随作業は music-performance-planning に任せる。
- 朝のセッションで、メールを含む作業を順に片付ける入口は `daily-desk`。この手順はそのメールの段を担う。
- 事例は `cases.md` に追記する。

フォーム保存・アクセス障害・代行送信を扱うときは `reference/browser-operations.md` を必ず全文読む。ログイン引き継ぎは `browser-login-handoff` に従う。
