# inbox-adjudication の事例

抽象化した実話。固有名詞は書かない(agent-tooling-authoring のサニタイズ規則)。

## 既読化中心の計画は却下された

溜まったメールの処理を頼まれ、既読化とアーカイブを中心にした計画を出したところ、
「もう少し丁寧に」と却下された。本人が求めたのは、返信が要るものを片っ端から下書きにして
裁定すること、フィルタにできるものは積極的に標準ルールへ積むことだった。
→ 既定の順序を、既読化を最後に置く形にした。

## 通知の順序は状態を表さない

予約ページで確定した合わせの通知が 4 件届き、4 枠が確定したと読んだ。直後に、相手が 1 枠を
取り消して別の枠を予約していたことが、別の通知で分かった。通知の並びでは現在の状態が決まらず、
カレンダーを読んで初めて確定した。
→ 日程は通知でなくカレンダーを正本にする。

## 必要数より多く確定していた

予約ページの説明は 3 回分だったが、カレンダーには 4 枠が確定していた。1 枠は本人の個人的な事情で、
避けたい日だった。外した予定は相手に通知が飛ぶため、削除せずに本人へ判断を渡した。
→ 外部へ通知が飛ぶ操作は、自分で実行しない。

## 全ジョブが数秒で落ちた

2 つのリポジトリの全チェックが 2〜3 秒で落ちた。ステップが 1 つも実行されておらず、注釈に
「支払いの失敗または利用上限」と出ていた。変更内容は無関係だった。課金を直したあと、
失敗した run を再実行したが、必須チェックの 1 つを再実行し忘れ、マージが止まったままだった。
→ 再実行は失敗した run をすべて対象にし、必須チェックが通ったことを読み戻す。

## 課金のあとに、実際のテスト失敗が見つかった

別の PR は、課金とは関係なく、実際に実行されて落ちていた。既定の設定を変えた変更に、テストが
追従しておらず、テストが本物の設定ファイルを読んでいたのが原因だった。
→ テストは、本物の設定でなく、条件を固定した写しを使う。

## 自動更新ボットが想定外に動いていた

意図しないボットの PR をマージしてしまった。調べると、バージョン更新の設定ファイルは無く、
脆弱性アラートに対するセキュリティ更新の設定が有効になっていた。別の更新ボットに一本化する
つもりだったが、そちらはリポジトリに導入されていなかった。
→ 担い手の移行は、新しい担い手が動いたのを確かめてから、古い方を止める。

## 未読の受信箱だけを見て、受信箱の外の個別メールを見落としかけた

手順どおり未読 11 件だけを見て進めかけた。本人の指摘で、直近 21 日分を、既読・受信箱の外・
フィルタ済みのメールまで広げて読み直したところ、人からの個別メール(予約の承認と、当日の
準備への質問)が、受信箱の外で未読のまま埋もれていた。原因は 2 つあった。手順の検索範囲が
未読の受信箱に限られていたことと、同じ差出人が一括連絡(本人は Bcc)と個別の返信(本人は To)
の両方を送り、差出人だけの規則が個別の返信を digest に振っていたこと。
→ 既定の検索範囲を 21 日・既読込み・受信箱の外込みにする。フィルタは宛先で分け、
個別の返信は受信箱に残す。

## 計画の承認の前に、ログインの壁に当たった

朝の机で、求人サービスのメッセージの返信状況を画面で読もうとして、ログインの壁に当たった。
計画に「ログインは承認後に本人へ頼む」と書いて ExitPlanMode に出したところ、「Plan モード中に
ログインを待ってほしい」と差し戻された。ブラウザでの閲覧は読み取り専用で、Plan モードの中でも行える。
→ ログインの壁に当たったら、ExitPlanMode の前に `browser-login-handoff` でログインだけを頼む。
承認後に回さない。

## 毎朝の処理に、一括処理の HTML ページを使うと重すぎる

一括処理の既定(返信の下書きを HTML のページにまとめ、1 件ずつ裁定する)は、数十件を前提にしていた。
毎朝 2〜3 件を処理する場面でも同じ形にすると、ページを作る手間が処理より大きくなる。
→ 毎朝の処理(日次モード)は、Gmail で返せるスレッドを返信形式の Gmail の下書きにし、HTML のページは
Gmail の外の媒体の分だけにする。一括処理の既定は変えない。

## 毎朝の検索で、カテゴリを除いたため、求人サービスのメッセージ 10 件を見落とした

毎朝の処理(日次モード)の最初の検索で、広告の混入を避けようと `promotions`・`social`・`forums`・`updates` の
カテゴリを除いた。ところが、LinkedIn の InMail は `updates` に入る。直近 21 日分の 10 件が、結果に 1 件も
出なかった。別の経路(機械の提案の一覧)に 1 件が載っていて気づいた。
→ 検索はカテゴリで絞らない。件数が多い自動通知は、送信元ごとに数えて除く。

## Gmail の外の返信状況を、画面で読む前に本人へ聞いた

LinkedIn などの返信は Gmail に送信済みが残らない。手順どおり本人に「どれに返信したか」を聞いて答えを得たが、
本人は処理の途中で「画面で確かめて」と求めた。ログインだけを本人に頼み、ブラウザでスレッドを開いたところ、
本人が「止まっている」と答えた 2 件は、どちらも最後のメッセージが先方で、本人の返信は無かった。
聞くよりも、画面を読む方が確かで、本人の手間も小さかった。
→ 本人に聞く前に、ブラウザで画面を読む。読めなかったときに限り、試した経路を添えて聞く。

## 道具の一覧にあることを、権限の確認だと読んだ

既読化の権限は計画の承認前に確かめる、という手順があった。コネクタの道具の一覧に既読の付け外しがあったため権限ありと読み、
1 件の試行をしないまま計画を承認に出した。実行で `Insufficient scope`(`gmail.modify` が無い)になり、段が未完了で終わった。
本人は手元のツールに既読化を足すよう求めた。そのツールは同じ権限のトークンを既に持っていたので、検索で指した未読を既読にする
サブコマンドを足し(空の検索と 50 件超を拒否、ドライランで全件を表示、戻せるログ)、承認済みの 4 件に使った。
→ 権限は、一覧ではなく、本人が承認した 1 件の試行で確かめる。拒否されたら、計画の段を最初から別の手段に書く。

## 一括処理の裁定が、ページを開いたブラウザの中に残るだけで、記録に戻らなかった

一括処理で、判断の表の 20 件、返信の下書き 3 件を HTML のページに並べた。本人の裁定はブラウザの localStorage に
保存され、「回答をまとめる」でチャットに貼らなければ、次のセッションにも届かない。その日の記録に載った裁定は 1 件だけで、
残りは「どこまで済んだか」が分からなかった。Gmail で返せる 1 件も、ページ止まりで Gmail の下書きにならなかった。
→ 未裁定の項目は `ask`・`draft` で記録に載せ(`worklog` の状態機械、`docs/agents/mail-lifecycle.md`)、裁定は固定の 1 枚の
ページの db に保存して次のセッションが `decide`・`pass` として書く。Gmail で返せるスレッドは一括モードでも
返信形式の Gmail の下書きまで作る。

## 返信の下書きの宛先が 1 文字違い、送った返信が不達だった

一括処理の返信を、元のメッセージへの返信形式で Gmail の下書きにした。本人が送ったあと、直後に配信エラー(宛先のアドレスが拒否された)が同じスレッドに届いた。下書きの宛先が、元の送信元と 1 文字違っていた。下書きを作ったあとに宛先を読み戻す手順が無く、一括処理の報告にも「宛先は未確認」と書かれていなかった。取り込みの途中で、スレッドを読み直して分かった。
→ 下書きを作った直後に `get_draft` で宛先を読み戻し、元の送信元(`Reply-To` があればそれ)と一字一句同じであることを確かめる。`to` を手で打たない。読み戻していなければ「宛先は未確認」と書く。

## 読み戻しの基準にした `sender` 欄が、アドレスのドットを落としていた

上の事例のあと、不達の原因を調べた。送信元のアドレスは `y.haruna@…` で、`search_threads` の `sender` 欄は `yharuna@…` と、ドットを落として返していた。不達になった返信の宛先は、この `sender` 欄と同じ綴り(ドット無し)だった。`sender` 欄を基準にして読み戻すと、誤った宛先を「一致」と読む。元のメッセージを `get_message` の `messageFormat: RAW` で取ると、`From` と `Return-Path` のヘッダは `y.haruna@…` だった。`get_thread` の `sender` 欄が同じかは未確認。
→ 読み戻しの基準は、`RAW` の `From` と `Reply-To` で取る。`search_threads` の `sender` 欄は、基準にも、`to` の入力元にも使わない。

## 処理を終えても、未読が 11 件のまま残っていた

一括処理で、返信の下書き・判断の表・記録を作り終え、未読の受信箱は 11 件のまま「既読化は権限の確認が先」と後回しにした。本人は「そもそも未読メールが未読のままなのが気持ち悪い。手元のボールがその時点では全て打ち返された状態になることを保証してほしい」と述べ、既読でも未処分のものは、未読と同じに扱う今の検索の範囲は変えないよう確認した。
→ 完成の条件を「範囲内のすべてのスレッドに処分が付き、未読が 0 件になり、ボールの在処(あなたの番・私の番・相手の番)を報告する」にした。未読は追跡の道具にしない(追跡は `worklog`・裁定ページ・カレンダー・Issue)。日次モードも、既読化を行う。

## 既読化の実行が、自動モードの分類器に拒否された

コネクタには `gmail.modify` が無く、手元の Gmail 用ツールの `sweep.py inbox-mark-read` で既読にする手順だった。ドライランは通ったが、`--execute` が分類器に「外部システムへの書き込み」として拒否された。本人は、規則を決めて既存の手順に乗せるよう指示していたが、この実行そのものへの承認は、分類器が読める形では無かった。
→ 迂回しない。本人に、実行する 1 行(`!` つきのコマンド)を渡す。繰り返し使うなら、本人が Bash の許可規則を置く。
