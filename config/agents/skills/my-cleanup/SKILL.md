`/my-cleanup` は、本人が習慣として手で打つ入口の 1 つ(もう 1 つは朝の机)である。旧名の
`backlog-cleanup`・`wrapup-chores`・`issue-hygiene` はこのスキルへの転送口で、手順の正本はここにある。

wrap-up inbox と起票済み wrapup 由来 Issue を 1 件ずつ Issue → PR で回すのは
摩擦が大きい。このスキルは収集 → 粗振り分け → 裁定 → Plan → 一括対処 → 消化を
定式化する。**確認の総数ではなく位置を変えるのがこのスキルの核**: 確認は
triage フェーズ(§2〜§4)に全部前倒しし、`ExitPlanMode` が GO を兼ねたあとは
一切止まらない。除外は閉じたタグでしか成立しないので、「規模が大きい」
「よく分からない」は agent が独断で母集団から落とす理由にならず、必ず
ユーザーへの問いに変換される。

気づき(inbox)は Stop で Issue にならない(ADR-1136)。vault の
`inbox/` に 1 件 1 ノートで溜まり、**ここで裁定したものだけ**が PR で直されるか、Issue になる。
直せるものは Issue を経ずに PR で直す。Issue にするのは、chores の PR に入らない大物(L3)と、
本人の作業が要るもの(L5)だけである。

## 1. 候補収集

- **inbox**: `~/.claude/hooks/issue-inbox --list-open --repo <owner/repo> --json` で読む(`<owner/repo>` は
  このリポジトリの `origin`)。vault を宣言している機体では vault の `inbox/` の、状態が open のノートが、
  **再発の行数の多い順**(同数なら初出が古い順)に出る。各要素は `title`・`repo`・`count`(= 再発の回数)・
  `first_seen`・`rows`(日付つきの行)・`note`(vault からの相対パス。jsonl の機体では `jsonl:<8 桁>`。§8 の `--set-status` の第 1 引数に、題名の代わりに渡せる)・`source`(`vault` / `jsonl`)・
  `signal`・`mechanism`・`existing`(as-code 化の候補のときだけ値がある。retro の `codify` などの行が渡す。
  `signal` が兆候、`mechanism` が次から防ぐ手段、`existing` が採用|拡張|自前。§4 の選択肢の根拠に添える)。
  vault の無い機体では inbox の jsonl の行が同じ形で出る(`source: jsonl`、1 行 = 1 回)。
  **読むのは `--list-open` だけにする** — vault の絶対パスを知る必要も、ノートを直接読み書きする必要も無い
  (状態の変更は `--set-status`、追記は `--add` に限る。この制約はこのスキルでも不変)。再発の回数が
  多いものは、直す価値の根拠として §3 の起草と §4 の選択肢に添える(ADR-543 の昇格の合図)。
  この結果も scratchpad のファイル(例 `findings-<取得時刻>.json`)に保存する(§5 で取り直して比べる)。
- **母集団は open Issue 全件 + inbox の open な気づき全件**: 起票済み Issue の発見は wrap-up フッター一致に頼らない — 実測(2026-09-21)で本文フッター一致は open Issue のごく一部にしか当たらず、汎用の attribution フッターのみを持つ Claude 起票 Issue の大半が発見漏れになっていた。`blocked-by-upstream` ラベルはクエリ段階で機械除外し、残りを §2 の粗振り分けで判定する:
  ```
  gh issue list --state open --limit 500 --json number,title,body,labels,updatedAt \
    | jq '[.[] | select(([.labels[].name] | index("blocked-by-upstream")) | not)]'
  ```
  この結果は scratchpad のファイル(例 `population-<取得時刻>.json`)に保存しておく。
  §5 の `ExitPlanMode` の直前に、同じクエリを取り直して差分を取るために使う(#971)。
  **この収集と差分は 1 コマンドにしてある**: `~/.claude/hooks/issue-inbox --collect <scratchpad のディレクトリ> --repo <owner/repo>`
  が、除外ラベルを除いた open な Issue(番号・題・更新日時)を `population.json` に、open な気づき(`--list-open --json` と同じ形)を
  `findings.json` に保存する。`--limit` と同数が返ったら、limit を倍にして取り直す(§1 の規則)のも、このコマンドが行う。本文
  (`body`)は保存しない(§2 の粗振り分けで本文が要る Issue は、`gh issue view` か、1 回の `gh issue list --json number,body` で
  読む)。§5 の差分は `--collect-diff`(同じ引数)。#1421。
  **取得件数が `--limit` と一致したら打ち切りの可能性がある**ので、その場合は limit を倍にして再実行する。wrap-up フッター regex(統合形 `Filed from [Claude Code](...) wrap-up inbox` と旧 2 行形式の両方にマッチする `test("Filed from \\[?Claude Code.*wrap-up inbox")`)は廃止しない — マッチする Issue は粗振り分けを経ずに無条件で候補に含める**ヒント**として使う。

## 2. 粗振り分け(本線・title + body だけで判断)

5 レーンに振る。判断は title + body だけで済む粒度でよい(本文を読んでも方針が
定まらないものは無理に決めず L2 に落とす):

| レーン | 条件 | 行き先 |
|---|---|---|
| L1 裁定不要 | やり方が一意で、選択肢の提示が発生しない | そのまま段1 |
| L2 裁定要 | 実装方針が分岐する、または情報が足りない | §3 の起草へ |
| L3 大物 | chores PR に物理的に入らない規模(設計判断・ADR 起草を要する、または変更が広範) | §4 の一括問いへ |
| L4 外部ブロック | `blocked-by-upstream` ラベル、または本文で **リポジトリ外**の事情(upstream の未修正・未 GA、他者のマージ待ち)が明示されている | `Blocked-Upstream:` |
| L5 本人操作 | 実機のブラウザ・カードの解錠・本人の判断・アカウント設定の画面など、**本人が操作しないと閉じない**。かつ第三者を介さず、そのセッションの作業領域に関わる | §7a の「本人作業フェーズ」(除外しない) |

明示的に禁じる規律を 4 つ書く:

- **「規模が大きい」は L4 にならない。** 必ず L3 に入れ、刈り取るかどうかは
  ユーザーが決める。規模・工数・セッション長・コンテキスト残量を理由にした除外は
  誤用であり、書いてはいけない(`requirements-inventory` §2 と同文)。
- **「よく分からない」で母集団から落とさない。** 分からなければ L2 に入れ、
  §3 のサブエージェントに調べさせる。
- **同一母集団内の Issue 待ちは L4 にならない。** `Blocked-Upstream:` は
  `requirements-inventory` §2 の定義どおり**リポジトリ外**の事情に限る。母集団の中に
  先行 Issue が居るなら、今回それを刈れば後続も着手可能になるので、後続は
  L2 または L3 に入れて**裁定に載せる**。

- **「本人の操作が要る」「実機・カード・同意が要る」は棄却の理由にならない。**
  規模・工数と同じ誤用で、問題は誰がいつ操作するかであって、やるかどうかではない。
  第三者(同僚・事務局・編集部・情シス・上長)の協力が要るもの、そのセッションの
  作業領域の外のものだけが、裁定で `User-Excluded:`(理由に「第三者」「領域外」と
  書く)になる。判別は L5 の条件(第三者を介さない・作業領域に関わる)で行い、
  迷ったら §4 の問いに載せる(本人の裁定 — tarotene/dotfiles#691)。

依存を持つ項目の扱い:

- §3 の起草では、先行 Issue の番号と「先行を今回刈った場合/刈らなかった場合」の
  両方を選択肢に含めさせる
- §4 の裁定で先行・後続の両方が選ばれたら、ADR-0027 の単一チェーン上で
  **先行を段 k、後続を段 k+1** に置く(依存の向きがそのまま段の順序になる)
- 先行が選ばれず後続だけ残った場合の処分は `User-Excluded: 先行 #N が今回対象外`
  であって、`Blocked-Upstream:` ではない

## 2a. Issue の構造の整理(旧 issue-hygiene。母集団の Issue を親子に束ねる)

§1 で集めた open Issue は、粗振り分けと同じ読みで、構造の面からも見る。同じ出自(同一の設計判断・
同一の先行 PR・同一の構想)から生まれた Issue が一覧上ただの兄弟として並ぶと、依存と完了条件が
見えなくなる。ここでは GitHub の sub-issues で親子を張り直し、作ったまま腐った tracking Issue を
清算する。親子の操作の手順(`gh` のコマンド、本文に子へのチェックボックスを書かないこと、
`tracking` ラベル、階層の上限、閉じ方)は `tracking-issue` スキルの §2・§4・§6・§7 が正本で、
ここには複写しない。

**候補の洗い出し**(母集団の title + body だけで済む粒度):

- **クラスタ**: 本文の相互参照(同一 ADR・同一先行 PR・同一構想への言及)で出自が同一と確かめられる
  Issue 群。「同じ時期に起票された」だけでは束ねる根拠にならない。出自が違っても、同一の運用領域に属し
  完了を一緒に追跡したい群は束ねてよいが、傘の本文に運用領域の名前を理由として書く。「open Issue の数を
  減らしたいから」は根拠にならない。2 件程度の小さな群ごとに傘を乱立させない。
- **昇格候補**(割れたのに親へ昇格していない Issue): 本文に子を指すチェック(`- [ ] #NN`)を持つ open
  Issue / `Closes`・`Fixes`・`Resolves` で 2 本以上の PR が紐づく open Issue(`gh pr list -R OWNER/REPO
  --state all --json number,closingIssuesReferences` で Issue ごとに数える)/ `gh issue list --json
  number,subIssuesSummary,parent` で親も子も持たない Issue のうち、相互参照からクラスタが疑われるもの。
- **腐った tracking Issue**: 子が全て closed なのに親が open のままのもの。閉じる条件は `tracking-issue` §7
  (全 sub-issue が closed で、かつ `## 完了定義` が満たされていること)。満たされていなければ閉じず、
  残作業を子として繋ぐ。子の一部が残っているものは清算せず、残作業を正しく子に繋ぎ直して open のまま維持する。
- **除外**: bot が管理する Issue(依存関係ダッシュボード等)は候補に入れない。

**レーンへの振り方**: 構造の操作は PR を伴わない GitHub 上の操作だが、§2 の 5 レーンに同じ基準で振る。

- 出自が本文で確かめられ、`tracking-issue` §7 の条件が読み取りだけで確かめられるもの(束ねる・親の
  本文を実態に合わせて書き直す・条件を満たした親を `completed` で閉じる)は L1。
- 運用領域で束ねる案、傘の粒度の判断が分かれるもの、完了定義が満たされているか読み取れない親は L2。
- **クラスタに属さない停滞 Issue は、構造の整理では閉じも束ねもしない。** 閉じるのは、§4 の裁定で本人が
  「閉じる」を選んだもの(処分は `Obsolete:`)だけで、それ以外は残す。これは旧 issue-hygiene の「ユーザーの
  明示判断なしに閉じたり束ねたりしない」と同じ線で、§2 の「規模が大きいは棄却理由にならない」とも両立する
  (閉じる理由に規模・工数を書かない)。

**実行**は §7 で、段の PR とは別に、GO のあとにまとめて行う(sub-issue の追加・親の本文の書き直し・
親の close)。傘の本文は `tracking-issue` の本文スケルトンで書く。

## 3. 選択肢の起草(L2 の各件に 1 サブエージェント、並列、read-only)

L2 に振った項目ごとに background subagent へ起草を委譲する(`github-audit-triage`
§2 と同じ型)。本線のコンテキストを個別の起草で焼かないためで、これをやらないと
「情報が足りないから要判断」を本線が言い出し、現行版と同じ日和りに戻る。

subagent への指示・返値の契約:

- 暗号化資料は復号しない。PIN 入力や復号ラッパーも使わず、必要な暗号文の
  パスと必要な箇所を本線へ返す。本線から渡された必要範囲の抜粋で調査し、
  取得できなかった事実を未確認として返す。
- `gh` と読み取り専用ツールのみ。**実装はしない**、案の比較だけ行う
- **Issue のコメントより先に、その Issue が指す手順書・ADR・runbook を読む。**
  本文中の `docs/`・`state/` のパス、関連する ADR 番号を対象リポジトリで読み、完了条件が
  既に満たされていないかを確かめる。満たされていれば、返値の先頭に「完了条件は既に
  満たされている(根拠: パスと行)」と書かせる(起票時のコメントだけを根拠にして、
  リポジトリの記録を読めば不要と分かる本人作業を選択肢に載せた実例がある。#983。
  同じ見落としが繰り返されたら、返値の形式検査への昇格を検討する)
- 実装案を 2〜4 個。各案に「変更するファイルと行数の概算」を付ける
- 推奨 1 つと、推奨理由 1 行
- 先行例: 出典(URL・`#N`・パス)+ 取得日、または `先行例なし:` + 探した範囲
- **挙動の断定には、読んだソースの版・ファイル・行を添えさせる。** フレームワーク・
  外部ライブラリ・crate の挙動(「関数 A を使えば〜できる」「型 B は公開されている」)が
  対象。添えられないものは `未確認` と返させる(#970)
- 軸: `表現不可能` / `還元` / `検出のみ` のいずれか + 1 句。**この返値は起草の
  結果であって、裁定の入力ではない**(検算は §4 の冒頭)
- 対処が PR の外(ホストローカルファイル・GitHub 設定等)に出る項目では、
  **「宣言化して正本に取り込む案」を必ず 1 案に含める**(ADR-0001: home-manager
  が正本 / ADR-0034: 実値は private wrapper flake)。実値を含むものは public
  リポに書けないので、private wrapper flake 行きの案として立てる
- 依存を持つ項目(§2 末尾)は「先行を刈った場合」「刈らなかった場合」を別案として出す
- ホストの設定リポジトリの正本は `~/.ghr/github.com/<owner>/<repo>` の置き場。
  ホーム直下の複製(`~/dotfiles` など)は履歴が分岐した古い写しのことがあるので、
  参照も、手順の根拠にもしない。導入・適用の手順を書く前に、`hms --help` の出力で
  適用手段を確かめる(適用は `hms` 1 本で、`git pull` は要らない。#817)。人に渡す
  手順は、本線が実体(コマンドの `--help`、`git status`)と突き合わせてから出す

先行例と軸をここで取らせることで、§5 の Plan の `## 先行例との対比` がほぼ
組み立て済みになる。

## 4. 裁定(`AskUserQuestion`、triage フェーズ内で完結)

**選択肢に載せる前に、§3 の返値の軸ラベルを本線で検算する。** 選択肢のラベルは
本人の裁定の入力になるので、誤ったラベルのまま載せると判断の前提が崩れる。各案の
軸を、定義に当てて確かめる: 不正な状態を表現できなくするなら `表現不可能`、既存の
より安い手段に置き換えるなら `還元`、検出して弾く・散文で促すだけなら `検出のみ`。
散文の規範は通常 `検出のみ` である。`既存手段: 拡張`(新しい道具を作らず既存を
伸ばす)と `軸: 還元` を取り違えない。返値と本線の判定が食い違ったら、本線の判定に
置き換えてから載せる。軸ラベルに加えて、返値の事実の主張(因果・時系列など)も、
「読んだ一次情報」か「推測」かを区別して選択肢に載せる(読めない主張に「推測」を
付ける。共有 AGENTS.md「引き継いだ数字と下書きは、検算してから本人に出す」)。

**軸ラベルに限らず、返値の事実の断定(挙動の断定)も、載せる前に検算する。**
返値にある挙動の断定は、サブエージェントが読んだと主張するだけで、共有 AGENTS.md の
「版を固定した一次ソースを読み、根拠をファイルと行で添える」を経ていない。Plan の
`## 先行例との対比` の `差分:` に挙動の断定を書くときは、**本線が一次ソースのファイルと行を
読んだものに限る**。読んでいない断定は `未確認` と書き、選択肢の推奨理由にしない
(実例: 「関数 A で目次を保ったまま章区切りを止められる」という返値が Plan に入って
承認されたが、実装前にソースを読むと関数 A は目次に効かなかった。「crate の型 B は公開
されている」という Issue の前提も、実際のバージョンでは private だった。#970)。

**選択肢や質問の本文に載せる件数は、暗算しない。** グループ別の列挙を足し算で書くと数え誤る(2026-10-28 に
対象外を 29 件と書いたが 30 件で、#249 を二重に数えていた。除外件数を 21 と数え誤った実例もあり、再発している)。
処分(L1〜L5 の振り分け、対象外、`Blocked-Upstream:`)ごとの番号の一覧を scratchpad に書き、件数はそこから
`jq` や `wc -l` で出す。番号を列挙するときは、同じ一覧から文字列を作り、全体の件数(§1 の母集団)と
グループの合計が一致することを確かめてから載せる。

- **L2**: 1 件 1 問。§3 の返値(軸は検算済みのもの)を選択肢にし、「今回は除外」を必ず加える。
  1 回の呼び出しで最大 4 問(`AskUserQuestion` の上限)なので、件数が多ければ
  複数回に分けて呼ぶ
- **L3**: `multiSelect` で一括。「今セッションで着手する大物を選ぶ」。各選択肢に
  **「→ 段N になる」コストを明記する**
- L3 で選ばれなかったものは `User-Excluded: 裁定で今回対象外` になる

- **L5**: 範囲の確認を 1 問で聞く(「第三者を介さず、作業領域に関わるものは本人作業フェーズで
  扱う。対象はこの N 件、除外はこの M 件でよいか」)。あわせて、本人作業フェーズで**止まる箇所**
  (カードの解錠、ブラウザでの同意、書き込みの承認、判断)を、Issue 本文から洗い出して
  同じ呼び出しで聞く — GO 後に止まらないために、ここで前倒しする(§7a)

これが完了すると、母集団全件が次のいずれかに確定している: L1(裁定不要)/
L2 の裁定結果(実装する案 or 除外)/ L3 の裁定結果(着手する段 or 除外)/
`Blocked-Upstream:`。

## 5. Plan を書く(このスキルは plan mode で走る)

plan mode でなければ `EnterPlanMode` を呼ぶ。Plan を書く直前に `git fetch origin` して、作業ツリーの HEAD と
`origin/<default>` の差を確かめる(差があるときの事実の取り方は `requirements-inventory` §1a、#935)。Plan には:

- `## 要求インベントリ` — 母集団の**全件**を `R1..Rn` で列挙する(open Issue +
  inbox の open な気づき)。各 `Rn` の処分は `段N で実装` / `Blocked-Upstream:` / `Obsolete:` /
  `User-Excluded:` のいずれか 1 つ
- L5 の `Rn` の処分は、本人作業の結果を反映する最後の段(§6)の `段N で実装` にする。
  閉じられなかったものは、状況コメントつきで open のままにする(§7a、§9)
- `## 先行例との対比` — §3 の返値から `Dn` 行を組み立てる
- **自己検査の前に、母集団と前提の差分を取り直す**(#971)。収集から `ExitPlanMode` までの間に
  起草の再起動や本人への質問が挟まると、Plan の前提が古くなる(実例: 起草エージェントの
  再起動が半日続く間に、別セッションが起票した Issue が母集団に 1 件増え、`ExitPlanMode` を
  本人に差し戻された)。次の 3 つを取り直して、§1 に保存した結果・Plan を書いたときの値と比べる:
  - open Issue と気づき: `~/.claude/hooks/issue-inbox --collect-diff <§1 のディレクトリ> --repo <owner/repo>` が、取り直して、
    保存した結果との差分だけを出す(`+` 増えた、`-` 消えた、`~` 更新日時が変わった。気づきは `再発 N -> M 回`)。差分が無ければ
    `no changes`(終了コード 0)、あれば差分の行(終了コード 1)、取得の失敗は終了コード 2。保存した結果は書き換えない。
    別のセッションが起票した Issue や、`--add` した新しい気づき、再発の増えたものが見つかる
  - default branch の先頭: `git fetch` 後の `origin/<default>` の SHA。Plan を書き始めたときと
    変わっていたら、Plan が根拠にしたファイルの差分を読む(`requirements-inventory` §1a)
  - Plan が根拠にした他リポジトリの Issue: `gh issue view <N> -R <OWNER/REPO> --json updatedAt`。
    根拠にした Issue の番号と `updatedAt` は、Plan を書くときに控えておく

  差分があれば、Plan の要求インベントリに足すか、前提が変わっていないことを確かめてから
  `ExitPlanMode` を呼ぶ。機械化できる(保存と diff だけ)ので、同じ差し戻しが繰り返された
  ら script への昇格を検討する(ADR-543 の昇格型)。
- 自己検査 2 本を走らせて指摘ゼロを確認してから `ExitPlanMode`:
  - `~/.claude/hooks/plan-scope-gate --check <プランファイル>`
  - `~/.claude/hooks/plan-precedent-gate --check <プランファイル>`

**`ExitPlanMode` が GO を兼ねる。** 個別の裁定は §4 で既に済んでいるので、
Plan 提示後に会話上で改めて表を出して GO を取り直すことはしない。

## 6. 段の構成

分割の軸は **「レビューが 1 本で成立するか」**。

- 段1 = chores PR。L1 と、裁定済みだが局所(数ファイル・独立に読める)な項目
- 段2 以降 = 非局所な裁定済み項目と、裁定で選ばれた大物を 1 件 1 段。依存を
  持つ組は §2 の規律どおり先行 → 後続の順で連続する段に置く

ADR-0027 に従い単一チェーンに積む。手順・`Stack:` 行・段ごとの `Closes` の
書き分けは `stacked-pr` スキルに委譲する(ここでは再掲しない)。

## 7. 一括対処(GO 後は止まらない)

- 最新の default branch から作業ブランチを切る(`Closes` が効くのは default
  branch 向き PR だけなので、ベースブランチを必ず確認する)。
- 項目ごとに 1 commit。Issue に対応する項目は commit message に `#N` を含める。
- §2a の構造の操作(sub-issue の追加・親の本文の書き直し・親の close)は、PR の段とは別に、`tracking-issue`
  の §2・§4・§6・§7 の手順で、GO のあとに行う。親を閉じる前に根拠(全 sub-issue が closed であること、
  完了定義の充足)をコメントに書き、閉じたあと状態を読み戻してから報告する。
- **段1 の最初の commit ができたら、すぐ push して PR を作り、以後はその PR に commit を足す。**
  サブエージェントへの委譲の完了を待つ Stop のたびに、`pr-gate` が「未 push の commit があります。
  PR はまだありません」と block し、PR 作成を急かす(2026-10-27 に 6 回。#1093)。かつての
  `--chores-begin` の「実行中の印」は ADR-1136 で削除され(`session-wrapup --chores-begin` は
  exit 1)、`pr-gate` を抑える手段は無い。PR が先にあれば `no_pr` の block は起きない。追加の push
  のたびに CI が回り直す費用は、この block の往復より小さい。
- 他リポジトリで作業する段は、`github-audit-triage` §6 の手順 1・2 に従う。
  scratchpad の clone は読み取りだけに使い、`herdr worktree create --cwd
  <clone> --branch <名前>` で切った worktree で編集・commit する
  (main-checkout-guard が clone への編集を deny する、#734)。
  worktree がセッションのプロジェクトの外にあるときは、git の `add`・`commit`・`push` が `git -C` になるか、
  `cd <dir> &&` と連結することになり、除外パターンに合わず sandbox に残って署名が `No secret key` で失敗する
  (`fetch` も `.git` が書き込み許可の外で `Read-only file system`。2026-10-28 に private wrapper の worktree で、
  段ごとに `dangerouslyDisableSandbox` を 3 回使った)。`config/claude/CLAUDE.md`「sandbox の外で動かす
  コマンドは、単体で呼ぶ」の `SANDBOX_COMPOUND_GUARD_ALLOW=1` + 承認つきの `dangerouslyDisableSandbox` の
  手順に従い、段ごとにその承認が要ることを、最初に本人へ伝える。
- **Issue の置き場と対処先の可視性が違うとき**は、§3 の起草の時点で
  `gh repo view <OWNER/REPO> --json visibility` で両方を調べ、裁定の選択肢に
  載せる前に扱いを決める。Issue が private で、対処先が public のリポジトリなら:
  - `gh issue transfer` は選択肢に出さない(private から public への移管は
    `Old issue cannot be transferred from private repository to public repository`
    で失敗する)。
  - public 側の commit・PR 本文に private リポジトリの名前・Issue 番号を書かない
    (公開ガードが止める)。PR は `No-Issue:` で理由を書き、理由に private の
    参照を入れない。`Closes <private>#N` も使えない。
  - private 側の Issue には、PR の URL をコメントして open のままにし、PR の
    マージ後に手で閉じる。閉じ忘れを拾えるよう、private 側の段の PR の
    `## 要確認` か本人への報告にポインタを置く(public 側の PR には書けない)。
- **段の実装は、既定で本線が行う**(本人の指示 2026-11-08: 「サブエージェント払い出すと効率落ちるので
  メインエージェントで集約して作業してほしい」、#1394)。払い出すたびに文脈の受け渡し・待ち・途中の中断の
  再開・結果の読み戻しが要り、全体では効率が落ちた(別の worktree に切り替わったまま `git add -A` や
  `git push` を別のリポジトリで実行した誤りも出た)。サブエージェントに出してよいのは、本線を止めたく
  ない**読み取りだけの独立した調査**(§3 の起草など)と、利用上限(HTTP 429)に近く、本線で回し切れない
  ときの例外だけである。
- 例外として段や repo をサブエージェントへ委譲するときは、`github-audit-triage` §6a の
  委譲の運用(波・止まる前の commit/push・共通指示のファイル化、#735)に従う。
  あわせて、作業場所は次のとおり渡す(#1004):
  - **`Agent` の `isolation: worktree` を使わない。** 本物の checkout の `.claude/worktrees/` 配下に
    worktree が作られ、`cargo` が上位の `Cargo.toml` を workspace と誤検出して `cargo fmt --all` が
    落ちる repo がある(commit hook が失敗し、サブエージェントが `--no-verify` で commit した実例)。
    本線が先に `herdr worktree create --cwd <本物の checkout> --branch <名前>` で本物の checkout の
    外に worktree を作り、その絶対パスを指示に書いて渡す。
  - 癖: `git worktree add` の直接実行は PreToolUse の hook が拒否する。`herdr worktree create` は
    本物の checkout の cwd でしか実行できず、linked worktree からは `linked_worktree_source` で
    拒否される。
  - 起点を動かす: 作った worktree の起点は default branch の HEAD である。チェーンの途中のブランチから
    始めるときは、worktree の中で `git reset --hard <ブランチ>` する(`herdr worktree create` の
    `--base <REF>` が同じことをするかは未確認 — `--help` に説明が無い)。
  - **`--no-verify` を使わせない。** 共通指示のファイルに「hook が落ちたら、原因を直して commit し
    直す。`--no-verify` で飛ばさない」を入れる。委譲した作業の commit が、リポジトリの検査(hook)を
    飛ばさずに積まれるようにするため。
- 各段の PR 本文はリポジトリの `pr-description` スケルトンに従う:
  - その段で対処した Issue はすべて `Closes #N` として列挙する
  - inbox 由来で対応する Issue が無い項目は、**新たに起票しない**(起票して
    即クローズする churn を避ける)。代わりに「課題」節に「inbox 直接消化分」
    として title / detail を列挙し、何を直したかを本文で監査できるようにする
  - その段の対処項目が inbox 直接消化分のみ(Issue が 1 つも無い)の場合に限り、
    `No-Issue:` で理由を明記する
  - Before/After は視覚的な変更があれば証跡を、無ければそのリポジトリの規約に
    沿って明示する

実装中に §5 で想定していなかった分岐が判明した場合の規律:

> 推奨案で進め、**PR 本文の `## 要確認` に「分岐があった / こちらを採った /
> もう一方はこう」を必ず書く**。`AskUserQuestion` で止まらない。完了定義は
> PR 作成までで merge しないので、レビューが安全網になる。

## 7a. 本人作業フェーズ(L5 を扱う。段の PR を作ったあと)

全段の PR を作ったあと、L5 の Issue を片付ける。結果は PR にも Issue にも残す。

- **私が動かせる部分は私が進める。** 読み取り・プレビュー・`--dry-run` で確かめられること(画面の
  構造、設定の現在値、復号した宣言の中身、実データでのコマンドの実行)は、本人を待たずに実測する。
  結果は、読み戻した手段を添えて報告する。読み戻せなかったものは「未確認」と書く。
- **止まるのは、フェーズの頭で聞いた箇所だけ。** カードの挿入と解錠(`! <コマンド>` で本人の
  端末に PIN を入れてもらう)、ブラウザでの同意、本人の判断(値の確定、宣言の中身)。途中で
  増えたものは、まとめて 1 回で聞く。
- **書き込みは、本人が承認した範囲に限る。** 外部システムへの書き込みは、安全な対象(取り消せる・
  他者に通知が飛ばない・本人の記録を壊さない)に限り、事前に対象を示して承認を得る。
  **アカウント設定は触らない** — 画面の経路と現在の状態を読み取りで確かめ、手順に書く。
  安全な対象が無い実験は、無理に作らず(本人のカレンダーに実験用の予定を足すなど)、条件が
  揃うまで open にする。
- **使った機構自体の不具合が見つかったら、その場で直す。** 実機で初めて動かして落ちたもの
  (偽の画面を使う単体テストでは見えなかった不具合)は、回帰テストを足して該当の段に積み、
  上の段を rebase で追従させる。`gh stack link` は全段の内容が確定し CI が green になって
  から 1 回だけ行う。
- **終わり方。** 完了条件を満たした Issue は、証跡(何を・どの手段で読み戻したか)をコメントして
  閉じる。満たせなかった Issue は、何をして何が残ったかをコメントして open のままにし、
  PR 本文の `## 要確認` にポインタ(`- #N — 一言`)を置く。コメントにも数字(時間・按分)は
  書かない(リポジトリの外向きの文面の規約に従う)。
- **確認の台帳(`verify-ledger: <host>`)は、コメントでなく本文を書き換える。** 確かめた項目は、
  その行を `- [x]` にして結果を行末に書く(`pr-description` §6 の手順 5)。確かめられなかった
  項目は行をそのまま残し、「変化なし」「今回は実施していない」のコメントを書かない。状態は本文の
  行が持ち、コメントを重ねても件数は減らない(2026-11-11 の棚卸しでは、#990・#979 の「変化なし」の
  コメントが、確認済みの機体を「残る」と書き直して食い違っていた)。台帳の外にある実機確認の
  Issue を見つけたら、行を台帳に移して閉じる(ADR-1529 の置き場 6)。

## 8. 気づきの消化タイミング

その項目を含む**段**の PR 作成(`gh pr create` 成功)の直後に、対処した気づきの状態を
`~/.claude/hooks/issue-inbox --set-status "<title>" <状態> [url] --repo <owner/repo> [--reason <理由>]` で変える
(第 1 引数は、ノートの `title` の完全一致か、`--list-open --json` の `note`。長い題名は `note` で指す。ノートの直接編集は不変で禁止)。

| 裁定 | 状態 | url |
|---|---|---|
| PR で直した(Issue を経ない) | `fixed` | その段の PR の URL |
| 大物・本人の作業として Issue にした | `issued` | `gh issue create` で作った Issue の URL |
| 直さない・もう起きない | `dropped` | 無し(`signal` を持つ候補は `--reason` が必須) |

- **`signal` を持つ候補(as-code 化の候補)を `dropped` にするときは、`--reason` に閉じた理由を 1 つ書く**。
  兆候ごとの採用・却下と理由を日次で数え、却下が続く兆候の定義を直すための実績になる(ADR-1276)。
  理由は「何が違ったか」で選ぶ:

  | `--reason` | 選ぶとき |
  |---|---|
  | `semantic-judgment` | 意味の判断が要り、機械では決められない |
  | `unobservable` | 機械から観測できない(チャットの報告、散在した書き込み経路など) |
  | `preference` | 好みの問題で、例外ゼロの規則ではない |
  | `one-off` | 一度きりの探索で、繰り返さない |
  | `existing-suffices` | 既存の仕組みで足りていた(探索が浅かった) |
  | `misread-signal` | 兆候の読み違い。この兆候の定義が当たっていない |

  `signal` を持たない旧い気づきは、理由なしで `dropped` にできる。

- **Issue にするのは L3 と L5 だけ**: 本人が裁定で「Issue にする」と選んだものを `gh issue create` で
  起票し(本文の末尾に出自フッター「🤖 Filed from [Claude Code](https://claude.com/claude-code) wrap-up inbox」を
  付ける。`--check-dup "<title>"` で同名の open Issue を先に確かめ、あれば新しく作らず `gh issue comment`)、
  その URL で `issued` にする。公開リポジトリの Issue には、再現に要る最小限の事実だけを書く
  (内部の名前は書かない。PreToolUse の denylist に弾かれると 1 往復を失う)。
- vault の無い機体(`source: jsonl`)では、同じコマンドが jsonl のその行を取り除く
  (`<inbox>.filed.jsonl` に退避)。状態は残らないが、PR 本文と commit が記録になる。
- **commit 直後ではなく PR 作成直後**にする理由: セッションが PR 作成前に終了しても気づきは
  open のまま残り、次の機会に拾い直せる。commit しかしていない段階で `fixed` にすると、push 前に
  セッションが落ちた場合に、直っていないのに直った記録になる。
- **merge 後ではなく PR 作成直後**にする理由: PR 作成から merge までの間、対処済みの項目が
  open のままだと、その間に走る別の `/my-cleanup` が同じ項目を再び拾う。merge を待って
  変える主体はこの機構には存在しない。PR 作成直後に変えておけば、記録は PR 本文と commit に
  恒久的に残る。
- 直したはずの気づきが再発したときは、`--add` がノートを自動で open に戻す(再発の行が足される)。
- 裁定されないまま `open` で 14 日たった気づきは、日次の `promotion-detect` が `lapsed` にする(ADR-1381)。`lapsed` は
  `--list-open` に出ない。再発すれば `--add` が open に戻し、`--set-status` で `fixed`・`dropped` にも進められる。

## 9. 完成の定義

次をすべて満たすまで完成と呼ばない:

- 母集団の全件が `## 要求インベントリ` にちょうど 1 回ずつ現れ、処分を持つ
  (発見漏れゼロ)
- `plan-scope-gate --check` と `plan-precedent-gate --check` が
  指摘ゼロ
- 全段の PR が作成済み(`stacked-pr` の完了定義に従う)
- 対処した項目の `Closes #N` が段ごとに 1:1 対応している(Issue を経ない直接消化分は
  本文の列挙で代替)
- 対処した気づきがすべて `--set-status` で `fixed` / `issued` / `dropped` になっている(`--list-open` に残っていない)
- リポジトリ標準の検証(selftest / lint / ビルド等)が段ごとに green
- 実装中に生じた分岐が該当段の PR 本文の `## 要確認` に列挙されている
- L5 を扱った場合: 母集団の L5 の各件が、閉じた(証跡つき)か、状況コメントつきで open に
  残っている。何もコメントされていない L5 を残さない
- §2a の構造の操作をした場合: 傘の sub-issues クエリが、想定した子を過不足なく返す。清算と判定した
  tracking Issue が closed になっている。昇格候補の各件が、昇格したか、見送りの理由つきで残っている

事例が積み重なったら `cases.md` を新設して追記する。サニタイズ規則は `agent-tooling-authoring` を参照。
