作業セッションで得た知見を、このリポジトリ(公開)に固定化するときの手順。「何に貯めるか」「どう配線するか」「どう書けば社内情報が漏れないか」の3点を毎回検討し直すのは無駄なので、ここにまとめる。

## 1. 器を選ぶ

| 知見の種類 | 器 |
|---|---|
| モデルが読んで従うべき判断知識(「こう考えろ」) | スキル。既存スキルの守備範囲に収まるなら、そのスキルの事例集(`cases.md` 等)に追記。新しい領域なら新設 |
| 機械的に検査・強制できる違反(「このパターンのファイル操作をしたら止める」) | フック(`config/claude/hooks/`) |
| ほぼ全セッションで常に必要な、ごく短い原則 | グローバル `CLAUDE.md`(コンテキスト税が全セッションにかかるので最終手段) |

判断の目安:
- 発動すべき場面を `description` のキーワードで具体的に言い切れるか(言い切れないなら発動精度が出ない)
- 本文が肥大しないか(不変の原則と、増え続ける事例は別ファイルに分離する)
- 機械的に検査できるなら、判断をモデルに委ねずフックに落とす方が確実

## 2. dotfiles への配線チェックリスト

1. `config/agents/skills/<name>/SKILL.md` を作成(frontmatter は `name` / `description` のみ。既存スキルの形式に合わせる)。事例集を持つなら同じディレクトリに `cases.md` 等の補助ファイルを置く。
2. `home/modules/agents.nix` に `home.file.".claude/skills/<name>/<file>".source = repoConfig + "/agents/skills/<name>/<file>";` を追加する。ファイル冒頭の機能一覧コメントにも1項目追記する(既存のフックの説明スタイルに合わせ、動機と設計意図を書く)。
3. `docs/claude/<name>.md` に設計ドキュメントを添える: 動機(どの失敗・不便から生まれたか)、器をスキルにした理由、内部構成の意図、運用(いつ・どう追記するか)。
4. **語彙に名指しする**(ADR-0000、`docs/agents/state-vocabulary.md`)。新しい skill は、自分が行う事象、または自分が前提を満たす事象を、`config/agents/*/vocabulary.json` の `carriers`(行う)か `gates`(前提を検査する機械)に `skill:<skill 名>` で 1 つ以上名指しする。本人に見せる状態なら `shown_by` でもよい。別リポジトリの対象に仕える skill は、`config/agents/vocabulary/external-objects.json` に対象の名前と skill 名を足す(対象の中身は書かない)。名指しできない skill は、仕えている skill への統合候補である。`scripts/vocab-graph-check --skills` が載っていない skill を列挙する。
5. home-manager switch して配備を確認し、新しいセッションで `skills 一覧` にあることと、想定した場面で自動発動することを確認する。

## 3. サニタイズ規則(正本 — 公開リポジトリに書く知見と、外部サービスへ送る文の両方。各スキルはここを参照し、重複させない)

書く先で規則が分かれる。公開リポジトリに書く知見は 3.1、カレンダー・メール等の外部サービスへ送る文は 3.2。

### 3.1 公開リポジトリに書く知見

このリポジトリは公開なので、社内固有の情報は一切載せない。知見を書くときは次を満たす:

- **固有名詞ゼロ**: 社名・製品名・機体名・プロジェクト名・リポジトリ名・人名・Issue/PR番号を書かない
- **URLゼロ**: 社内リソースへのURLは書かない(公式ドキュメントなど一般に公開された参照先は例外)
- **実物の持ち込み禁止**: スクリーンショット・実ファイルのコピー・実データを貼らない。構造を抽象化して書き直した再現のみ可
- **数値・識別子の出自を確認する**: 座標・アドレス・容量・パラメータ値などが社内の設計を特定しないか確認する(公開データシートに載っている値は可)
- **書き方は「抽象化した実話」**: 失敗の因果関係(何をしようとして、何が起きて、なぜ起きたか)はそのまま保存し、文脈だけを一般名詞(「組み込みファームウェアの手順書」「Webアプリのデプロイ手順」等)まで抽象化する。完全な作り話に差し替えると因果関係が歪みやすいので避ける
- **コミット前の最終確認**: 追記した差分を、固有名詞とURLの観点で読み直す。迷ったら書かない側に倒す

### 3.2 外部サービスへ送る文

カレンダー・メール・日程調整サービスなど、リポジトリの外へ出る文(件名・説明欄・本文・相手への連絡文)は、リポジトリ内に閉じた文章とは別物として扱う。3.1 と同じ判断だが、送り先がユーザーの実カレンダー・実メール・外部サービスである点が異なる。次の 4 項目を書かない(この一覧が唯一の正本で、他のスキルには再掲しない):

- プロジェクト名
- リポジトリ名
- 内部の Issue 番号
- 内部ファイルパス

汎用の言葉で要件が伝わるように書き直す。送り先が自分だけの private な外部サービスでも同じ。

機械検査: `bleep`(PreToolUse、matcher `Bash|mcp__.*`)が、MCP ツールの入力文字列に含まれる非公開リポジトリ・組織の語を denylist と照合して止める(配線は `docs/agents/public-publish-guard.md`)。検査の対象は denylist に載った語で、上の 4 項目すべてを検出する保証はない。この節の散文は検査の意図であり、検査が止めない項目や hook が動かない経路でのフォールバックである。

外部サービスへ文を送るスキルは、「外部サービスへ送る文は `agent-tooling-authoring` §3.2 に従う」と 1〜2 行で参照し、禁止項目を再掲しない。事例は `human-task-scheduling` の事例節にある。

## 4. スキル設計の作法

- `description` に発動キーワードを具体的に列挙する(日本語・英語の両方を含めておくと拾われやすい)
- 不変の原則(本文)と、増え続ける事例(別ファイル)を分離する
- 「〜するとよい」という推奨表現より、「〜するまで完成と呼ばない」のような検証可能な条件として書く方が実効性が高い

## 5. 散文の手順をスクリプトに昇格させるとき(ADR-543)

SKILL.md に書いたコマンド列(コードブロック)が繰り返し逐語で実行されて
いるなど、決定論的なスクリプト・gate へ昇格させる兆候が出たときも、
元の散文をコードブロックごと削除しない。散文は「このスクリプトが何を
しようとしているか(意図)」と「スクリプトが失敗した・想定外の入力に
出会ったときに LLM が代わりに従う手順(フォールバック)」として残す。
スクリプトの前後に短い説明を添える形でよい — 散文とスクリプトが同じ
skill の中で共存し、片方が壊れても他方で迂回できる状態を保つ。

このリポジトリのツール追加・改名では `docs/agents/tooling-conventions.md` を読み、責務名・正本・配布・互換入口を揃える。
