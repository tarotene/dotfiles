依頼者が「敵対的レビューをぶつけて」「先行例・文献を調査してから」と
毎回書かなくても済むように、Plan mode の設計判断には常に先行例接地の
結果を書く。詳細な設計動機と文献根拠は `docs/adr/0012-precedent-
grounding-over-prompted-adversarial-review.md` と
`docs/agents/precedent-grounding.md` を参照。

要点: 「敵対的に見よ」という抽象指示ではなく、設計判断ごとに
検証可能な 1 行を書く。批評は文脈を切った critic(copilot-plan-review
の lens A)が、その行を根拠に監査する。

## 1. 非自明な設計判断の見つけ方

「妥当な代替が他にも存在し、その中の一つを選んでいる箇所」だけを拾う。
典型例:

- 機構の選び方(hook / skill / CLAUDE.md / ADR のどれに置くか)
- 配置・分割の仕方(1 ファイル vs 複数、stacked PR の段の切り方)
- 命名・語彙(既存の `-gate`/`-guard`/`-allow` のような規約に沿うか)
- プロトコル・データ形式(JSON スキーマ、gate の判定条件)
- アルゴリズム・手法(研究的性質を持つ問題)

対象**外**: typo 修正、既存パターンをそのまま適用するだけの変更、
唯一の実装方法しかない配線作業。これらは Plan 全体を通じて非自明な
設計判断がなければ、節ではなく 1 行の免除で済む。

## 1a. Plan の外でも、推奨には先行例を引く

`AskUserQuestion` や grilling(`/grill-me`)の選択肢に、非自明な仕組みの選択として
`(Recommended)` を付けるときも、付ける前に先行例を 1 つ引く。Plan の `## 先行例との
対比` の外にある推奨は、`plan-precedent-gate` が検査しないので、引かないまま付けやすい
(2026-10-14、CI の許可リストで生え直しを止める案を根拠なしに推奨し、本人に「判断の根拠は
既存規範や外部知識に接地してほしい」と指摘された。先行例を読み直すと推奨が変わった。#783)。
先行例を引けないときは、選択肢の description に「先行例未確認」と書く。

## 1b. ADR や Amendment を計画に含めるとき

ADR・設計文書・skill のような決定成果物や、ADR への `## Amendment` を計画に含めるときは、
その `### 執行点` に挙げる、**`.md` でも `docs/` 配下でもない実体**を計画に書く。
`decision-colocation` は PR 作成時にしか働かないので、承認の後で執行点が無いと分かると、
承認済みの計画を差し替える申告が要る(2026-10-08、規約の文章だけで執行される決定に
Amendment を計画し、PR 作成の段で止められた。#763)。決定が規約の文章だけで執行される
ものなら、Amendment を計画せず、理由を Issue のコメントと既存の規約文書に残す選択肢を、
計画の段階で出す。

## 2. 出典の優先順位

`config/claude/CLAUDE.md`「発明する前に先行例を確認する」と同じ順:

1. 一次情報源(公式ドキュメント・upstream ソース/spec・学術文献)
2. 組織内の先行実装・過去の決定(この dotfiles リポジトリ内の
   `docs/adr/`・既存の hook/skill・過去の Issue/PR が最優先。同じ
   リポジトリ内で答えが見つかるのに外部を探すのは遠回り)
3. 二次情報(ブログ等)は 1–2 の裏取りがある場合のみ

外部の一次情報(論文・公式ドキュメント)を要する調査は、本線を止めない
ため `research` スキルで background agent に委譲する。検索クエリに
会社固有の識別子(社名・非公開プロジェクト名)を入れない。

文書を読むだけでは採否が分からない事実(対象の地域・条件で API が応答するか、
ビルドが通るか)は、一次情報を読んで済ませず、手元で 1 回実測する。書き方と
順序の規則は `technology-selection` スキル §1 を参照。

## 2a. 調査 agent の報告を、外部へ書き込む根拠にするとき(#967)

Slack などの外部チャネルを読む調査 agent の報告をもとに、他チームのリポジトリへ Issue や
PR を出す計画は、**書き込みの段の前に、報告の各行を一次情報で読み直す段を置く**。一次情報は、
元の投稿・資料、既存の Issue と文書である。報告は、検索した結果の要約であって、一次情報の
代わりにならない。

実例: ある計画で、書き込みの前に一次確認の段を 1 つ挟むと、報告の約 4 割が、既に文書に
書かれている・既存の Issue で足りる・報告自体が誤り、のいずれかだった。誤りは、「暫定確定」
と報告された値が撤回済みだった、「対立」と報告された論点が伝聞の 1 件だけだった、別の対象の
話の取り違え、存在しない Issue 番号、の形で出た。挟まなければ、誤った Issue が十数件、他チームの
リポジトリに立っていた。

計画の段は次の形にする。各行の判定を表にして、書き込みの段は「採用」の行だけを対象にする:

```markdown
- 段1: 報告の各行を一次情報で読み直す(元の投稿・資料・既存の Issue と文書を読み、各行を
  「採用 / 既に文書にある / 既存の Issue で足りる / 報告が誤り」に振る。読めなかった行は
  「未確認」とし、書き込みの対象にしない)
- 段2: 段1で「採用」とした行だけを書き込む
```

書式の検査(gate)は置かない。同じ誤りが再発してから、昇格を検討する(ADR-543 の昇格型)。

## 3. 節の文法

```markdown
## 先行例との対比

- D1: <採った設計判断を 1 文で>
  先行例: <著者/組織, タイトル, 公開日> <URL | リポジトリ内パス | #N> (取得 YYYY-MM-DD)
  差分: 一致 | 異なる — <理由>
- D2: <採った設計判断を 1 文で>
  先行例なし: <探した範囲(どこを・何のキーワードで・一次/二次のどちらまで)>
```

各 `Dn` には、上記に加えて `軸:`(`表現不可能|還元|検出のみ` のいずれか、
`先行例なし:` の枝でも必須)トークンが必要になる。技術・仕組みの選択
(ツール・ライブラリの採否、hook/skill の要否)を含む `Dn` は、外部依存の
新設・置換・撤去、新しい道具・単位の実装言語の選択、または戻せないもの
(データの損失・外部契約・人手の作業)が生じる選択のときに限り
`本命:`/`対抗馬:`/`外した候補:` も書く。書き直しの作業量・歴史的経緯は
理由にしない(technology-selection スキル §0)。軸の定義・duality 閉集合・
重い欄の詳しい書き方は `technology-selection` スキルを参照。重い欄を持つ
`Dn` にはさらに `既存手段:` 行(ADR-543)も必須になる — 書式は
technology-selection スキル §6 を参照。

gate は各 `Dn` ブロック(`- Dn:` 行とその下の従属行)内にトークンが揃っている
かだけを見る。従属行の順序・行数は検査しない(1 行に詰めても、順序を入れ替えて
も通る)。

- `Dn` は要求インベントリの `Rn` と同じ発想の ID。設計判断 1 つ = 1 ブロック。
  重複させない。
- `先行例:` 行には出典トークン(URL、リポジトリ内パス、`#N` の Issue/PR
  番号のいずれか)と `(取得 YYYY-MM-DD)` を必ず書く。取得日は捏造せず、
  実際にこのセッションで読んだ日にする。
- `差分: 一致` は先行例の判断をそのまま採った場合。`差分: 異なる` は
  先行例から意図的に外れた場合で、理由を書く(ADR-0012 の
  「Alternatives considered」と同じ役割)。
- `先行例なし:` は探したが見つからなかった場合。「探さなかった」の
  言い換えにしない — 実際に探した範囲を書く。
- 設計判断を含まない Plan は節そのものを省略し、代わりに 1 行:
  ```
  先行例: 該当なし — <理由(例: 既存スクリプトのバグ修正で設計判断を含まない)>
  ```

## 4. 批評者(lens A)が監査すること

`copilot-plan-review` の lens A は、この節の各 `Dn` について:

- 出典(リポジトリ内パスや Issue/PR は実際に読む)が主張を実際に支えて
  いるか
- `差分: 異なる` の理由が成立するか(単なる好みではないか)
- `先行例なし:` の探索範囲が、その設計判断の重要度に見合っているか
- 節に載っていない非自明な設計判断が Plan の他所に紛れていないか

を見る。**出典を示せない「もっと良い代替案があるかもしれない」型の
指摘は報告しない** — これは open-ended search を助長し、CLAUDE.md の
方針とも文献(ADR-0012)とも矛盾する。severity の目安は、理由のない
逸脱は MAJOR、引用した先行例と矛盾して要件を満たさなくなる場合は
BLOCKER。

## 5. アンチパターン

- データモデル案(ファイルを分けるか統合するか、外部キーで参照するか
  埋め込むか等)を比較するとき、「変更量が小さい」を推奨理由の主軸に
  使う。変更量・実装コストの大小は技術選定3軸のいずれにも属さない
  (`technology-selection` §6 参照)。まず「正規化(重複の有無)」「参照
  整合性を型で表現できるか、検査スクリプトに委ねるしかないか」で比較
  し直す — 後者が実質的な表現不可能性の軸になる。
- 出典のない一般論(「〜という考え方が一般的」)を `先行例:` の内容に
  書く。出典トークンが無ければ節の要件を満たさない。
- 二次情報(個人ブログ・まとめ記事)だけを出典にする。一次情報の裏取り
  がないなら `差分:` ではなく `先行例なし:` として扱う。
- このセッションで実際に読んでいない URL や、記憶からの推測で書いた
  取得日。読んだ範囲だけを書く。
- 「先行例: 該当なし」を、探すのが面倒だったときの言い換えに使う。
  免除は「設計判断そのものが存在しない」ときだけ有効。

## 6. 提出前の自己検査

プランファイルを書き終えたら、ExitPlanMode の前に必ず:

```bash
~/.claude/hooks/plan-precedent-gate --check <プランファイル>
```

`OK:` が出るまで修正してから抜ける。gate の deny を書式検査代わりに使わない
(deny 1 往復ごとに並列の Copilot レビューも巻き添えで走る)。
