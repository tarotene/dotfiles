# mail-lifecycle — 未裁定のメール項目が、状態をたどって必ず終わる

決定の記録: `docs/adr/0000-mail-lifecycle.md`(ADR-1256 の D2・D3・D5 を改める)
語彙の正本: `config/agents/mail-lifecycle/vocabulary.json`
実体: `crates/worklog/src/mail.rs`(書き込みの検査・畳み込み・sweep・控え)、`crates/worklog/src/main.rs`(`worklog mail`)
仕様と検査: `config/agents/mail-lifecycle/spec/`(Quint)、`home/tests/mail-lifecycle-spec.nix`、CI の `mail-lifecycle-spec` ジョブ

## 何を解くか

メールを読んで、推奨と下書きを用意したが、本人の裁定がまだ済んでいない項目(未裁定項目)は、
ページに並べただけでは、その後を追う仕組みが無い。裁定が戻らなければ、黙って残る。
`worklog` の `mail` kind は結論を残すが、「まだ終わっていない」を表さなかった。

この文書は、未裁定項目を閉じた状態機械で表し、すべての項目が終端に入る(取りこぼされない)ことを、
書き込み口の検査と模型検査で保証する仕組みを説明する。

## 状態と出来事

状態は保存しない。vault の当日ノートの `[mail]` 行を出来事とみなし、同じ鍵の行を順にたどって決める
(event sourcing)。表の正本は `vocabulary.json` 1 枚で、`worklog` は `include_str!` で、Quint の仕様は
`spec/vocab.jq` で、同じ表を読む。

| 状態 | 種別 | 意味 |
|---|---|---|
| `awaiting` | 未了 | 本人の裁定待ち(推奨や下書きを見せた) |
| `decided` | 未了 | 裁定済みで、反映がまだ |
| `closed` | 終端 | 終わった(返信を送った・正本に反映した・何もしなくてよい) |
| `dismissed` | 終端 | 本人が断った・見送った |
| `stale` | 終端 | 返事が無いまま期限が来て、機械が閉じた |
| `superseded` | 終端 | 別の追跡先(Issue・カレンダーの期限・同じスレッドの新しい項目)へ移した |

出来事(閉語彙。`by` は書く主体):

| 出来事 | 遷移 | by |
|---|---|---|
| `read` | (新規) → closed | agent |
| `draft` | (新規) → awaiting | agent |
| `ask` | (新規) → awaiting | agent |
| `decide` | awaiting → decided | person |
| `apply` | awaiting / decided → closed | agent |
| `pass` | (新規) / awaiting / decided → dismissed | person |
| `remind` | awaiting / decided → 同じ状態 | machine |
| `move` | awaiting / decided → superseded(移し先 `to:` が要る) | agent |
| `stale` | awaiting / decided → stale | machine |

`machine` の出来事(`remind`・`stale`)は `worklog mail sweep` だけが書き、`worklog add mail` は拒否する。

## 行の形と鍵

```text
- 09:12 [mail] ask: 要旨 [gmail:<スレッド>/<メッセージ> due:2026-11-28]
- 09:13 [mail] draft: 要旨 [linkedin:<会話>/20261029T2307]
- 09:14 [mail] move: 要旨 [gmail:<スレッド>/<メッセージ> to:<owner/repo#N | cal:YYYY-MM-DD | mail:<鍵>>]
- 09:15 [mail] read: 約 490 件を読んだ [none]
```

- 鍵は `<媒体>:<スレッド>/<受信>`。受信は Gmail ならメッセージ ID、メッセージごとの ID が取れない媒体は
  画面に出る受信日時を分まで(`YYYYMMDDTHHMM`)。同じ受信を読み直しても、鍵が同じなので項目は増えない。
- 同じスレッドの未了は常に 1 つ。新しい受信を `read`・`draft`・`ask` で開くとき(`read` で即座に終端になる
  受信でも)、`worklog` は同じ命令の中で、古い未了を先に `move`(移し先 `to:mail:<新しい鍵>`)で移す。
  未記録の鍵への `pass` では移さない(本人が新しい受信を見送っても、古い未了の判断は残す)。
- 受信の新旧は、画面の受信日時(固定幅)は字句順、Gmail のメッセージ ID は長さ、字句順で比べる。Gmail の ID が
  時刻順に増えることは確かめていない(未確認)。
- 並行して 2 機体が同じスレッドの未了を 2 つ作って合流したら、畳み込みは受信の古い方を移したとみなす。
  遅れて届いた古い受信は、開いた直後に自分が移される(新しい受信の未了が残る)。
- `[none]` は件数の集計の行で、`read` だけ。項目にならない。
- 要旨は結論だけ(120 文字まで)。`@`・`http`・角括弧を含められない(ADR-1256 D4)。

## 時間の決まり

`vocabulary.json` の `timers`(7 / 7 / 3)で、`worklog mail sweep` が決める。判定は純関数で、
朝の机が結果を本人に見せる。

- 最後の出来事から 7 日たった未了、または期限の 3 日前の未了に `remind` を書く。
- `remind` が今日より前にあり、さらに 7 日たった、または期限を過ぎた未了に `stale` を書く。
  **`stale` の前には、必ず(最後の実質的な出来事より後の、今日より前の)`remind` がある。**
- 実質的な出来事(`decide` など)は、時計と `remind` を数え直す。
- 同じ日に `sweep` を何度回しても、書く行は増えない。
- 返事の無い項目は、最長 14 日で終端に入る。

## 終端の控え

ノートは本人も Obsidian で編集でき、LiveSync で同期される。終端の行を手で消すと、畳み込みは未了に戻る。
追記専用の記録の外にある操作は防げないので、**検出する**。

- `add` と `sweep` は、終端の行を書いた後に、機体ごとの控え `~/.local/state/claude/worklog/mail-terminal`
  (JSON Lines。環境変数 `WORKLOG_STATE_DIR` で置き場を変えられる)にも、鍵・終端・行の本文を書く。
- `worklog mail check` と `mail open` は、控えにあるのにノートに同じ終端が無い鍵を「終端の行が消えた」と出す。
  `sweep` はその項目を再通知しない。
- 控えにある鍵への、開く出来事(`read`・`draft`・`ask`)は「記録済み」にする。読み直した受信を未記録と見て
  開き直すと、消された終端が通常の未了に戻ってしまう(仕様の `handled`)。
- 本人は `worklog mail restore <鍵>` で控えの行を書き戻すか、`worklog mail forget <鍵>` で控えから捨てる。

## 使い方

```text
worklog add mail "<出来事>: <要旨> [<媒体>:<スレッド>/<受信> [due:YYYY-MM-DD]]"
worklog mail open                  # 未了の一覧(状態・鍵・最後の出来事からの日数・期限・要旨)
worklog mail check                 # 食い違いの一覧。あれば exit 1
worklog mail sweep [--dry-run]     # remind と stale を書く(書いた行を出す)
worklog mail restore <鍵> | forget <鍵>
```

書く順序の規約: **記録を先に書き、Gmail の下書きを後で作る。** 記録にあって下書きが無ければ、次の机で
作り直す(下書きが先で記録が無いと、取りこぼしを検出できない)。

## 仕様と検査

未裁定項目の寿命は `spec/lifecycle.qnt`(Quint)に書き、TLC で検査する。遷移の可否の正本は語彙 JSON で、
仕様は検査のたびに `spec/vocab.jq` で JSON から生成したモジュールを読む(写しをコミットしない)。

| ファイル | 内容 |
|---|---|
| `spec/lifecycle.qnt` | 参加者(エージェント・本人・掃引)、共有記憶(機体ごとのノートの行の写し、LiveSync の遅れ、Gmail の下書き、機体ごとの終端の控え)、環境の動作(落ちる・行の削除・日の進み)、性質 |
| `spec/scenarios.json` | 検査の表。規則(有効 / 1 つずつ無効)と環境の組と、期待(通る / 反例が出る) |
| `spec/vocab.jq` | 語彙 JSON から、仕様が import する `vocab.qnt` を作る |

実行は `nix build .#checks.x86_64-linux.mail-lifecycle-spec -L`(`home/tests/mail-lifecycle-spec.nix`)。
表の 1 行が 1 つの derivation で、CI の `mail-lifecycle-spec` ジョブ(`.github/workflows/ci.yml`。語彙・仕様・
`worklog` の crate が変わった PR と main への push で回す)が回す。期待が「反例が出る」の行は、規則を 1 つ外した
ときに意図した性質だけが破れることを示す回帰テストで、規則が効かなくなれば赤になる。語彙の遷移ごとに、
仕様がその遷移を起こせる(到達可能)ことも確かめる(`cover`)。

**仕様と実装の一致。** 仕様の探索(`quint run`)が出す軌跡(ITF。nix の `mail-lifecycle-itf`)の各状態にある、
機体ごとのノートの行の写しを、`crates/worklog/tests/itf_replay.rs` が実装の `fold` に通し、項目ごとの状態と
食い違いの数が仕様の畳み込みと同じであることを確かめる(同じジョブの後段)。この突き合わせは、実装が
仕様と違う規則を持っていた 2 か所(`pass` で古い未了を移すか、遅れて届いた古い受信を移す向き)を実際に見つけた。

性質と、検査の対応:

| 性質 | 内容 | 検査 |
|---|---|---|
| S1 | 終端の状態からは戻らない(追記専用の記録の上) | 不変条件 `s1` |
| S2 | 鍵ごとの終端は 1 つ | 不変条件 `s2` |
| S3 | スレッドごとの未了は高々 1 つ | 不変条件 `s3` |
| S4 | `stale` の前には、同じ鍵の `remind` が、より前の日にある | 不変条件 `s4` |
| S5 | 同じ受信を読み直しても、状態は変わらない | 不変条件 `s5` |
| S6 | 仕様が起こす遷移はすべて語彙にあり、語彙の遷移はすべて起こせる | 不変条件 `s6`、`cover` |
| S7 | 手で消された終端の行は、同じ機体の `check` が必ず出す。出した項目に掃引は書かない | 不変条件 `s7`・`s7b` |
| L1 | 開いた項目は、いずれ終端に入る(本人が答えなくても) | 活性 `l1` |
| L2 | 届いた受信は、いずれ項目になる(または記録済みと判定される) | 活性 `l2` |
| L3 | 下書きを作る前に落ちた項目は、いずれ作り直されるか終端に入る | 活性 `l3` |

活性は、日が進み、同期が届き、机が `sweep` を回し、読む側が動く、という公平性の仮定のもとで検査する。
本人の行動には公平性を置かない(答えなくても終端に入ることを検査する)。

検査の範囲(有界の模型): 項目 1〜4 件(スレッド 2 つまで)、機体 1〜2 台。時間つきで 2 機体・2 件以上は、状態が
数百万に増えて 10 分で終わらなかったので、行ごとに絞っている(時間つきの 2 機体は 1 件、4 件は時間なし・1 機体)。
実時間の閾値(7・7・3 日)は、仕様では小さい値(`scenarios.json` の `REMIND_AFTER` など)に置き換えていて、
語彙の `timers` を読まない。`timers` を変えても検査は追随しない(実装の `sweep` は `timers` を読み、単体試験が
7・7・3 を確かめる)。機体の間で行が届く順が違うと、畳み込みの最終状態が食い違いうる(収束は性質に入れていない)。
`s3` は、畳み込みに暗黙の supersede を入れた形で検査している(新しい項目を開いたとき、書き手が古い未了を
見ていなかった行で働いたら破れる)。

## 保証しないこと(限界を認める)


- 別の機体で書かれた終端の行を手で消した場合は、その機体で `check` を走らせたときにだけ見つかる
  (控えは機体ごと)。
- 控えそのものを消した場合は検出できない。
- 本人が未了の行を手で消すと項目は見えなくなるが、同じ受信を次に読めば開き直される(L2)。
- 要旨に書かれた相手の名前は検出できない(ADR-1256 D4)。

## 壊れ方

- 書き漏れ: 検出しない。取りこぼした受信は、次に読んだときに項目になる。
- ノートの行が解析できない(旧い文法・手書きの崩れ): `check` が「解析できない行」として出す。
  切り替え日(`2026-10-30`)より前のノートの `[mail]` 行は旧い文法なので畳み込まない(`list` では読める)。
- 時刻は JST 固定で、`TZ` に依存しない。試験用に `WORKLOG_NOW`(unix 秒)で固定できる。
