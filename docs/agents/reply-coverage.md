# reply-coverage — 相手のいる会話への返信が、相手の未決の依頼すべてに答えているかを検査する

設計の判断: `docs/adr/1585-reply-coverage.md`(#1577)。実装: `crates/reply-coverage`。

## 何のためか

返信を下書きするとき、最新の 1 通だけを読んで書くと、会話の最初に相手が出していた依頼(日程の候補・質問・書類の依頼)を取りこぼす。
取りこぼすと、相手は「答えてもらえていない」と受け取り、話の流れが変わる(#1577。紹介会社の電話の日程候補に触れず、質問にだけ答えた)。

原則: **相手のいる会話に返す文は、会話の始めからの、相手の未決の依頼すべてへの応答として書く。**
会話の全文を読み、依頼を逐語で列挙し、各項目に「答える / 断る / 保留(理由と時期)/ 依頼でない」を付けてから書く。
前の返信が依頼を取りこぼしていたなら、今回答えるときに、ずれた・遅れたことへ軽く触れて詫びる。

## 使い方

```text
reply-coverage import --id <媒体:id> --file <ファイル> [--format raw|normalized] [--message-id <id>]…
reply-coverage import-gmail --file <get_thread の結果の JSON>
reply-coverage check  --thread <媒体:id> --draft <ファイル> [--model <m>] [--me <手がかり>]
reply-coverage verify --thread <媒体:id> --draft <ファイル>
reply-coverage bench  --cases <dir>… [--variants m1,m2] [--repeat N] [--me <手がかり>]
reply-coverage sweep
```

1. 会話の全文を保存する(`import`)。会話の id は `<媒体>:<会話を指す印>`(`gmail:<スレッド id>`、`linkedin:<会話の印>`)。
   整形していない会話(ブラウザの snapshot など)は `--format raw`(既定)で取り込み、`check` の `--me` に、本人の発言の見分け方
   (たとえば「名前が `<本人の名前>` の発言が本人」)を渡す。`## them|me|other <時刻>` の見出しでメッセージを区切った形は `normalized`。
   **Gmail の会話が大きいとき**(`get_thread` の結果が数万字を超えるとき)は、ツールの結果がファイルに保存され、PostToolUse の hook は
   応答を受け取れない(2026-11-15 に、8 通で約 14 万字・16 通で約 59 万字の会話で確かめた)。ファイルの場所は、ツールのエラーの文面に
   出る。`reply-coverage import-gmail --file <そのファイル>` が、hook と同じ関数で正規の形に直して保存する(エージェントが書き写さない)。
2. 最終稿(`ja-polish` を通したあと)をファイルに書き、`check` を実行する。相手の依頼の一覧と、各依頼の処分(答える・断る・
   保留・先に答え済み・取り下げ済み・★未回答)が出る。終了コード 0 が合格、1 が不合格、2 が検査できなかった(通信・認証の失敗など。
   「合格」にはならない)。
3. 不合格なら、未回答の依頼に答える(断る・保留する)一文を追加して、もう一度 `check` する。
4. `verify` は、記録だけを引いて、その最終稿が合格しているかを答える(LLM は呼ばない)。下書き作成ゲート(段2)と、
   裁定ページの生成(段3)が、同じ照会を呼ぶ。

## 検出と照合

`check` は、会話の全文と下書きを、文脈を切った新しい Claude(`claude -p`)に渡す。ツールは渡さない(`--tools ""`)ので、会話に紛れた
指示に乗っ取られても、読み書きも実行もできない。出力は JSON スキーマ(`crates/reply-coverage/src/detect.rs` の `SCHEMA`)で縛る。

モデルの出力は信用せず、Rust 側で次を照合する(`detect::judge`)。

- 依頼の引用が会話の全文に逐語でない → その依頼を捨てる(存在しない依頼に、人は動けない)。
- 「答えた・断った・保留した」の根拠が下書きに逐語でない → 未回答に戻す。
- 「先に答え済み・相手が取り下げた」の根拠が会話の全文に逐語でない → 未回答に戻す。
- 前の返信が取りこぼしていた依頼(`late`)に今回答えるのに、詫びの文が下書きに逐語でない → **助言**(報告に出すが、合否に入れない)。
  本人の言葉は「軽く詫びてもよい」で、必須ではない。しかも `late` は検出(LLM)の判断で、実物の会話の計測で、保留(「確認に一日ほしい」と
  伝えた返信)を「取りこぼした」と解釈する誤りが出た。誤りで正しい下書きを止めるより、助言にした(段4。ADR の Amendment)。

合格は、未回答が 1 件もないこと。依頼が 0 件(お礼だけの会話)なら合格。
**照合で防げないもの**: 検出が相手の依頼を挙げ損ねる(見落とし)。精度は `bench` で測る。

## 止める口と逃げ道(段2)

- **会話の全文の保存**(PostToolUse の規則 `reply-thread-snapshot`): Gmail の `get_thread` の応答から、会話の全文を保存する。
  エージェントに書き写させない。メッセージの id の索引を持ち、返信の `replyToMessageId` から会話を引く。
- **下書き作成ゲート**(PreToolUse の規則 `reply-coverage-gate`): Gmail の `create_draft`・`update_draft`・`reply` のうち、
  返信先(`replyToMessageId`)を持つ呼び出しを、`verify` が通らなければ拒否する。拒否の文面は、次の一手(会話を取得する、
  `check` を実行する、未回答の依頼に答える)を書く。返信でない新規の下書き・送信・転送は対象外。記録を引くだけで LLM は呼ばない。
- **通知メール起点の会話は、ブラウザで読んだ会話の取り込みを要する**(F70、2026-11-19)。保存した会話の相手のメッセージの差出人が、媒体
  (LinkedIn・LAPRAS・Findy)の通知メールのもの(`verify::NOTIFIER_MARKERS`)で、24 時間以内に Gmail 以外の会話(ブラウザの
  `import`)の保存がないときは、`verify`(下書き作成ゲートと裁定ページの生成が呼ぶ)が `NotificationOnly` で止まる。通知は、同じ件名でも別の
  スレッドに分かれ、本人が媒体で送った文は Gmail に残らない(通知のスレッドだけで組んだ下書きが検査を通ったが、同じ会話で本人が面談を見送り、相手が承知していた)。
  どのブラウザの会話が、その通知に当たるかは、機械では結びつけない(会話の印を通知から導けない)ので、「24 時間以内のブラウザの取り込みが 1 件でもあるか」だけを見る
  (取り込み忘れを塞ぐ。取り違えは塞がない: 検出のみ)。
- **`reply-coverage ready --thread <媒体:id>`**(#1620): 返信案を作る・本人に見せる**前**の確認。会話の全文が保存済みで 24 時間以内か(通知メールの会話は、上の
  取り込みもあるか)。0=読み込み済み、1=足りない(次の一手を書く)。下書きの検査(`check`)より前の段で、下書きは不要。
- 有効にした機体(`~/.config/dotfiles/reply-coverage` の目印がある機体。`home/modules/reply-coverage.nix` が既定で置く)だけで働く。
  目印がなければ何もしない。判定不能(状態の置き場がない、入力の形が違う)は、拒否に変えず通す。
- **逃げ道**: `SKIP_REPLY_COVERAGE_GATE=1`(セッションの環境変数)。検出が使えない(通信・認証の失敗)とき、本人が決めて使う。
- 順序: 本文を書く → `ja-polish` → `reply-coverage check`(最終稿のファイル) → 下書きの作成。最終稿の sha で、両方のゲートが照合する。
- 既知の穴: Codex の MCP 名(`mcp__codex_apps__gmail_…`)は、規則の一致が未確認(ja-polish ゲートと同じ穴)。Slack の下書きは、入力の
  スレッド返信を示す欄が未確認(この機体に Slack の MCP がない)なので、規則に載せていない。ブラウザの媒体・日程調整・招待・GitHub は、
  搬送路が違い、段3 で扱う。

## 搬送路の一覧(媒体ごと)

原則(共有 AGENTS.md「相手のいる会話へ返すときは…」)は媒体を問わない。会話の取得と、止める手段は媒体ごとに異なる。

| 媒体 | 会話の取得 | 止める手段 | 機械で止められない穴 |
|---|---|---|---|
| Gmail の返信 | `get_thread` の応答を hook が自動で保存(段2) | 下書き作成ゲート(`reply-coverage-gate`、段2) | Codex の MCP 名は未確認。`send_message`・`forward` は対象外 |
| LinkedIn・LAPRAS・Findy のメッセージ | `browser_snapshot` の `filename` で保存し、`reply-coverage import` で取り込む | 裁定ページの生成(`build.sh` が `verify` を呼ぶ。形式 7) | 代行送信の入力(`browser_type`)は、どの hook も見ない。確認の表(依頼と処分)と本人の確認が代わり |
| チャット(`AskUserQuestion`)で返信案を本人に見せる段 | 上の媒体のとおり(`reply-coverage ready` で、見せる前に確かめる) | **未実装(意図あり)**。`AskUserQuestion` の入力から本文を取り出す機構(hook-router の規則)は技術的には作れるが、「返信案」の語に反応する規則は、返信と無関係な質問を止める誤検出が大きい。手順書(`ready` を見せる前に通す)だけが担う | 手順書だけ(検出のみ)。#1620 は、この機構が入るまで open |
| Slack | 未実装(意図あり) | 未実装(意図あり。入力のスレッド返信の欄が未確認) | — |
| 日程調整・「いつ空いてる?」の返答 | 依頼が載っていた会話の全文を読む(`slot-availability` 手順 1-0) | 返信の下書きは上の媒体の手段。調整さんへの書き込みは止める手段がない | 手順書だけが担う(検出のみ) |
| カレンダー招待への返答(`respond_to_event`) | 招待の説明欄と他の出席者のコメントを読む(`slot-availability`) | ない(下書きを経ない) | 手順書だけが担う(検出のみ) |
| GitHub のレビューのスレッド | `resolve-pr-threads` が、スレッドの全コメントを取得して表示する(100 件まで) | ない(返信の書式は固定の 3 つの型) | 全コメントを読む手順と、最後のコメントが他者のスレッドを先に扱う規則だけ |
| GitHub の Issue・PR のコメント | `gh issue view --comments` など、全件を読む | ない | 原則だけ(検出のみ) |
| esa・Claude Docs・artifact のコメント | 全件を読む | ない | 原則だけ(検出のみ) |

## 状態の置き場(`~/.local/state/claude/reply-coverage/`)

- `threads/<id>.json`: 会話の全文(`id`・`fetched_ts`・`format`・`message_ids`・`text`)。有効期限は 60 日。
- `records.jsonl`: 検査の記録 1 行 1 件(`thread`・`thread_sha`・`draft_sha`・`verdict`・`model`・`asks`・`unanswered`・`apology_missing`)。
- 権限は、ディレクトリが 0700、ファイルが 0600。Git の外・vault の外(vault は LiveSync でスマホに同期されるため、
  第三者のメッセージの全文を置かない。ADR-1256 D4)。正本は媒体(Gmail など)のままで、保存は複製にすぎない。別の機体では取り直す。
- 環境変数 `REPLY_COVERAGE_STATE_DIR` で置き場を差し替えられる(テスト用)。

`verify` の判定: 保存した全文があり、24 時間以内であり、その全文の sha と最終稿の sha の両方が一致する合格の記録が、最新である。
最終稿を 1 字(空白の違いを除く)直す、または会話を取り直して中身が変わる(相手の新しい返信)と、合格は引き継がれない。

## 見本と計測(`bench`)

見本は 1 件 1 ディレクトリ: `conversation.thread`(会話の全文)・`draft.draft`(下書き)・`expected.json`
(`{"verdict":"pass|fail","unanswered":["引用の一部",…]}`)。拡張子を `.md`・`.txt` にしないのは、擬似メッセージが
文書として書き直し(`ja-polish`)の対象にならないようにするため。

- **架空の見本**: `crates/reply-coverage/tests/fixtures/`(11 件。日程候補の抜け、複数の質問の 1 つの抜け、書類の依頼の抜け、
  先に答え済み、取り下げ済み、詫びの有無、お礼だけ、英語の長い会話の中ほどの依頼、会話に紛れた検査係への指示)。各見本の
  `canned.json` は、正しい検出が返すはずの出力で、`cargo test` が、判定・引用の逐語・偽りの検出が通らないこと(負例)を確かめる。
- **本物の見本**: 個人の会話は、非公開の person-state リポジトリに置き、`reply-coverage bench --cases <dir>` か、環境変数
  `REPLY_COVERAGE_PRIVATE_CASES` で指す。公開側のコード・文書・出力に、本物の本文と相手の名前を出さない。表に出すのは、
  見本の id と判定だけ(テストが確かめる)。
- 表の物差し: 判定の一致、不合格の見本で期待の未回答を挙げられた数(再現)、合格の見本の誤検出、失敗、平均秒。
  何も書き換えず、記録も残さない。

### 計測の結果(2026-11-15、`bench --repeat 3`、見本 25 件 × 3 回 = 75 回)

実物の見本 14 件(非公開リポジトリ。紹介会社の担当者との実際のやり取りから作った。通る 9・落ちる 5)と、架空の見本 11 件。表に出る数値だけを書く
(本文・相手の名前は、非公開側にだけある)。

| モデル | 判定の一致 | 不合格の見本の検出(再現) | 合格の見本の誤検出 | 平均秒 |
|---|---|---|---|---|
| `claude-sonnet-5-5` | 73/75 | 28/30 | 0 | 5.7 |
| `claude-haiku-5-5` | 72/75 | 27/30 | 2 | 8.2 |

- **既定のモデルは `claude-sonnet-5-5`**。誤検出が 0 で、速い。誤検出(正しい下書きを止める)は、本人の作業を止めるので、再現率より重く見た。
  `claude-haiku-5-5` は、同じ見本で誤検出が 2 件あった。
- **指示文の改訂が効いた。** 改訂前の同じ実物の見本(14 件を 1 回)では、2 モデルとも判定一致は 10/14 で、合格の見本の誤検出が 4 件あった。原因は 3 つだった:
  (1)「ご一読ください」のような、返信で触れなくてよい行動の依頼を、未回答にした。(2) 保留(「確認に一日ほしい」)を、見落とした依頼と解釈し、`late` にして詫びを求めた。
  (3) 会話の中で、すでに応じ終えた依頼を、未回答にした。指示文に、返信の文面で応えるべきものだけを挙げること、保留は応じたものとして扱うこと、
  すでに応じ終えた依頼を未回答にしないことを追加した。
- **残る誤り**: 不合格のはずの見本を通した(見落とし)が、`claude-sonnet-5-5` で 2/30。実際の返信から「レジュメを添付します」の行を消した負例
  (`m02`)で、相手の依頼が「作成を進めていただければと存じます」という穏やかな言い方のため、依頼として挙げない回があった。指示文を「返信で触れなくてよい行動の依頼は
  挙げない」と絞った代償で、依頼の言い方が穏やかなものは見落とす可能性がある。**この検査が保証するのは、答え漏れの検出が増えることであって、見落としがゼロになることではない**。
  残りは、裁定ページ・代行送信の確認の表で、本人が見る(検出のみ)。
- 同じ入力でも、判定は実行ごとに揺れる。揺れは `--repeat` で数える。改訂後の 75 回で、実行ごとに判定が変わった見本は、`claude-sonnet-5-5` で 1 件(`m02` のみ)、`claude-haiku-5-5` で 3 件だった。
- 実物の見本は、本人が実際に送った返信(通る見本)と、そこから行を消して作った負例なので、答え漏れなく書いたものの標本であり、依頼の言い方も紹介会社の定型に偏る。
  ほかの種類の会話(友人、Slack、GitHub)での精度は、未計測。

実物の見本の置き場と作り方は、非公開リポジトリの見本のディレクトリの README にある(公開側には、見本の id と判定の集計だけを書く)。
