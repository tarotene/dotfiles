# human-task-scheduling — 電話等ハンドオフ作業をカレンダーに反映する判断知識

## なぜこれが必要か

外部窓口(業者・医療機関等)への確認電話は Claude が代行できず、営業時間という
時間帯制約もある。従来はトークスクリプトを Markdown に書いてユーザーに渡す
だけで完了とみなしていたが、これは「ユーザーが後で自発的に思い出して営業時間
内に実行する」ことに賭ける設計であり、失念のリスクを Claude 側の作業として
解消できていなかった。

## 器をスキルにした理由

「営業時間とユーザーの空き時間の重なりを探し、衝突しない枠を選ぶ」は判断を
要する作業であり、機械的なフックでは代替できない(空きカレンダーの解釈には
文脈判断が要る — 「予定なし」がそのまま「対応できる」を意味するとは限らない)。
CLAUDE.md への格上げも検討したが、発動条件を「電話等のハンドオフ作業」という
キーワードで言い切れるため、全セッション常時発火のグローバル原則にする必要は
ないと判断した。

## 内部構成の意図

手順は5段階(営業時間の洗い出し→空き時間の突合→予定作成→書き込み先の
確認→前提条件の明記)。

- 4番目(書き込み先の確認)は、確定した予定を予定データへ書く PR で出し、
  射影カレンダーへ反映させる。Claude が提案した予定を無条件に個人の
  主カレンダーへ直書きしない、という安全側の判断を明文化したもの。
- 5番目(前提条件の明記)は、依存関係のあるタスクを早まって実行させないための
  転記。

「外部サービスへの書き込みはサニタイズ対象」節は、規則の本体を持たず、
`agent-tooling-authoring` §3.2「外部サービスへ送る文」(禁止項目の一覧の正本。
`music-performance-planning`・`venue-search`・`slot-availability` も同じ節を
参照する)への参照だけを置く。カレンダーの説明欄にプロジェクト名や Issue 番号を
書いたところ、外部カレンダーサービス送信のガード機構に private リポジトリ
参照として検知され、書き直しになった実例が直接の根拠で、その事例はこの
スキルの事例節に残す。この検知は「送信先が社外/自分のプライベートな外部
サービスであっても、リポジトリ固有の識別子を含めば止まる」という設計であり、
サニタイズ規則がリポジトリへのコミット以外の外部送信経路にも及ぶ運用に
なっていることを可視化した。これを受けて、正本の範囲を §3.2 として明示した。

## 運用

新しい失敗事例(サニタイズ漏れの新パターン、営業時間データの誤認識等)が
出たら、`SKILL.md` の事例節に追記する。
