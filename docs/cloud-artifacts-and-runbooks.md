# クラウド成果物の命名規則と、人手を要する手順書(runbook)の書式

`docs/personal-cloud-projects.md` は GCP プロジェクト名・OAuth 同意画面名を
`<tool>-<github-username>` などの決定論的な導出規則に落とし込んだ。その
おかげで「都度考えるには実害に対して決定コストが割に合わない」命名判断が
機械的な導出になっている。ただしその規則の対象は GCP 側の命名に限られる。
個人がクラウド上に作る成果物は GCP だけではなく、人手を要する GUI 操作を
含む手順書の書き方も実例ごとにばらついている(#505)。この文書は同じ型で、
次の 2 つを 1 か所に定める。

1. GCP 以外のクラウド成果物(Calendar・Drive・チャット等)の命名規則
2. 人手を要する手順書(runbook)の書式

この文書は規則の置き場であり、個々のツール固有の値(実際の表示名・フォルダ名・
識別子)は書かない。値は導出規則から、そのツールを持つ側のリポジトリで
導出する。

## 1. クラウド成果物の命名規則

### 1.1 共通の語彙

`personal-cloud-projects.md` の `<tool>`(ツールのバイナリ/コマンド名、
小文字・ハイフン区切り)と `<github-username>` をそのまま共有する。成果物の
種類ごとに別の語彙を発明しない。「どのツールが作った成果物か」を名前から
辿れることを最優先にする。

### 1.2 導出規則

| 成果物 | 規則 |
|---|---|
| 射影専用カレンダーの表示名 | `<tool>`。人間が手で予定を入れるカレンダーと混ざらないよう、ツールが書き込む専用の 1 本にし、目的の説明を表示名に足さない(説明はカレンダーの説明欄に書く) |
| 射影されたイベントの件名 | 接頭辞マーカー 1 個 + 本題。マーカーは全角角括弧 `【<状態語>】` で、状態語は 1.3 の閉語彙から選ぶ |
| Drive のフォルダ | ルートは `<tool>`、その下の用途別は `<tool>/<purpose>`。`<purpose>` は小文字・ハイフン区切り |
| チャンネル・スペース等の名前付き場所 | `<tool>-<purpose>`(小文字・ハイフン区切り)。プラットフォーム固有の文字種・長さの制約がこれと衝突する場合は、制約を優先して最小限だけ崩し、その理由をその場所の説明欄に残す |
| 説明欄・メモ欄 | 1 行目に作成元のツール名(`<tool>`)と、手順書または規則へのポインタを書く。名前だけでは辿れない由来を残すため |

規則に当てはまらない新しい種類の成果物が現れたら、その場で都度命名せず、
この表に行を足してから命名する(表が増えることが、判断が閉じていく進捗である)。

### 1.3 イベント件名のマーカー(状態語の閉語彙)

角括弧マーカーは、特定ツールの設定ファイルや docstring に個別に散らばらせず、
ここに登録した状態語だけを使う。

| 状態語 | 意味 |
|---|---|
| `【調整中】` | 日時や参加者がまだ確定していない仮の予定 |
| `【勉強期間】` | 試験に向けた学習期間。日付範囲を占めるが、特定の時刻には縛られない |
| `【試験本番】` | 試験当日。動かせない本番のイベント |

上の 3 語は、この文書ができる前から個別のツールの設定ファイルに散らばって
いた既存の使用例を集約したもので、新しく発明した語ではない。

状態語を足すときは、既存の語と意味が重ならないことを確認してから表に追記する。
マーカーは件名の先頭に 1 個だけ付け、複数並べない(状態は 1 つに決まる)。

## 2. 人手を要する手順書(runbook)の書式

人間にしかできない操作(ブラウザ GUI・資格情報の発行・実機での確認)を含む
手順書は、提示する場所(チャット・Issue・PR 本文・docs)を問わず、共有
`AGENTS.md`「人に依頼する手順は、場所を問わず『フル』で書く」に従う。この節は
その 5 要素(遷移経路・正確な名称・入力値・完了確認・根拠)を、docs に置く
手順書として構造化したときの書式を定める。

### 2.1 構成

```markdown
# <手順書のタイトル>

<1〜2 文: 何を達成する手順か、いつ使うか>

## 前提
- <必要な権限・事前に済んでいること>

## 値
| 項目 | 値 | 変更 |
|---|---|---|
| <項目名> | <導出済みの具体値> | 可 / 不可(<理由>) |

## 手順
1. [機械] <コマンドを実行する>
   - 完了確認: <出力に何が出れば完了か>
2. [人] <画面名> → <メニュー名> → <ボタン名> を押す
   - 入力: <項目名> = <値>(それ以外の項目は触らない)
   - 完了確認: <画面に何が表示されれば完了か>
   - 根拠: <出典の URL または既存 runbook・Issue 番号> (取得 YYYY-MM-DD)

## うまくいかないとき
- <症状>: <原因と対処>

## 根拠
- <手順全体の出典>
```

### 2.2 ルール

- **機械と人を書き分ける。** 各ステップの先頭に `[機械]`(コマンドや API で
  実行でき、エージェントが代行できる)か `[人]`(GUI・資格情報・実機が要る)
  を付ける。`[人]` のステップはエージェントが代行しない。連続する `[機械]` は
  1 つのコードブロックにまとめてよい。
- **`[人]` のステップは 1 ステップ 1 操作にする。** 「プロジェクトを作成して
  アカウントを発行する」のように複数の画面遷移を 1 行に畳まない。
- **値は「値」表に導出済みの具体値で出す。** 「何でもいい」「適宜」と書かない。
  値を決められない項目は、`personal-cloud-projects.md` や 1.2 の導出規則から
  具体値を出してから表に書く。
- **変更可・不可を明記する。** 作成後に変更できない値(GCP のプロジェクト ID
  など)は「不可」とし、理由を書く。後から変えられる値と、やり直しが要る値を
  読者が区別できるようにする。
- **確かめられていない画面名・項目名は推測で書かず `未確認` と書く。** 出典が
  取れていない記述を、確定した手順に見せない。
- **機密の値は本文に書かない。** 値を取得するコマンド(生値を端末に残さない
  形)を `[機械]` ステップとして書く。

### 2.3 既存の手順書との関係

`docs/cutover-runbook.md`(ホスト移行)は、この書式が定まる前に書かれた長大な
手順書で、`[機械]` と `[人]` の区別が節ごとに暗黙になっている。全面的な書き直しは
しない — 新しい節を足すとき、または既存の節を直すときに、その節だけをこの書式
に寄せる。

## 3. 参照の導線

GCP や OAuth のセットアップを案内する場面(手順書の作成、`gas-clasp-ops` 等の
スキルの実行、ユーザーへの手順提示)では、案内を書き始める前に
`docs/personal-cloud-projects.md` を引き、導出規則から値を出す。標準が存在するのに
引く手掛かりが無かった、という発見漏れ(#505 のコメントの再現ケース)を、
各スキルの冒頭に置いたこの文書へのポインタで防ぐ。
