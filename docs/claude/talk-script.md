# talk-script スキル

`config/claude/skills/talk-script/` — 発表のスライドを作るときに発動する個人スキル。
`SKILL.md`(手順)と `cases.md`(判断の事例、追記型)の 2 ファイル構成。

## 動機

「スライドを作るときは、見た目に凝った HTML を作る公開スキル
(zarazhangrui/frontend-slides)に振り分けたい」という依頼から始まった。
ただし依頼者は、構成・ストーリーを見た目と不可分に重視している。究極的には
スピーカーノートが主で、スライドは補助資料にしたい。ノートの条件は、単独で
発表練習ができるプレインテキストであり、ホワイトボードを使って話しても
遜色がないこと。

そこで振り分け先を決める前に、そのツールがこの目的にそぐうかを一次ソースで
判断した(取得 2026-10-19、main HEAD `9906a34d640d2111f724544cbc50f7f130569ae1`)。

- スピーカーノートを出力に載せる機構が無い。言及は、PPTX 変換時に抽出した
  ノートを HTML コメントで残す 1 行のみ(`SKILL.md` の Phase 4)。
  プレゼンタービューもノート書き出しも無い。ノートに関する Issue も無い。
- 構成を先に固める工程が無い。Phase 1 は目的・枚数・素材の有無・密度の
  4 問だけで、アウトラインの確認は画像を渡したときにしか走らない。
- 主従が逆。スライドが主で、ノートは付属。担うのは見た目の層だけ。

結論は「単体では不適合」。ただし見た目の層としては有用なので、捨てずに
描画層の候補の 1 つとして残した。

## 構成

- 正本は Marp の Markdown 1 ファイル。語りを各スライド末尾の HTML コメントに
  全文で書く。コメントの外がスライド、中が原稿。
- 練習用の原稿は `marp --notes` で正本から導出する。複写しない。
- 発表用 HTML は Marp の既定テンプレートで出す(`p` キーでプレゼンタービュー)。
- 構成の規律は 3 層とホワイトボード試験(`SKILL.md` §1〜§4)。
  1. 談話全体の主張を 1 文で書く。これが無いうちは語りを書き始めない。
  2. 節ごとに主張を 1 文で立て、その下に語りを全文の散文で書く。
  3. スライドは語りの後から派生させる。見出しは主張の 1 文、本体は証拠 1 つ。
     箇条書きは既定で使わない。
  - ホワイトボード試験: 語りが図に触れるときは、図の内容を言葉で言い直す。

3 層のうち、スライド側(文の見出しと、主に画像で支える本体)は
assertion-evidence の設計に沿う。出典は Alley & Robertshaw, "Rethinking the design
of presentation slides: Creating slides that are readily comprehended", ASME IMECE
2004, DOI 10.1115/imece2004-61889(取得 2026-10-19)。談話全体と節の主張を先に
書く上位 2 層と、ホワイトボード試験は、依頼者の要求から足した。Alley & Neeley
2005(Technical Communication 52(4))は所在を確認しただけで、本文は読んでいない。

## 資料型の追加(単体で読む場面)

講演型(語りが主、1 枚 1 証拠)だけでは、商談・面談の画面共有のように、
スライドを単体で読ませる場面に合わない。外部のレビューが、そうした場面に向けて
表と情報量を増やす方向の規則を出してきた。そこで §1 の問診に「聴衆が次に下す判断」
と「単体で読む場面か」を足し、§4a に資料型を置いた。

- 先行例: Duarte, Inc. の Slidedocs。「チームが自分のペースで考えを消化するための
  視覚的な文書」という定義で、読まれる資料であり、発表される資料と区別される
  (https://www.duarte.com/slidedocs/ 、公開日の記載なし、取得 2026-10-19)。
  本文で確かめたのは定義と対比までで、設計規則の全文は未確認。
- 差分: Slidedocs は事前配布・置き土産の文書を指す。ここでは口頭を補う画面共有も
  含める。見出しを主張の 1 文に保つ点は、講演型の assertion-evidence から持ち込む。
- 素材の範囲で止める規則は、レビュー案が台帳に無い手順や標語を足していた事例から
  足した(`cases.md` の事例 2)。

| 採らなかった案 | 採らなかった理由 |
|---|---|
| 資料型を別のスキルにする | 構成を先に固める工程(§1〜§2)が共通で、description が競合して振り分けが曖昧になる |
| 資料型を既定にする | 語りが主の場面で、スライドが語りを置き換えてしまう |
| レビュー案を、講演型と合わないとして断る | 案の規則の大半(構成の順序、見出しの文、番号の対応)は講演型にも使える |

## 器をスキルにした理由

「構成を先に固め、語りを先に書く」は判断と順序の知識で、機械的に検査できない。
ルーティングも、スキルの description のキーワード一致だけが現状の手段である。
プロンプトの内容で振り分ける hook はこのリポジトリに無く、新設する理由も無い
(散文で始め、同じ違反が繰り返されてから決定論化する、ADR-543 の昇格型)。

## frontend-slides の配備

スキルとして `~/.claude/skills/` に置かない。description が「スライドを作るとき」に
反応するため、構成より先に見た目の工程へ入ってしまうからである。代わりに
flake の非 flake input(rev 固定、bleep と同じ形)から
`~/.local/share/frontend-slides/` に配備する。skills の走査対象外なので発火は
衝突せず、talk-script が明示指示のときだけ `SKILL.md` を読んで使う。

更新は flake input の rev を上げる。上げるときは、ノート出力の有無(上の動機の
1 点目)が変わっていないかを `SKILL.md` で確かめ、変わっていれば本スキルの §6 と
`cases.md` を見直す。

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| frontend-slides へ丸ごと振り分け | ノート出力が無く、主従が逆。上の動機を参照 |
| Slidev | ノートは持てるが、原稿だけをテキストで書き出す手段が無い。Node のプロジェクト構造も要る |
| reveal.js | 感触で外した(ノートが HTML 内の `<aside>` で、Markdown 単一ファイルの手触りが薄い)。分析ではない |
| 原稿とスライドを別ファイルにする | 複写と同期が生まれる。単一正本から導出できるなら要らない |
| 原稿からスライドを生成する自前スクリプト | Marp のコメント記法で同じことができる。道具を新設しない |
| UserPromptSubmit hook で振り分け | description で足りる。誤発火の調整コストが先に立つ |

## 動作確認(2026-10-19、vega の activation をビルドして実測)

- pinned の marp-cli 4.4.0 で、3 枚のデッキの `--notes` が語りをスライド順に
  連結し、境界は `---` 1 行になった。HTML 書き出しも通った。
- `--pdf --pdf-notes` は、PATH 上のブラウザで 3 ページの PDF を出し、語りが
  3 件のテキスト注釈として入っていた(qpdf で展開して注釈の内容を確認)。
- ローカル画像を参照するデッキは `--allow-local-files` が要る。付けないと
  Marp が読み込みを止めて警告する。

## 未確認

- `--pptx` は試していない。配布で PPTX を求められた最初の機会に試して、

- 他のホスト(arcturus、altair)での PDF 書き出し。ブラウザの解決は
