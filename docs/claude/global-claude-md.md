# global-claude-md — 調査規律を全セッションに常時注入する

`~/.claude/CLAUDE.md` は Claude Code が全セッションのコンテキストに常時読み込む
ファイルだが、これまで dotfiles は配備していなかった。実装は
`config/claude/CLAUDE.md`、配備は `home/modules/claude.nix` の
`home.file.".claude/CLAUDE.md"`。

## なぜこのファイルを作ったか

Plan mode で明示的に指示しない限り、既存研究の調査・Slack/Google Drive の検索・
GitHub のクローリングをしないまま計画を書き切ってしまう、という不満が出発点。
ただし結論は「read-only ならとにかく積極的にやれ」ではない —— read-only にも
無視できないコストが 3 つある:

1. herdr のタブバー(`docs/claude/claude-usage.md`)が可視化している
   5h/週間のレート制限を、無条件の調査が消費する。
2. 的外れな検索結果がコンテキストに残ると計画の質はむしろ下がる。取ってきた
   情報は捨てられない。
3. 検索クエリそのものが「何を作ろうとしているか」という文脈を外部サービスに
   送る行為であり、read-only という分類はローカル環境に対してのものでしかない。

そこで義務化する対象を「クローリングの実行」ではなく「情報源を参照するかどうかの
**判断**」に変えた。検証可能な不確実性(Slack/Drive/GitHub/公式ドキュメント/文献に
答えが実在しそうな仮定)が現れたら判断を明示し、やらないなら理由を書く。同様に
「ベストプラクティスを調べろ」も具体化した:一般論の収集ではなく、**新しい設計を
発明する前に確立されたやり方が存在するかを確認する義務**とし、優先順位を一次情報源
(公式ドキュメント・upstream ソース・学術文献)→組織内の先行実装→二次情報の順に
固定した。

適用範囲は Plan mode に限定していない。発火条件を「Plan mode に入ったこと」では
なく「非自明な設計判断・検証可能な不確実性の出現」に置いているため、実装中の
判断や Plan なしの相談にも同じ規律がかかる。trivial な作業(typo 修正など)では
この発火条件が成立しないので、オーバーヘッドは自然に発生しない。

## なぜ hook でもスキルでもなく CLAUDE.md か

- **hook**(`issue-index.sh` のような SessionStart + additionalContext)は、
  そのセッション固有の動的な値(open Issue 一覧など)を生成する仕組みであり、
  今回のような静的な行動方針には過剰で、hook 登録(`registerHooks` への
  event/command 追加)という余分な複雑さを持ち込む。
- **スキル**(`~/.claude/skills/`)は呼び出し(トリガー)を起点に発動する
  仕組みで、常時・受動的に効かせたい方針には向かない。
- **CLAUDE.md** は Claude Code が仕組みとして全セッションに常時読み込む唯一の
  経路で、今回のような「常に成立していてほしい行動規範」の正規の置き場。

## read-only 配布と `#` 追記の犠牲

`home.file` は store symlink で配備するため `~/.claude/CLAUDE.md` は read-only
になり、セッション中に `#` で始めるメモを打つショートカット(CLAUDE.md への追記)は
書き込み失敗するようになる。これは herdr の `config/herdr/` (`docs/claude/
herdr-sidebar-metadata.md` 参照)と同じ設計判断で、意図的に許容している:
その場の追記を許すと宣言的管理からのドリフトが始まり、次の `hms` で誰にも
説明のつかない差分に化ける。知見を永続化したいときは
`docs/claude/skill-gardening.md` の PR フローに乗せる —— つまり「追記したい」
という気持ちそのものは正しく、その受け口を CLAUDE.md の直接編集からリポジトリの
レビュー可能な変更に付け替えている。

## 公開リポジトリ(ADR-0004)としての文面

`config/claude/CLAUDE.md` の本文は会社固有の情報を含まない一般的な行動規範として
書いた。Slack/Google Drive は「コネクタが接続されている場合」と条件付きにしてあり、
identity(personal/company)やホストによってコネクタの可用性が違っても文面が
破綻しない。

## 効果の確かめ方

挙動そのものは一度きりの `nix build` では検証できない(プロンプトへの効き方の
問題)。`hms .` 適用後、新しいセッションを開いて非自明な設計判断を含む依頼を
投げ、判断の明示(参照する/しない理由)が自発的に出るかを観察する。効きが弱ければ
文面を PR で調整する —— このファイル自体が唯一の正本なので、調整は
`config/claude/CLAUDE.md` を編集するだけで済む。
