# github-audit-triage: 監査駆動の一括裁定スキルの設計理由

## 何が問題だったか

`github-audit`(前身の `github-audit-rulesets`/`github-audit-charters`)は
決定的判定のみを行い、直すのは `repo-charter` の 1 リポジトリずつの対話型
インタビューか、各 `*-repo-governance` スキルの手動実行しかなかった。
ADR-0013 導入時点のように**全リポジトリが drifted**な状態では、「次に触る
タイミングで個別 retrofit」は事実上収束しない。

別セッションが並行して、この収束問題に対応する charter-sweep スキル(#180)を
独自に開発していた。監査 findings を入力に LLM が全リポジトリの charter を
一括起草し、一括レビュー表を経て一括適用・**merge・GitHub メタデータ反映まで
自動で行う**設計だった。これを実地適用した結果、2 つの実害が観測された:

1. **README の品質劣化**: 機械的な一括適用が、確立された README 規範
   (standard-readme・GitHub 公式・Art of README)から外れた内容(改名の
   経緯・日付、個別 Issue 番号の焼き込み、Issue litmus への長文弁明)を
   生成した。ガードレールなしに「早く収束させる」ことだけを最適化すると、
   充填された文章の質が担保されない。
2. **人間裁定なしの正本書き換え**: 一括レビューの GO を経ても、GitHub
   description/topics のようなメタデータ反映を PR merge を待たずに直接
   実行しており、README(正本)とメタデータ(鏡)が一時的に矛盾しうる
   状態を作っていた。さらに PR の merge 自体も自動で行っており、LLM が
   人間のレビューを経ずに正本を書き換える経路が実質的に存在していた。

## 設計判断

- **ADR-0015 の判断ループの LLM ノードはこのスキルだけに限定する。**
  `github-audit` 自体は LLM を一切呼ばない(既存 2 スクリプトの設計原則を
  継承)。「決定論ノードが drift を検出 → LLM ノードが裁定支援に整形 →
  人間が GO/修正/除外/exempt を返す → 正本へ書き戻す → 再監査」という
  閉ループの外で、LLM が正本を直接書き換える経路を作らない。
- **完了定義を PR 作成までに固定する(#180 の「merge まで自動」を廃止)。**
  merge とメタデータ反映は必ず人間裁定の**後**、かつ PR が実際に merge
  された**後**に行う。README(正本)が確定する前にメタデータ(鏡)を
  書き換えると、両者が一時的に矛盾する — この矛盾を許容しないための順序
  制約であり、グローバル CLAUDE.md の実装タスク完了定義(commit→push→PR
  作成)とも整合する。
- **品質ガードレールを起草プロンプトに明示的に埋め込む。** `repo-charter`
  スキルの README/CONTRIBUTING テンプレートと禁止事項(ADR-0016 の一次情報
  接地済みの規範)をそのまま参照させ、triage スキル側で独自の緩い基準を
  作らない。「一括だから多少質を落としてでも収束させる」という判断を
  明示的に禁じる — #180 の症状はまさにこの判断が生んだ。
- **低確信フラグ(起草しないレーン)を維持する。** #180 で既に確立されて
  いた設計で、`docs/claude/repo-charter.md` のパイロット適合が示した
  「命名と責務の乖離」のような構造問題は機械起草の対象外とし、人間の対話
  (`repo-charter` の個別インタビュー)に残す。naming ドメインのクラス裁定・
  改名提案もこのレーンに準じる(ADR-0014 が定める、意味判断は人間へ)。
- **PR 本文規約・低確信フラグ・exempt 処分・self-verify は #180 の設計を
  継承する。** ゼロから作り直さず、実害の原因(merge 自動化・品質ガード
  レール欠如)だけを修正して巻き取る。

## Alternatives considered

- **#180 をそのまま採用し、merge だけ手動確認を挟む** — merge 手前で
  1 回止めるだけでは、README の品質劣化(症状 1)は直らない。品質の根本
  原因はガードレールの不在であり、merge 手前の確認はそれを検出できない。
  棄却。
- **triage スキルを作らず、drift のたびに `repo-charter` を都度呼ぶ** —
  全リポジトリが再び drifted になった ADR-0016 導入直後のような状況では
  収束しない(#180 が最初に解こうとした問題そのもの)。棄却。
- **triage スキルにも独自の LLM gate(2 段階レビュー)を設ける** — 人間の
  GO という 1 回の裁定点が既にあり、LLM 同士のレビューを重ねても
  ADR-0012 の知見(外部信号のない自己批評は収束しない)がここにも当てはまる。
  品質はプロンプト側のガードレール(repo-charter テンプレート参照の強制)
  で担保する方が確実。採らない。

## Consequences

- `#180` は本スキルへの巻き取りを理由に close する。charter-sweep が
  seed した README(もしあれば)は次回の棚卸しで新スキーマへ再適合が必要 —
  フォローアップとして別セッションの棚卸しに送る。
- `github-audit` のドメインが増えるたびに、このスキルの一括レビュー表の
  列(要約欄の書式)も対応するドメイン用に拡張する必要がある。
- 一括適用が実際に走る規模(全リポジトリ drift の再初期化直後など)では
  subagent 数・PR 数が大きくなりうる。このスキルの GO は依然として
  リポジトリ×ドメイン単位の 1 回のレビュー表で完結する型を採っている —
  `wrapup-chores` は 2026-09-23(ADR-387)に「確認の総数ではなく位置を
  変える」型(triage フェーズで `AskUserQuestion` による裁定を尽くし、
  `ExitPlanMode` を GO とする)へ分岐したため、両者はもう同型ではない。
  このスキルに同種の裁定フェーズを導入すべきかを検討した結果は次の節
  (#386)。

## `wrapup-chores` の裁定前倒し型を導入するか(#386、検討結果: 導入しない)

ADR-387 で `wrapup-chores` が裁定前倒し型に反転した際、このスキルは同じ
分岐を見送った(型を変えなかった)。その判断が妥当かどうかを #386 で
別途検討した。結論: **導入しない**。理由は 2 つの軸で `wrapup-chores`
とは前提が異なるため。

1. **母集団の規模が一桁違う。** `wrapup-chores` の母集団は 1 リポジトリの
   open Issue(実測でおおむね数十件)だが、このスキルの母集団はアカウント
   全体の(リポジトリ数 × ドメイン数)の組(#278 実装時の実測: archived
   込み 65 リポジトリ × 最大 7 ドメイン)。`AskUserQuestion` は 1 回の
   呼び出しで最大 4 問しか出せず、finding 単位の裁定前倒しはこの規模では
   1 回のレビュー表より往復回数が確実に増える。`wrapup-chores` の
   SKILL.md 自身も §4 で「件数が多ければ複数回に分けて呼ぶ」と、この
   往復コストを既に認めている — このスキルの規模ではその往復がさらに
   何倍にも増える。
2. **ADR-387 が修正した実害(§3 相当の欠落)が、このスキルには元から
   無い。** `wrapup-chores` の 2026-09-21 版が抱えていた根本原因は
   「要判断と分類した項目に一切手を付けず、ユーザーの目にも触れさせない」
   ことだった(ADR-387 Context)。このスキルの低確信フラグ(§3)は逆に、
   起草こそしないが**必ず一括レビュー表に載せて**「`repo-charter` へ送る」
   という処分を明示する — 項目が黙って消える経路が無い。裁定前倒しが
   解決する問題(裁定の機会が一度も来ない)は、このスキルでは既に §4 の
   単発レビューで解決済みだった。

副次的な観察として、このスキルの単発レビューは**起草の後**に来る設計が
`wrapup-chores` より合っている — naming の盲再導出や nav-doc 再構成の
ような提案は、抽象的な質問より具体的な差分を見てからの方が裁定しやすい。
裁定前倒し(起草前に確認)へ移すと、この種の findings ではむしろ判断材料
が減る。

裁定の粒度(finding 単位 / リポジトリ単位 / ドメイン単位、#386 が挙げた
論点)も、既存の「リポジトリ×ドメイン単位・行ごとに GO/修正/除外/exempt」
という一括レビュー表の設計で既に答えが出ている — 新たな設計は不要。

## Scope 外(現時点)

- merge 自体の自動化(人間が最終確認する設計を維持する)。
- GitHub description/topics 反映の自動化(README merge 後、人間が個別に
  実行する — §6 参照)。
- naming ドメインの改名実行(topic 宣言までがこのスキルの範囲、実際の
  `gh repo rename` は人間の裁定と実行に委ねる)。
