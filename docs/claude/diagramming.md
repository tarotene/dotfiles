# diagramming スキル

`config/claude/skills/diagramming/` — 作図するときに発動する個人スキル。`SKILL.md`(原則・処方)と `cases.md`(失敗事例集、追記型)の2ファイル構成。

## 動機

社内の実作業で、手書きSVGによる図解が2つの独立した失敗を起こした:

1. **矢印の接続不良**: ボックスの座標と矢印端点の座標が別々にハードコードされ、レイアウトを直したときに矢印だけ古い位置を指したままずれた。
2. **ジャンルの取り違え**: 時間発展・手続きを表現すべき内容を、静的な位置模式図の上に番号付き矢印を重ねて表現してしまった。図中に「これは実際の値ではなく進行状況を示す色分けです」という言い訳の注釈が必要になるほど無理な表現だった。本来はNコマ+差分ハイライトで描くべき内容だった。

前者は技術選定・検証手順の欠落、後者は「内容の型に対してどのジャンルの図が正しいか」という判断が抜けていたことによるUX上の失敗であり、どちらも再発しうる。

## スキルにした理由

失敗2(ジャンル選択)は「この内容にはこの図が正しい」という判断知識であり、機械的に検査できない。フックで防げるのは失敗1の一部(例: SVGファイル書き込み後にレンダリング確認を強制する)に限られ、それだけでは再発防止にならない。判断知識全体をカバーできる器はスキルだけだった。

## 2層構成の意図

- **処方層**(内容の型→ジャンル→推奨技術): 描き始める前にジャンルを誤らないための表。技術は「GitHubで見せるだけならmermaid → 見栄えを優先するならD2等でSVG生成 → レイアウトエンジンで表現できない図だけ手書きSVG」の3段構えにし、手書きSVGを最後の手段に位置づけた。
- **原則層**(技術非依存の不変条件): 手書きSVGに落ちた場合に限らず適用される、「矢印端点をボックス定義から導出する」「完成の定義に視認(レンダリング+画像としてRead)を含める」という不変条件。

原則(不変)と事例(増える)を同じファイルに書くと本文が肥大するため分離した。

## cases.md の運用

イベント駆動の手動追記。レビューで指摘を受けた・新しい失敗パターンに気づいたときに、`skill-gardening` のサニタイズ規則に従って抽象化してから追記する。定期的な自動追記の仕組みは意図的に作っていない(発動契機が「気づいたとき」であり、定期実行と噛み合わない)。

## フック後付けの検討余地

PostToolUse で `*.svg` の書き込みを検知し、レンダリング済みPNGを実際にReadしたかどうかを強制するフックは、原則層の「完成の定義に視認を含める」を機械的に補強できる余地がある。ただし現時点では未実装(誤発火の調整コストが先に立つため、まずスキル記述だけで運用してみる)。
