# living-description スキル

`config/claude/skills/living-description/SKILL.md` — Issue/PRの本文(Description)を「起票時点のスナップショット」ではなく「現在の合意状態を表す正本」として運用する習慣を持つスキル。

## 動機

複数の関連Issueに渡る設計変更で、方式の裁定が1つの親Issueのコメント上で確定した後、その裁定内容を関連する全てのIssue本文へ反映する作業を行った際、次が起きていた:

- 提案先のIssue本文に残っていた「合意前」の警告バナーが、確定後も除去されていなかった
- 仕様の数値(項目数・バイト配置等)が確定前の値のまま複数箇所に重複して残っていた
- 議論の途中で出た暫定的な値(後に衝突が発覚して1回付け替えられていた)が、本文には反映されずコメントにだけ残っていた
- その暫定値自体、後から「そもそも採番はこの提案の関心事ではなく別プロセスに委ねるべき」と判明していたが、この気付きも本文には反映されていなかった

コメントに裁定を書くことと、確定後に本文を書き直すことは別の作業であり、後者を明示的に意識しないと素通りしてしまう。これは特定のドメインに依存しない一般的な作業習慣なので、スキルとして切り出した。

## `diagramming` / `skill-gardening` との関係

既存2スキルとは独立の関心。`diagramming` は作図、`skill-gardening` はスキルの育て方(メタ)。`living-description` は「文書の複数コピー間の整合性を、裁定が変わるたびに能動的に保つ」という運用習慣で、対象はIssue/PRに限らない(複数の関連文書に同じ仕様が重複するあらゆる場面に当てはまる)。

## 事例集の分離

`cases.md` は追記型の失敗事例集。本文(SKILL.md)は不変の原則3点(コメントで決まったら直す・重複箇所を横断的に同期する・完成の定義)に絞り、事例が増えるほど太る部分は分離している。サニタイズ規則は`skill-gardening`側の正本を参照する形にして重複を避けている。
