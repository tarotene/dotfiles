## 何が問題だったか

herdr で開いていた複数の個人リポジトリ(公開・非公開を含む)を実地調査した
結果(2026-09-16)、README の目的文と GitHub description は全リポジトリに
存在していた。予想に反して「目的が書かれていない」は問題ではなかった。

実際に欠けていたのは、**「この Issue はこのリポジトリに属するか」を判定
できる形式**だった。Scope の書き方はリポジトリごとにバラバラ
(専用の見出しがある、Why 節に混在している、別の詳細ドキュメントに
丸投げしている、など)で、機械検査できる共通スキーマが存在しなかった。
GitHub topics に至っては調査した範囲の全リポジトリで未設定だった。

このうち非公開の 1 リポジトリ(小さな数理検証ツール)では、この問題が
既に実害化していた。README は「自動提案は入力を 1 回だけ見て提案し、
以降の工程には関与しない」と明言している一方、open Issue の 1 件は
それと正反対の反復ループ提案を要求していた。README とトラッカーは
既に矛盾しており、隣接する新機能(ある種のワークフロー自動化)を Issue
として切ってよいかという粗い判断さえ、この矛盾のせいで一意に決まらない
状態だった(この非公開リポジトリの固有名・具体的な Issue 番号は、
dotfiles が private/company リポジトリ名を自身のツリーに書かない方針
[`docs/claude/public-publish-guard.md`]により、ここでは伏せる)。

## 設計判断

- **正本は README、GitHub description はミラー**。Web UI で人が最初に見る
  場所と agent が必ず読む場所を一致させるため。description を正本にすると
  Web UI 経由でしか見えず、agent の作業フロー(リポジトリを clone/開く →
  README を読む)から外れる。
- **charter は 3 見出し + topics の固定スキーマ**(`docs/github-audit.md`
  に判定条件の詳細)。自由記述の「良い Scope 節」を期待するのではなく、
  見出しリテラルを固定して機械検査可能にした。良い内容を書く動機付けは
  スキーマではなく `repo-charter` スキルのインタビュー手順が担う。
- **Issue litmus は判定問だけでなく実例を要求する**。判定問(「その Issue は
  ○○を前進させるか」)だけでは抽象的すぎて、結局読み手の解釈に戻ってしまう。
  採用例・棄却例を書かせることで、新しい Issue 候補をパターンマッチで
  判定できるようにした。
- **監査は LLM を呼ばない**(`github-audit charters` 参照)。見出しの存在・
  description との文字列一致・topics 数という決定的な条件だけを見る。
  litmus の**内容の質**(判定問が本当に鋭いか)は監査の対象外 — そこは
  charter インタビュー(人間との対話)の責務であり、事後の自動検査には
  向かない。
- **AGENTS.md は監査対象に含めない**。AGENTS.md は「作業規約」であって
  「方向性」ではなく、二つを同じ検査対象にすると存在チェックが形骸化する
  リスクがある(中身を検査できないなら、空ファイルでも合格してしまう)。
  ただし `repo-charter` スキルは AGENTS.md 雛形に charter への参照 1 行を
  播く — 二重管理ではなく片方向の参照。

## パイロット適合で分かったこと(命名と責務の乖離)

上記の非公開リポジトリに charter の Issue litmus をパイロット適用する
過程で、リポジトリ名自体が「これから量産する自動化」を想起させる一方、
実際の中身は狭い検証テーゼの testbed だと分かった。名前と責務の不一致は
迷走の一因でもあったため、そのリポジトリは検証テーゼに忠実な新しい名前に
改名し、元の名前は将来「実際に量産機能を持つ」別リポジトリのために保留
した(改名の詳細・具体的なリポジトリ名は private 側の作業であり、
このリポジトリのツリーには残さない)。

適合後の Issue litmus はおおよそ次の形になった(内容を一般化して示す):

> 判定問: その Issue は、このリポジトリが検証しようとしている狭いテーゼ
> (「2 つの実装が同じ入力から同じ出力を導くか」)を直接前進させるか?
>
> 採用例: 別実装との突き合わせ検証の追加、許容誤差の根拠づけ。
>
> 棄却例: 検証対象そのものを使ったワークフローの自動化・便利ツール化
> (対象領域の自動処理を提案する反復ループなど — いずれも将来の別
> リポジトリの責務)、特定ツール専用の便利機能。

この litmus により、矛盾していた open Issue は棄却例に直接該当すると
機械的に判定でき、隣接する新機能提案(自動処理系の Issue)の可否も
同じ棄却例から即決できるようになった。

## スコープ外(現時点)

- Issue 起票時にリトマス照合を自動で行う hook(意味判断が要るため LLM
  なしでは書式検査までしかできない。第 2 弾候補)。
- 各リポジトリ自身の CI での自己検査(横断監査の `github-audit charters`
  が現状の代替)。
- 全リポジトリへの charter 一括適用(監査の drift 報告に任せ、各リポを
  次に触るときに順次適合化する)。
