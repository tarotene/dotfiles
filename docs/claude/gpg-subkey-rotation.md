# gpg-subkey-rotation — GPG サブ鍵ローテーションを抜け漏れなく終わらせる

`config/claude/skills/gpg-subkey-rotation/SKILL.md` の設計根拠。

## なぜこれが必要か

`gpg-subkey rotate` は「新しいサブ鍵を作る」ことしかしない。実際にローテー
ションを完了させるには、export → nix 編集 → GitHub/keyserver 同期 → PR →
`hms` 適用という後続 5 ステップが要る(`docs/operations.md` の「Rotating a
machine-local GPG [S] signing subkey」節に手順そのものは既にある)。

問題は手順の有無ではなく、**途中で止まっても誰も気づけない**こと。`rotate`
を実行した直後は何も壊れていないように見える(古いサブ鍵はまだ有効なので
署名は失敗しない)。実際には export/nix 編集/sync のどれかを飛ばした状態で
機体が「新しいサブ鍵を使い始める」と、そこから初めて GitHub 上の commit
署名検証が `unknown_key` で静かに壊れる。発覚するのは早くて次の PR の CI、
遅ければ何日も後になる。

この失敗が実際に起きた: ある機体で `[S]` サブ鍵を rotate した後、export・
nix 編集・GitHub/keyserver 同期のどれも行わずにセッションが終わった。数日
後、別の目的で作業していたセッションが偶然その機体で commit を作り、PR の
「Commits must have verified signatures」チェックで初めて発覚した。原因の
特定に `gpg-subkey sync` の drift レポートを読む調査が必要だった。

## なぜスキルにしたか

`docs/operations.md` は手順の**正本**として既にあるが、それは人間が能動的
に読みに行く文書であり、Claude が rotate だけ実行して途中で会話を終える
ことを防ぐものではない。必要なのは「rotate は 7 ステップの一部でしかなく、
3 つの完了条件が揃うまで終わりと呼ばない」という強制力をセッション内で
持たせること — これはスキルの役割であり、機械的に検査できる違反ではない
(hook 化は見送り。理由は次節)。

## なぜ hook にしなかったか

「rotate 直後に PreToolUse/Stop で完了チェックを強制する」hook 化も検討
したが、次の理由で見送った:

- rotate はハードウェア操作(YubiKey 挿入・タッチ)を要し、実行はほぼ常に
  ユーザーの手動操作か、Claude が明示的に依頼して待つ形になる。「rotate
  コマンドの直後」を hook で捕捉しても、後続ステップは別セッション・別日に
  行われることが多く、状態を跨いで追跡する仕組みが別途要る。
- 完了判定(`gpg-subkey sync` の drift 有無)は既にコマンド自体が提供して
  いる。「rotate したら sync を忘れずに」を強制したいだけなら、スキルの
  完了条件チェックリストで十分に機能する。
- 発見の入口(このスキルが生まれた実例)は pr-gate.sh 等の既存 hook が既に
  持つ「CI 失敗を見逃さない」という別の安全網であり、そこが機能している
  限り、rotate 専用の新しい hook を足す優先度は低い。

## 内部構成の意図

- SKILL.md は「1. 全体像(7 ステップ)→ 2. 完了条件 → 3. 進行中の見分け方
  → 4. 落とし穴」の順に並べ、`copilot-model-bump` スキルの「完了条件を
  明示するまで完成と呼ばない」という書き方を踏襲した。
- 実例(失敗の経緯)は skill-gardening のサニタイズ規則に従い、ホスト名・
  リポジトリ名・具体的な鍵 ID を書かずに抽象化した。
- 3節「ローテーション進行中の見分け方」は、次に別のセッションがこの状態に
  遭遇したときに `gpg-subkey status` / `sync` の出力だけから「今どこで
  止まっているか」を逆算できるようにするための節。

## 運用(いつ・どう追記するか)

- `gpg-subkey` 自体のサブコマンドが増減したら、1節のステップ番号を
  合わせて見直す。
- 新しい落とし穴(例: `sync --fix` の非対話フラグ要件)を踏んだら 4節に
  追記する。
