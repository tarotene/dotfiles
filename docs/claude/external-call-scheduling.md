# external-call-scheduling — 電話等ハンドオフ作業をカレンダーに反映する判断知識

## なぜこれが必要か

外部窓口(業者・医療機関等)への確認電話は Claude が代行できず、営業時間という
時間帯制約もある。従来はトークスクリプトを Markdown に書いてユーザーに渡す
だけで完了とみなしていたが、これは「ユーザーが後で自発的に思い出して営業時間
内に実行する」ことに賭ける設計であり、失念のリスクを Claude 側の作業として
解消できていなかった。

## 器をスキルにした理由

「営業時間とユーザーの空き時間の重なりを探し、衝突しない枠を選ぶ」は判断を
要する作業であり、機械的なフックでは代替できない(空きカレンダーの解釈には
文脈判断が要る — 「予定なし」がそのまま「対応できる」を意味するとは限らない)。
CLAUDE.md への格上げも検討したが、発動条件を「電話等のハンドオフ作業」という
キーワードで言い切れるため、全セッション常時発火のグローバル原則にする必要は
ないと判断した。

## 内部構成の意図

手順は5段階(営業時間の洗い出し→空き時間の突合→予定作成→専用カレンダーの
有無確認→前提条件の明記)。

- 4番目(専用カレンダーの有無確認)は、Claude が提案した予定を無条件に個人の
  主カレンダーへ書き込まない、という安全側の判断を明文化したもの。
- 5番目(前提条件の明記)は、依存関係のあるタスクを早まって実行させないための
  転記。

「外部サービスへの書き込みはサニタイズ対象」節は、`skill-gardening` が定める
サニタイズ規則(このリポジトリへのコミット向け)を、カレンダー・メール等の
外部送信全般に拡張したもの。カレンダーの説明欄にプロジェクト名や Issue 番号を
書いたところ、外部カレンダーサービス送信のガード機構に private リポジトリ
参照として検知され、書き直しになった実例が直接の根拠になっている。この検知は
「送信先が社外/自分のプライベートな外部サービスであっても、リポジトリ固有の
識別子を含めば止まる」という設計であり、`skill-gardening` が本来リポジトリへの
コミットを想定して書いたサニタイズ規則が、実際にはそれ以外の外部送信経路にも
及ぶ運用になっていることを可視化した。

## 運用

新しい失敗事例(サニタイズ漏れの新パターン、営業時間データの誤認識等)が
出たら、`SKILL.md` の事例節に追記する。
