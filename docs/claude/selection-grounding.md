# selection-grounding — 「クリーンかつ先進的」を検証可能な 3 軸に変換する

依頼者が自認していた「クリーンかつ先進的な技術選定を好む傾向」を、抽象的な
標準指示(「クリーンで先進的にせよ」)にはせず、`precedent-grounding` が
確立した `## 先行例との対比` 節にトークンを 1 つ足すだけで検証可能にした
設計記録。決定は `docs/adr/0035-selection-grounding.md`。実装は
`config/agents/AGENTS.md`(規律の短文)、`config/claude/CLAUDE.md`
(形式検査の配線)、`config/claude/skills/selection-grounding/SKILL.md`
(書き方)、`config/claude/hooks/plan-precedent-gate.sh`(形式検査、
既存 gate への加算)、`config/claude/hooks/copilot-plan-review.sh` の
lens A(監査項目の追加)。

## なぜ独立した plan 節・独立した gate にしなかったか

`## 技術選定` という新しい節と専用の `plan-tech-gate.sh` を作る案を最初に
検討したが、`ExitPlanMode` の gate はすでに `plan-scope-gate.sh`・
`plan-precedent-gate.sh`・`plan-fresh-gate.sh` の 3 本があり、4 本目を
建てることは本設計自身の軸 2(還元性: その仕組みは、より安い手段では
担えない仕事をしているか)に反する。技術選定の判断は precedent-grounding
が拾う設計判断の部分集合(「妥当な代替が複数ある場面」という発火条件が
完全に一致する)なので、既存の器に載せられるかを先に検討した —
`docs/adr/0033-nav-doc-no-materialisation.md` Decision 6「新規ドメインを
作らない(既存 charters ドメインを拡張する)」と同じ判断。

## なぜ「先進性」を軸 1 にしなかったか

依頼を字面どおり受け取れば「クリーンかつ先進的」は 2 つの対等な基準に
見える。だが dotfiles と、人格の手がかりとして参照した別の private
リポジトリ(person-state hub)の決定履歴を横断調査すると、実際の決定は
先進性を独立変数として扱っていなかった。`apt→nix`・`bash→Rust`・
`pip→uv`・`esa.io→Obsidian` はすべて「宣言的・単一正本・型付き・pin
固定」で説明でき、新しさで説明する必要がない。逆に dotfiles ADR-0024 は
Deno(より新しく表現力も高い)を「closure 固定手法(deno2nix)が
アーカイブ済みで後継がない」という理由で明示的に棄却し、Rust を採った —
新しさが表現不可能性に負けた実例。この 1 件が「先進性は独立の第一基準
ではない」という帰無仮説の反証にならなかったため、先進性を軸 3(同順位
破りのみ)に格下げした。

## なぜ「クリーン」を 2 つの軸に割ったか

「クリーン」という言葉は、構造面(不正な状態を表現不可能にする)と
還元面(要素は、より安い手段では担えない仕事をしているときだけ残す)の
2 つの異なる力を指しているのに、1 語のままだと後者が前者の言い訳に
使われるリスクがある。「表現不可能性を上げるためだから」を理由に機構が
無限に増える失敗モードは、参照した private リポジトリの決定履歴に
繰り返し現れていた: cadence 制約充足ソルバの自作を「エンジニアとしては
魅力的だが…コア問題を再生産する皮肉なリスク」として却下し、新しい
`season:` フィールドを既存の `status:` と意味が重複するという理由で
却下していた。dotfiles 側でも、消費者が 1 つも生き残っていない SOPS
ランタイム復号チャネル(ADR-0010)や、実質 1 個の秘密のための入れ物に
なっていたリポジトリ(ADR-0022)を丸ごと撤去した実例がある。還元性を
独立の軸として表現不可能性の直後に置くことで、この抑制を明文化した。

## なぜ候補集合の誠実さを別立てにしたか

3 軸の辞書式順序は「複数の候補を同じ土俵で比較した」ことを前提にして
いる。だが候補が実質 1 つしかない調査(本命が先に決まっていて、他の
選択肢を名目上並べただけの追認調査)は、3 軸をどれだけ厳密に適用しても
誠実な判断にはならない。参照した private リポジトリの決定履歴には、
本命(Obsidian、「憧れ駆動」と自認)が先に決まっていたにもかかわらず、
依頼者自身が「HedgeDoc とかと一応戦わせてほしい」と手動で指示し、
同じ評価軸で本気の対抗馬を戦わせた実例があった。これは
`docs/adr/0012-precedent-grounding-over-prompted-adversarial-review.md`
が指摘した教義(都度の指示は抽象的な標準指示にせず検証可能な出力形式に
機構化する)の、まだ拾われていなかった適用例だった。`本命:`/`対抗馬:`/
`外した候補:` という重い欄は、この実例をそのまま書き方に変換したもの。

## なぜ重い欄を毎回書かせないか

`本命:`/`対抗馬:`/`外した候補:` を全 `Dn` に強制すると、hook の置き場所
のような軽い設計判断にまで重い記述を要求することになり、これも軸 2
(還元性)に反する。発火条件を「外部依存の新設・置換・撤去、または撤収
コストが導入コストを上回る選択」に絞ったのは、`docs/adr/0007`(private
リポジトリ側、esa.io → Obsidian 移行の ADR)が「構築・撤収の二度手間」を
明示的な判断材料にしていたことと、dotfiles ADR-0025(自作 pre-release
CLI 導入の撤収コスト最小化設計)の両方が、同じ「あとで引き返すコストが
高い」という基準を独立に採用していたため。

## なぜ節名 `## 先行例との対比` を変えなかったか

selection-grounding の判断は必ずしも「先行例との対比」ではなく「複数の
軸での評価」が主眼であり、節名は正確ではない。それでも改名しなかった
理由は、改名の波及先(CLAUDE.md・precedent-grounding スキル・gate 本体・
selftest・本ドキュメント・`docs/adr/0012` の Amendment)に対して、得られる
ものが名前の正確さだけだったため。参照した private リポジトリの
`docs/adr/0004`(person-state hub 化の ADR)の D8 が同種のトレードオフを
"Known weakness, accepted... so it does not need re-litigating later." と
明記していたのに倣い、本ドキュメントに受容した弱点として記録するに留めた。

## 形式検査(plan-precedent-gate.sh への加算)

新しい gate は作らず、既存の `plan-precedent-gate.sh` に検査項目を足す。

1. `軸:` トークン(`表現不可能|還元|検出のみ`)が各 `Dn` に存在するか。
   `先行例なし:` の枝でも必須 — 還元性の判定は先行例の有無と独立。
2. 重い欄(`本命:`/`対抗馬:`/`外した候補:`)の節内整合性 — どれか 1 つ
   でもあれば `本命:` と `対抗馬:` が揃っているか。**この gate は
   「重い欄を書くべきだったのに書いていない」ことは検出しない** —
   発火条件(外部依存の出入り・撤収コスト)の判定はプランの内容に対する
   意味判断であり、decision-theoretic に決定論では解けない。ここは
   precedent-grounding と同じ二層構造(形式は gate、内容は critic)に
   従い、lens A の監査項目に「外部依存の出入りを伴う `Dn` に重い欄が
   無い」を追加して埋める。

`example_block()` に `軸:` 行の例文を追加し、`selftest()` に軸欠落・
`軸: 検出のみ` 単体・重い欄の片方欠落の各ケースを追加する(既存ケースは
回帰させない)。

## 効果の確かめ方

`precedent-grounding.md` と同じく、一度きりの `nix build` では検証
できない(プロンプトへの効き方の問題)。

```bash
# lens A が実際に選定関連の finding を出しているか
jq -r '.judged.findings[]? | select(.summary | test("軸|本命|対抗馬|技術選定"))' \
  ~/.claude/plan-reviews/*.json 2>/dev/null
```

効きが弱ければ `config/agents/AGENTS.md` の追記文か
`selection-grounding` スキルの文面を PR で調整する。
