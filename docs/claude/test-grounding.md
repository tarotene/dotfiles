# test-grounding スキル

`config/claude/skills/test-grounding/` — 複数の実コンポーネントが絡む検証項目・試験手順を書く前に発動する個人スキル。`SKILL.md`(原則)と `cases.md`(事例集、追記型)の2ファイル構成。

## 動機

社内の実作業で、既に一定の完成度がある検証項目ドラフト（試験手順の `assert` 群）をレビューする依頼があった。レビューの前に「ドラフトが前提とする結線・状態遷移そのものが正しいか」を確認する必要があると判断し、レビューではなく先に facts 文書＋層別モデル文書を作る方針に切り替えたところ、モデル作成の過程だけで4種類の食い違い（結線記述の欠落・実在しないレジスタ名を参照する assert・実装より過剰に厳しい判定閾値・上位仕様と下位実装の間の状態機械の不一致）が見つかった（詳細は `cases.md` 事例1）。

これらはいずれも、ドラフトや上位の設計文書だけを読んで気づける類のものではなく、一次資料（結線図・レジスタ定義・実装コード）に実際に当たらないと見えない食い違いだった。**モデルを作る作業そのものが一次資料に当たることを強制する**という効果があり、これは偶然ではなく毎回再現できる手順として固定化する価値があると判断した。

## スキルにした理由

「検証項目を書く前にモデルを作る」という判断は、機械的には検査できない（ドラフトの体裁が整っていても内容が一次資料と整合しているかはコードから読み取れない）。フックで強制できるのは「facts文書が存在すること」程度の存在チェックに限られ、それでは「作ったが薄い」を防げない。判断の質そのものを担保する器はスキルだけだった。

## 内部構成の意図

- **原則層**(`SKILL.md`): なぜモデルを先に作るか（3層の情報が独立に食い違うという構造的理由）／モデルの最小構成（facts文書 + 層別状態機械+突合表）／検算の4観点（フィールド実在・閾値過剰不足・層間状態整合・結線経路完全性）／完了条件（検証可能な条件として記述）。
- **事例層**(`cases.md`): 実際に4種の食い違いが見つかった経緯を、固有名詞を一般名詞（「センサX」「制御コンピュータA」等）まで抽象化して記録。因果関係（何を確認しようとして、何が一次資料に当たって初めて見えたか）はそのまま保存し、文脈だけを抽象化した。

facts文書側の書き方の規則（事実・計算・解釈の分離、出典必須、不整合は両論併記）は、既存の「機器の一次文書から事実整理を行う」文書の運用から一般化したもので、このスキル固有の発明ではない。

## cases.md の運用

イベント駆動の手動追記。別の種類の食い違い（例: 単位・座標系の不一致、タイミング前提の食い違い）を発見したときに、`skill-gardening` のサニタイズ規則に従って抽象化してから追記する。
