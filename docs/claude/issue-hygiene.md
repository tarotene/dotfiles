# issue-hygiene スキル

`config/claude/skills/issue-hygiene/SKILL.md` — open Issue が出自(同一 ADR / PR / 構想)ごとに束ねられずに積み上がったとき、GitHub の sub-issues 機能で親子構造を明示し直し、腐った tracking Issue を清算する定期衛生管理の手順。

## 動機

ある個人リポジトリで open Issue が 15 件に達し、うち 7 件が同一の先行 PR(person-state hub 系の設計裁定)に由来するフォローアップだったが、Issue 一覧上はただの兄弟としてしか見えず、相互の依存関係や完了条件が読めなくなっていた。同じリポジトリには先例として、チェックボックス方式(`- [ ] #NN` を本文に列挙する)の tracking Issue が既に 1 件あったが、子 Issue が全てクローズ済みであるにもかかわらず本文のチェックボックスが更新されないまま open で残っていた。子の状態変化を追跡する主体が本文の手動編集しかなく、誰も更新しないまま放置されると本文と実態が乖離する — この腐敗パターンを繰り返さないための手順が必要になった。

## チェックボックス方式ではなくネイティブ sub-issues を選んだ理由

チェックボックス方式は Markdown だけで完結し、GitHub の機能追加を待たずに使える利点はあるが、子の状態(クローズ/オープン)が本文のチェック印と自動で同期しない。GitHub のネイティブ sub-issues 機能(`gh issue edit --add-sub-issue`。2026-09-09 時点で `gh` 2.94.0 以降が対応し、GraphQL の `addSubIssue` mutation を直接叩く必要はない)は、進捗(◯/N 件)が GitHub 側で自動集計されるため、本文の手動更新という腐敗源そのものを取り除ける。親には `tracking` ラベルを付ける(2026-09-09 時点で `tarotene/dotfiles` に既存の `tracking` ラベルは無く、`tracking-issue` 規約の導入時に新設した)。

## 本文の役割を「機能で表現できない文脈だけ」に絞った理由・「書く/更新する」側を分離した理由

sub-issues 機能が子の一覧・進捗を自動表示する以上、本文に同じ一覧を重複させると、今度は「本文の子一覧」と「実際の sub-issues」の二重管理になり、結局チェックボックス方式と同じ腐敗リスクを持ち込む。本文には機能で表現できない情報(傘の外の Issue への依存・完了の定義・意図的に含めなかった Issue の説明)だけを書く設計にすることで、更新すべき箇所を最小化した。これは `living-description` が定める「本文は現在の合意状態を表す正本」という原則の具体化でもある。

この原則自体は当初 `issue-hygiene` §4 に書いていたが、`issue-hygiene` の description は「Issue 整理・tracking を清算」で発動する事後の衛生管理スキルであり、Issue を起票・更新する場面では引かれない。実際に public リポジトリのチェックボックス付き Issue はチェック済みが 1 つも無く、sub-issues 未使用の親候補も放置されたままだった(実測は `docs/claude/tracking-issue.md` 参照)。原因は規約の不在ではなく「規約が発動する場所の不在」だったため、書く/更新する側の規約を `tracking-issue` スキルへ分離し、`issue-hygiene` の description に起票・更新の発動語を含めないことで、両スキルが競合せず住み分けるようにした。

## 定期衛生管理と位置づけた理由

Issue の構造化は一度やって終わりではなく、新しい Issue が起票されるたびに既存の傘に属するべきものが出てくる。単発のタスクではなく、リポジトリの手入れとして定期的に(または Issue 数が閾値を超えたときに)見直す運用を前提にスキルとして固定化した。

## 棚卸し粒度をスコープに含めた理由

「同じ時期に起票された」だけでは束ねる根拠にならない、という判断基準を明文化した。出自が異なる Issue を機械的に束ねると、傘が「Issue 数を減らすための箱」に成り下がり、完了条件が意味を持たなくなる。逆に出自が同一でも粒度が細かすぎる(2 件しかない傘を乱立させる)と調整コストだけが増えるため、両方向の閾値をスキル本文に残した。

## 昇格候補の洗い出し手順を追加した理由

`tracking-issue` の発火条件は「実作業が 2 つ以上の子に割れた時点」の事後昇格だが、事後昇格は誰かが気づいて操作しない限り起きない。実測(2026-09-09)で「本文が空のまま複数の子 Issue を実質束ねている親」「コメントに正本が分裂した親」が既に存在することが分かったため、定期棚卸しの入口として §7 に 3 経路(本文の `- [ ] #NN` 参照・`Closes` が 2 本以上ぶら下がる Issue・親子未設定のクラスタ)を機械的に洗い出す手順を追加した。
