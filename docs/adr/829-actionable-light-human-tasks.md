# ADR-829 — 軽い人手タスクは、着手可能になった日のうちに予定化する

- Status: Accepted(D1 の「1 回で完結する」の Issue への適用と、D3・D4 の「待ちが解けてから」は ADR-1000 が改めた)
- Date: 2026-10-18
- Issue: No-Issue(`/grill-me` ではなく通常の依頼中に裁定。依頼は「基本、軽いコストで着手できる人手を必要とするタスクは、着手可能になったらすぐやる、くらいのルールにしたい」と「そのために私が所有する他のリポジトリをフルに活かすことにしたい」。範囲の問いに、本人は「予定入れ + ルールの最小版」を選んだ)

## Context

人手が要る残作業には、印(`handoff:human`)と予定化の手順(`handoff` スキル §7、`external-call-scheduling`)がある。
一方、AI 担当の着手可能タスクはセッション開始時に issue-index が出すが、人手担当の着手可能タスクを出す仕組みは
無かった。このため、設計と検査が済んで人手の段だけが残った Issue(試作品を工房で刷って実測する作業)が、誰にも
見えないまま着手可能になり続ける。実際に、open Issue が 1 件だけの個人リポジトリで、その 1 件がこの状態だった。

人手タスクは、軽いものと重いものでは扱いが違う。軽いものは、先送りしても得るものが無く、先送りするほど
その結果を待つ次の設計が止まる。重いものは、枠の確保そのものが判断を要する。この ADR は軽いものだけを対象にする。

## Decision

### D1: 「軽い人手タスク」を、4 つの条件をすべて満たす人手タスクと定める

- 1 回で完結する
- 現地の作業が 2 時間以内(移動を除く)
- 費用が 3,000 円以内
- 取り消せない確定操作を含まない(申請の送信は含めない)

数値は本人が選んだ案の値で、この ADR の改訂で変える。「移動を除く」という限定は、本人の指定ではなく起草時の
解釈である。

### D2: 軽さは閉じたラベル `handoff:light` で宣言し、本文は読まない

`handoff:human` に加えて `handoff:light` を付ける。付ける判断は、人手タスクを起票する側(`handoff` スキル §1)が
D1 に照らして行う。本文には根拠として `## 見積り` 節を書くが、検知はラベルだけで行い、節は機械的に読まない。

### D3: 着手可能な軽い人手タスクを、issue-index が owner 全体の検索で SessionStart に出す

条件は、`handoff:human` かつ `handoff:light` で、自分に assign され、GitHub Issue dependencies の `blocked_by` が
0 の open Issue。検索の単位はリポジトリではなく owner で、cwd の owner が viewer 自身のときだけ使う。会社など
別 owner のセッションには出さない。viewer が不明なら出さない。ラベルなし・0 件・取得失敗は節ごと黙って省く。

### D4: 見えたセッションは、その日のうちに予定化する

予定化の手順は `handoff` スキル §7 に置く。最も早く空く枠を探し、外部の承認や予約が要るものは主カレンダーに
`【調整中】` で仮押さえし、外部へ送る文面は下書き止まりにし、確定操作は本人と同期的に進める。その日のうちに
枠が取れない理由があれば、Issue にコメントで残す。新しい routine や hook は作らない。

## 先行例との対比

- 人手の残作業の印と予定化: 本リポジトリの `docs/agents/handoff.md` の D4(閉語彙ラベル)・D7(着手可能な `handoff:ai` を issue-index に出す)。D1 から D3 はその型の拡張で、軽さを閉語彙のラベルにする点と、検索を owner 単位にする点だけが異なる。
- 外部の営業時間と本人の空きを突き合わせてカレンダーに入れる手順: `config/agents/skills/external-call-scheduling/SKILL.md`。D4 はこれを使う。ただし同スキルが専用カレンダーを使うとする点は採らず、busy 判定に入る主カレンダーへの仮押さえにする。専用カレンダーは busy 判定の対象外なので、確定前の枠が他の調整に食われる。
- 通知を出す routine を増やさない方針: 私的な person-state リポジトリの日次 routine の ADR。D4 が新しい routine を作らない根拠で、cloud routine は登録済みリポジトリにしか届かないので、個人の別リポジトリの Issue には届かない。

## 却下した案

- **日次 routine に枝を足す案。** 上のとおり届かない。
- **本文の見積りを読んで軽さを導く案。** 自由記述のパースになる。`handoff` D4 が退けたタイトル接頭辞案と同じ理由で採らない。
- **共有の AGENTS.md に規範として書く案。** 会社のリポジトリには当てはまらない規範なので、共有層には置かない。D3 の owner 判定で個人のリポジトリに限る。
- **軽さの数値を持たず、すべての人手タスクを対象にする案。** 重い人手タスクは枠の確保に判断が要り、同じ日のうちに予定化する規範と合わない。

## 見つからなかったもの

- 個人の人手タスクを「軽さ」で分けて即日の予定化を求める既存の運用規約。GTD の「2 分ルール」は同じ発想だが、基準が 2 分で、移動や予約を伴う作業には当てはまらない。この ADR は一次文献の調査をしていない。
