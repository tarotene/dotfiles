# ADR-0000 — 個人の契約の機体は、別の側の持ち主の非公開リポジトリを読まない

- Status: Accepted
- Date: 2026-11-15
- Issue: No-Issue(自分の open PR の汚れを朝の机で掃除する設計の途中で、本人が「会社の org の分は、この PC では
  事実上不可視として扱う」規則を足した。本人の裁定の逐語は Context)

## Context

GitHub のアカウントは、会社と個人で共用している(ADR-523 が、同じ理由で通知の消化を持ち主で分けた)。
2026-11-15、自分の open PR を横断で数えるために、持ち主を絞らず `gh search prs --author @me --state open` を
実行し、会社側の**非公開**リポジトリの PR の題名と件数を、個人の契約の機体のセッションに表示した。

本人の裁定(2026-11-15、`AskUserQuestion` の回答と、その前の発言):

- 「会社の org 以下の分は、この PC では事実上不可視として扱って(そういうルールにしたい)」(org の名前は、ADR-0034 により伏せた)
- 範囲は、持ち主の表(ADR-523 D2)の会社側の全体。効かせ方は、道具で絞る・規範・拒否の 3 つ。
- 「public repo はフルオープンなので一切気を使う必要ない」。会社側から個人を見るときは「private もみてもよい。
  個人の契約プランでは厳密に学習データに使われないことを保証しない一方で、会社の契約ではそれを保証している
  という非対称性があるから(その範囲で安全にできることは何をやってもよい)」。

線の理由は、契約の非対称である。ADR-523 の線(仕事の分担)とは理由が違うので、可視性を区別する。

## Decision

### D1: 読んでよい範囲を、機体の契約の側と、リポジトリの可視性で決める

| 機体の契約 | 同じ側の持ち主 | 別の側・表に無い持ち主 |
|---|---|---|
| 個人 | 公開・非公開とも可 | 公開だけ可(非公開、公開と確かめられないものは不可) |
| 会社 | 可 | 可 |

- 側は、持ち主の表(GitHub のログイン名 → `personal` / `company`)で引く。表は ADR-523 D2 と同じ正本(非公開の
  設定リポジトリが持つ持ち主の表)から、`dotfiles.github.owners` を通して、機体の
  `~/.config/dotfiles/github-owners.toml` に配る。このリポジトリには値(持ち主の名前)を書かない(ADR-0034)。
- 機体の契約の側は、`dotfiles-identity verify` が通って `company` のときだけ会社。通らないとき、Claude 以外
  (Codex・Copilot)は、個人として扱う(制限する側に倒す)。
- 表のファイルが無い機体は、この規則を配っていないので何も制限しない(配備の順序の事故で、自分の非公開
  リポジトリまで止めないため)。ファイルがあるのに読めないときは、`gh` を止める。
- ADR-523 の通知の振り分け(通知ツール)は変えない。あちらは公開の会社リポジトリも会社側に回すので、より厳しい側に
  倒れていて、この規則と矛盾しない。

### D2: 実行前の拒否(`repo-scope-guard`)と、規範の節で効かせる

`hook-router` の規則として、Bash の `gh` を実行前に見る。拒否する形は、別の側・表に無い持ち主の非公開
リポジトリを指す `-R`・URL・`gh repo <verb>`・`gh api repos/…`・cwd の origin と、絞りの無い横断検索
(`gh search …`、`gh api search/…`、`gh api user/repos` など)。公開かの判定は `gh api repos/<o>/<r> --jq .visibility`
(1 日の写しつき)で、引けなければ閉じる。逃げ道の環境変数は置かない(例外は表を直す)。

機械で止まらない経路(`gh api graphql` の本文・ブラウザ・WebFetch・`GH_REPO`)は、共有の規範の節
「機体の契約の外にある非公開リポジトリを読まない」が担う。

### D3: 自分の PR を一覧する道具は、母集団を同じ側の持ち主だけで作る

別の側には、最初から問い合わせない(拒否に頼らない)。`pr-hygiene-check` がこの形を使う。

## 先行例との対比

- D1: 読んでよい範囲を、機体の契約の側と、リポジトリの可視性の 2 つで決める
  先行例: 本人の ADR, "ADR-523: 朝の机で GitHub 未読通知を消化し、会社と個人を持ち主で分ける" person-state リポジトリ(非公開)の ADR-523 D2・D3 (取得 2026-11-15)
  差分: 異なる — ADR-523 は仕事の分担の線で、可視性を区別しない。今回は学習利用の契約の非対称が理由なので、公開リポジトリを外し、会社の契約の機体では制限しない
  軸: 表現不可能 — 側は閉じた 2 語の表、契約の側は `dotfiles-identity verify` の一致判定に乗る
- D2: 拒否を `hook-router` の規則(Rust の crate)として足し、可視性を照会して判定する
  先行例: 本リポジトリ, ci-wait-guard の規則登録 `crates/hook-router/src/rules.rs` (取得 2026-11-15)
  差分: 一致 — 同じ Rule の型・budget・node の配線
  軸: 検出のみ — 実行前に拒否する。GraphQL の本文・ブラウザは範囲外で、規範の散文が受け持つ
- D3: 母集団を最初から同じ側の持ち主だけで作る
  先行例なし: 本リポジトリの `crates/`・`docs/agents/` と `gh search` の公式の絞り(`--owner`・`--visibility`)を探した。拒否に頼らず、問い合わせの範囲で絞る形は、自分の PR の一覧にしか要らない
  軸: 表現不可能 — 別の側の持ち主には問い合わせられない形にする

## Consequences

- 個人の機体で、会社側の非公開リポジトリは、`gh` で読めなくなる。公開の会社リポジトリは読める。
- 持ち主の表が、通知ツールの設定と `repo-scope-guard` の 2 つの読み手を持つ。正本は 1 つの TOML のまま。
- 持ち主の表に無い持ち主(新しい組織・他人の OSS)の非公開は、本人が表に足すまで読めない。机の段 3a が、
  表に無い持ち主を本人に聞く(既存)。
- 配備の順序: この ADR の変更が `main` に入って機体に配られても、非公開の設定リポジトリが
  `dotfiles.github.owners` を入れるまでは、規則は働かない(ファイルが無いので)。
