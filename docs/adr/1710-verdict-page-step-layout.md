# ADR-1710 — メール裁定ページの構造を、ステップ型(画面の枠・固定の格子・止まったときだけ理由を出す状態行)にし、デザインの正本に従わせる

- Status: Accepted
- Date: 2026-11-25
- Issue: No-Issue(ADR-1708 の原則の層の続き。裁定ページは、本人が操作する面で、最初に構造を選び直す面。ADR-1701 の `audit` が拾った違反の解消も含む)

## Context

メール裁定ページ(`config/agents/skills/inbox-adjudication/reference/verdict-page/`)の雛形は、全項目のカードを 1 枚の縦スクロールに並べる構造だった。項目の入力の並び(紙のカードの順)に 1 つの枠へ並べ、確定は Ctrl+Enter だけで、確認用の別画面は無く、キー入力の状態は、画面の上端に固定した 3 行の帯に常に出していた。

次の問題があった。

- 幅 390px で固定の帯が画面の約 3 分の 1 を占め、1 件あたりに出せる情報(根拠・引用・下書き)が少ない。根拠が 160 文字を超えると、推奨とボタンが押し出されるので、折り畳んでいた。
- 構造を、課題の性質から選んだ記録が無い。順次の裁定に答える面で、1 件ずつ進む構造と縦 1 枚の構造を比べて、触って選んだことが無い。
- `visual_diff.py audit`(ADR-1701・ADR-1704)が、この雛形に 10 件の違反を出していた: ボタンにフォーカスして Space を押しても押されない(C12)、幅 390px の横スクロール(C4)、24px 未満の操作部(C3)、囲いの無い `:hover`(C16)、16px 未満の入力欄 13 件(C17)。
- `config/web/` の正本(トークン・部品・共有の振る舞い)を取り込んでいない。色は独自の名前の 16 進の直書きだった。

本人が、同じ架空のデータの練習用の画面で、縦 1 枚の案と、1 件ずつ進むステップ型の案を並べて触り、ステップ型を選んだ(2026-11-25)。最初のステップ型の試作は、(1) ページ全体が縦に動く、(2) 項目の種類ごとに、ボタンの幅・行数・「あとで」「その他」の位置がずれる、(3) 状態行が冗長、という 3 点で「ブレて気持ち悪い」と指摘された。これを直した版(案 A2)を、本人が「妥協案としては良さそう」と評価し、構造として確定した。

## Decision

### D1: 裁定ページの構造は、ステップ型(1 件 1 画面 + 全件の概観 + 選ぶと自動で次へ + 最後に確認画面 + 完了画面)にする。縦 1 枚の構造は退ける

画面は 3 つ(1 件の画面・確認画面・完了画面)。全件の状態は、画面上端の番号の格子に、印(✓・あとで・!・空)つきで常に出し、押すと、その件へ飛べる。選ぶと自動で次へ進み(最後の件と、確認画面から直しに来たときは確認画面へ)、確認画面の「直す」で任意の件へ戻れる。キーだけで最後まで完結する。

先行例: GOV.UK Service Manual「Structuring forms」(`config/web/principles.toml` の `gov-one`。「Start by splitting the form across multiple pages with each page containing just one thing」)と、同じ文書の例外「User research will tell you when you can merge pages together. For example, if you’re designing an internal service for government users who need to repeat and switch between tasks quickly.」、NN/g「Wizards」の「Use wizards for novice users or infrequent processes (e.g., configuration or setup).」と「wizards can quickly become annoying and overly controlling if they have to be used over and over again」 https://www.gov.uk/service-manual/design/form-structure https://www.nngroup.com/articles/wizards/ (取得 2026-11-25。引用は原文と逐語で照合した)
差分: 異なる — 先行例は、内部向けで反復する熟練者には、1 件ずつ閉じ込める構造を避けるとする。この面は、利用者が本人 1 人で毎日使う(反復する熟練者)ので、先行例が避けるとする側に当たる。それでも 1 件ずつの構造を選んだのは、(1) 項目が互いに独立で、比較・相互参照が要らない(段階的開示の適用条件。`nn-progressive`)、(2) 件数が多く、1 件あたりの情報(根拠・引用・下書き)が多い、(3) 本人が練習用の画面で縦 1 枚の案と並べて触って選んだ(先行例の例外が言う「利用者調査で決める」)、による。反復する熟練者を閉じ込めないための手当てとして、全件の概観の常時表示・選ぶと自動で次へ・キーだけで完結・確認画面から任意の件へ戻れること、を入れた。
退けた案: 縦 1 枚(現行)。1 件あたりの情報量が、幅 390px の固定の帯に削られ、根拠の折り畳みを要した。ステップ型の最初の試作(画面の枠も固定の格子も無い)。ページが縦に動き、ボタンの位置が種類ごとにずれた。
軸: 検出のみ — 構造の選択は、規則で書けない好みと習慣に属する部分が大きく、本人が触って選んだ記録に置く。構造を宣言させる規則は、続く ADR(`page-structure` の宣言と検査)で足す。

### D2: 画面の枠・選択肢の固定の格子・止まったときだけ理由を出す状態行を、雛形の規則にする

- **画面の枠。** 画面の高さに収める(`100dvh`)。ページ全体は縦にも横にも動かさない。動くのは、本体の領域(1 件の内容)だけ。上に状態行・見出し・概観の格子、下に選択肢と戻る・次へを固定する。
- **選択肢の固定の格子。** 内容の選択肢(2〜5 個)は、幅 390px で 2 列、40rem 以上で 3 列の格子。全ボタンが同じ幅・同じ高さ。「推奨」の印は、ボタンの角に重ねて、幅も高さも変えない。「あとで」と「その他」は、どの種類でも、選択肢の下の同じ 2 マスに固定する。最初の件でも、「前へ」の場所を空ける。
- **状態行。** 固定高の 1 行。普段は直前の結果だけ(読み上げの対象は、ここだけ)。キーが止まったときだけ、警告の色で理由を出す。効いているときの「受付中」・画面名・残り件数・押せるキーは出さない(符号は各ボタンに出ており、全件の状態は概観の格子に出ているので、重複する)。

実測(2026-11-25、Chromium、`practice` の 11 種の項目を同じ幅で): 幅 390px・360px・1280px のすべてで、ページの縦スクロール 0・横スクロール 0・24px 未満の操作部 0。「あとで」「その他」「次へ」の位置は、11 種のすべてで 1 通り。内容の選択肢の幅と高さも、幅ごとに 1 通り(390px は 179×56、360px・高さ 640px は 164×52、1280px は 240×56)。本体の領域の中身が領域を超える件があり、そのときは領域の中で動く。iPhone の Safari の実機は未確認。

先行例: `config/web/components.css` の `.actions`(PC は戻るが左・次へが右、狭い幅は縦積みで次へが上。ADR-1687 の置き方の裁定)。
差分: 一致 — 戻る・次への置き方は共有の部品のまま使う。画面の枠・固定の格子・状態行の規則は、この面の構造に固有で、共有の部品にはしない(使う面が 1 つ。ADR-1660 D6 と同じ型で、2 つ目の面が出たら裁定する)。
軸: 表現不可能 — ボタンの位置を CSS の固定の格子で宣言し、ラベルの長さで位置が変わる状態を作れなくした(宣言 > 手続き)。

### D3: 幅 40rem 以下かつ高さ 760px 以下の端末では、戻る・次へを縦に積まず 1 行に並べ、注意の帯を隠す。デジタル庁デザインシステムの置き方からの例外として記録する

本体の領域を残すため。本人が、この例外を採ると裁定した(2026-11-25)。デジタル庁デザインシステムのボタンの置き方(狭い幅は縦に積み、「次へ」を上)から外れる。iPhone の Safari の実機での確認は未了で、確認は台帳に払い出す。

先行例: `config/web/components.css` の `.actions`(ADR-1687)。
差分: 異なる — 低い画面で、縦に積むと、本体の領域が小さくなり、「ページが縦に動かない」が崩れる端末(幅 360px・高さ 640px)が出る。その幅と高さに限り、1 行にする。
軸: 検出のみ — 低い端末での崩れは、実機でしか確かめられない部分が残る。

### D4: 選択肢の「その他」を選ぶキーの符号は、今回は固定しない

符号は、`options.json` の並びから、紙の生成器と画面が同じ規則で導く。「その他」は、選択肢の数が種類で違うので、種類ごとに c〜f と変わる。固定するには、画面・紙の生成器・両方が共有する選択肢の表を同時に変える必要があり、紙の生成器は別の非公開リポジトリにあって、その側の表の複写は、取り込み元の版で固定されている。dotfiles の変更だけで画面の符号を変えると、紙と画面の符号が食い違う。本人が、今回は変えないと裁定した(2026-11-25)。固定の要否は、未裁定として残す。

軸: 検出のみ — 種類ごとに変わる符号は、画面が表の並びから導くので、紙と画面が食い違う状態は検査(`build.sh --selftest` の符号の往復)で落とす。固定は、別の変更で、紙と画面を同時に直す。

### D5: ショートカットのキーは、共有の `keyguard` で受ける。Ctrl+Enter だけは、`keyguard` の外に置く

ボタン・要約・リンクにフォーカスがあるとき、その標準のキー操作(Enter・Space)を、ショートカット(Space = 「あとで」)が奪わないことを、`config/web/behavior.js` の `keyguard` に任せる(`selection.toml` の `way = "shared"`。手書きの条件分岐は書かない)。これで C12 の違反が消えた。Ctrl+Enter(確認画面へ・確定)は、標準のキー操作ではない組み合わせで、入力欄の中でも効かせるので、`keyguard` の外の 1 つの `keydown` に置く(`keyguard` は、文字を入れる欄では `Escape` 以外のすべてのキーを通さない)。

保存の表示は、共有の `saver` を取り込まない。`saver` は、状態の表示の要素を、組み立てたあとも持ち続ける前提だが、この面は、画面が替わるたびに 1 件の画面を組み直し、項目ごとの保存の状態(`saveSt`)を、画面の外の変数に持つ。確定後の完了画面にも、保存できていない項目の一覧を出すので、組み直しに強い持ち方にしている。`saver` への置き換えは、別の変更で検討する(未実装、意図あり)。

先行例: ADR-1703 の Amendment 1(`behavior.js`・`keyguard`・`saver`・`viewstate`)と、`config/web/selection.toml` の対応表 (取得 2026-11-25)
差分: 一致 — `keyguard` は、そのまま使う。異なる — `saver` は、組み直す画面と相性が悪く、今回は取り込まない。
既存手段: config/web/behavior.js — 採用: 既存の共有部品(新しいファイルを作らない)
軸: 還元 — Enter・Space を奪わない仕事を、共有の 1 か所の実装に寄せ、手書きの複写を作らない。

### D6: デザインの正本(`variables.css`・`components.css`・`behavior.js`)を、区間の pin で雛形に取り込む。主色は、この面のテーマに残す

雛形は、Artifact の 1 枚だけの HTML で、CSS・JavaScript を HTML の中に持つので、正本を、印を付けた区間に複写する(ADR-1700 D3。`design-pin:begin`・`design-pin:end` の行の間。区間の sha256 が、正本のファイルの sha256 と一致する)。固定は、リポジトリ根の `design-pin.toml` に書き、CI の `design-pin` が、複写と、pin した commit の正本の内容を照合する。色は役割(`--bg`・`--surface`・`--text`・`--accent`・`--ng` など)から引き、16 進を雛形に直書きしない。面の主色(teal)は、`--accent`・`--on-accent`・`--accent-text`・`--focus` の 4 つの上書きだけで残す(ADR-1677 D3)。書体は機体の書体で、第三者からは読み込まない(ADR-1677 D6)。

先行例: ADR-1700 D3(区間の pin)と、ADR-1685(pin 型の配り方) (取得 2026-11-25)
差分: 一致 — 区間の pin の書式をそのまま使う。異なる点は、正本のリポジトリ自身の面が、同じ仕組みで自分の正本を取り込み、CI で照合すること(別のリポジトリの面は、自分の CI から `design-pin` を呼ぶ)。
既存手段: design-pin.toml — 採用: .github/actions/design-pin(既存の検査。新しい検査は書かない)
軸: 表現不可能 — 単一正本 > 複写 + 同期。複写が正本からずれる状態を、区間の sha256 の照合で書けなくする。

### D7: 縦 1 枚のページが持っていた機能は、ステップ型の画面に写す。写せないものは、理由を書いて廃止する

| 縦 1 枚の機能 | ステップ型での扱い |
|---|---|
| 紙の回の番号の照合(任意の警告) | 確認画面に残す(キー入力の条件にしない) |
| 規則ありと判定して外した候補(`excluded`) | 確認画面の末尾に、畳んで出す |
| どの項目にも結びつかない下書き | 確認画面の末尾に出す。結びつく下書きは、その件の画面に出す |
| ページ上部の「この選択のあとの分担」 | 確認画面に出す。各ボタンの押した後の分担は、1 件の画面にも出す |
| ページ上部の件数欄・常設の「推奨をすべて採用」「回答をまとめる」 | 確認画面に出す(件数は、概観の格子と確認画面の文が持つ) |
| 長い根拠の折り畳み | **廃止**: 操作が下に固定され、根拠が長くても押す場所が動かない |
| マウス・フォーカスで触ったカードにキーのカーソルを移す(`syncCursor`) | **廃止**: 見ている件は 1 つで、カーソルが 2 系統に分かれる状態が無い |
| 3 行の状態行(キーが効くか・いまのカード・押せるキー) | **廃止**: 止まったときだけ理由を出す 1 行に(D2) |

軸: 検出のみ — 写し漏れは、`build.sh --selftest`(件数と概観の一致、画面ごとのキー、保存先の形)と、実描画の `audit` で拾う範囲だけを機械で見る。

## Alternatives considered

- **縦 1 枚のままにして、固定の帯だけを縮める**: 1 件あたりの情報量の制約と、根拠の折り畳みは残る。構造を触って選んだ結果と食い違う。採らない。
- **ウィザード(確認画面なし、戻れない)**: 反復する熟練者を閉じ込める。確認画面と、任意の件への戻りを残す。採らない。
- **`saver`・`viewstate` も取り込む**: `saver` は D5 の理由で今回は見送る。`viewstate`(読み込み中・失敗・空の出し分け)は、この面の保存先への接続の状態の出し方と重なるが、画面の組み直しの方式と合わせる検討が要るので、別の変更に回す(未実装、意図あり)。

## Consequences

- `visual_diff.py audit` を裁定ページに回すと、違反は 10 件から 0 件(通った検査 11 件)になる(2026-11-25)。
- 形式の版(`format_version`)は上げない。入力(`items.schema.json`)と保存先(`verdicts.schema.json`)の形は変わらず、読む側(別リポジトリの机の手順)の pin は動かない。机の手順の中の、画面の説明(紙の番号の照合・キーの操作)は、別のリポジトリで直す。
- 実機(iPhone の Safari)での確認は未了(台帳に払い出す)。
- 構造を宣言させる規則(`page-structure` の宣言と検査)は、続く ADR で足す。この雛形は、そのための宣言(`<meta name="page-structure" content="step">` と、課題の性質の軸 `page-axes`)を、先に持つ。
