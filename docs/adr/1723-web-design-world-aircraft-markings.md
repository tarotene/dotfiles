# ADR-1723 — Web の面の全体に通す見た目の世界を「機体のマーキング」に決め、色の役割に `--marker` を足す

- Status: Accepted
- Date: 2026-11-26
- Issue: No-Issue（本人の依頼。Web ページの見た目を作り直す前に、全体に適用するデザインのコンセプト = デザインシステムを固める）
- Related: ADR-1677(Pages のデザイン基準)、ADR-1685(正本の配り方)、ADR-1687(部品)、ADR-1700(見本ページ)、ADR-1719(impeccable の配備)、ADR-1722(目視できる Chrome の Playwright)

## Context

ADR-1677 から ADR-1711 までは、基準・トークン・部品・ページの型・構造の規則という「検査できる骨格」を敷いた。値は DADS(デジタル庁)由来の中立な値で、**どの見た目を目指すか**は決まっていなかった。各面を作り直す前に、全面に通す見た目の世界を 1 つ決める。本人が避けたい見た目として挙げたのは、事務的で味気ない / 面ごとに別物に見える / AI が作った感じ、の 3 つ。

## Decision

### D1: 世界は、impeccable の抽選(`concept-seed`)と決定ページで、本人が選ぶ

候補を出す側が好みの見た目を先に勧めない。私の候補リスト(本人の世界から 7 つ)の何番目を作るかは抽選が決め、本人が決定ページで選ぶ。1 回目の手(パート譜・時刻表・オリエンテーリング・発車標・現状の磨き込み)に本人が「航空もしくは HUD 風で、現状の裁定のよいところを取りたい」と添えて引き直し、2 回目の手(航空・HUD の系統。機体のマーキング・HUD の表示・デザイン年鑑の図版・星図・格子の見本・現状の磨き込み)から、**機体のマーキング**を選んだ。

先行例: Paul Bakaus, impeccable `reference/new-work.md`・`new-work-world.md`(スキル 4.11.0。concept-seed の前に見た目を提案しない。本人が決定ページで選ぶ)(取得 2026-11-26)
差分: 異なる — 上流は 1 つの面の世界を決める流れ。ここは全面に通す世界で、避けたい見た目(3 点)と既存の制約(ADR-1677 の骨格)を入力に先に渡し、選ばれた世界を `config/web/` の正本に落とす。
軸: 還元 — 候補を出して本人に選ばせる仕事は、手元の検査(`visual_diff.py audit` など)では担えない。
本命: impeccable の `new-work` と `concept-seed`(配備済み)。
対抗馬: 標準の `/frontend-design`(同じ評価軸「案を並べて本人に選ばせる探索を、誰が担うか」。抽選の仕組みが無い)。1 案だけを書いて承認を取る案(同軸。選択肢が無く、避けたい見た目の 3 点に反する)。
外した候補: なし。
既存手段: impeccable(ADR-1719) — 採用: 新しい道具は作らない。

### D2: 世界の置き場は、既存の正本と `config/web/DESIGN.md` の 1 本に限る

トークンの値は `variables.css`(`variables.json` は生成)、部品は `components.css`、見本は `specimen.html`。散文は、impeccable が読み書く `DESIGN.md` と、製品の事実を持つ `PRODUCT.md`(どちらも `config/web/`)の 2 本だけ。別の「コンセプト文書」は置かない。

先行例: dotfiles ADR-1700(見本ページと機械可読の値でデザインシステムを 1 か所に集約する)(取得 2026-11-26)
差分: 一致 — 同じ正本に世界の値を足す。散文は、見た目の値を重複して持たず、`DESIGN.md` の frontmatter が正本の値を指す。
軸: 表現不可能 — 単一正本 > 複写+同期。

### D3: 世界は、役割の名前・状態の色の意味・コントラストの検査を保ち、色の役割を `--marker` の 1 つだけ足す

DADS の灰色と青を、鋼色の灰色と墨色に置き換えた(DADS の semantic の緑・赤・橙はそのまま)。`--accent` の既定は墨色。面ごとのテーマが主色で上書きする点(accent の 4 つ)は変えない。**足した役割は `--marker`(安全黄 #f2c200)の 1 つ**で、「いまの件」「いまのステップ」の印の専用色。役割の集合は 16 から 17 になる。

`--marker` は、明るい背景(#e9ecee)とのコントラストが約 1.4:1 で、図形の 3:1 に届かない。そこで次の 2 つを守る。(1) 単独で使わず、同じ規則の中で `--text` の輪郭と対にする(`web_components` が、`var(--marker)` を持つ規則に `var(--text)` を求める)。(2) その上に文字を載せない(暗の設定で `--text` は明るい色に反転し、黄色の上に載せると約 1.4:1 になるため)。

先行例: dotfiles ADR-1677 D4(骨格は共通 = 役割の名前・尺度・状態の色の意味・書体・合格条件。テーマは役割に値を与えて差し替える)(取得 2026-11-26)
差分: 異なる — 骨格の「役割の名前」の集合を 1 つ広げる。ADR-1677 D4 の本文は役割の集合を固定とは書いていない(骨格に役割の名前が含まれる)が、`web_variables` が役割の集合を閉じて検査していたので、集合を広げることを本人に確かめて承認を得た(2026-11-26)。承認時の説明は「`--marker` の上に載せる文字は墨色で、コントラスト 4.5:1 以上を検査する」だったが、文字を載せない設計にしたので、文字の組でなく「輪郭と対」の検査に差し替えた(`--on-marker` を足すと役割が 2 つ増えるため採らなかった)。この差し替えは、PR を出す前に本人へ申告した。
軸: 表現不可能 — 閉じた役割の集合に 1 つだけ足し、単独で使える形を検査で作れなくする。
本命: `--marker` を 1 つ足し、輪郭と対にする検査を `web_components` に足す。
対抗馬: `--accent` を黄色にする案(同じ評価軸「黄色を、図形の 3:1 を満たす役割のどれに置くか」。明るい背景とのコントラストが足りず、`web_variables` が落とす)。黄色を使わず、いまの件を太い墨色の枠で示す案(同軸。世界の署名が薄れる。本人が選ばなかった)。
外した候補: 墨色を固定する役割 `--on-marker` を足す案(感触でなく分析で外した: 役割が 2 つ増え、黄色の上に文字を載せる設計自体が不要だった)。

### D4: 他の面は、取り込むまで見た目が変わらない

各面は、正本の区間の複写(`design-pin`)を持つ。正本を変えても、複写は変えない限り古い値のまま(固定した commit と sha256 を検査する)。取り込みは、面ごとに、完了定義の手順に従って別に積む。

先行例: dotfiles ADR-1685(配り方 = pin 型。取り込みは面が commit を上げて行う)(取得 2026-11-26)
差分: 一致。
軸: 表現不可能 — 複写の更新を別の変更にし、正本の変更が全面の見た目を同時に変える状態を作らない。
