# ADR-1729 — Web の面は共通のテーマを持たず、共通に残すのは工程・床・状態の色の意味・通信の床だけにする

- Status: Accepted
- Date: 2026-11-27
- Issue: No-Issue(本人の依頼。面ごとの目的が個別具体的なので、全面に通す共通のテーマをやめる)
- Amends: ADR-1677 D4(骨格は全面で共通、面ごとに変えてよいのは主色だけ)、ADR-1685 D1・D2(正本を各面が複写して pin する・役割の集合を閉じ、上書きは accent の 4 つだけ)、ADR-1687 D1(部品は正本の役割だけを参照する)、ADR-1723(全面に通す世界。D1 の世界の選び方は、面ごとに行う形で残る)
- Related: ADR-1677 D6(第三者の配信元の禁止は残す)、ADR-1711(構造の宣言は残す)、ADR-1719(impeccable の配備)

## Context

ADR-1677 から ADR-1723 までは、全面に共通の骨格(役割の名前・尺度・状態の色の意味)を敷き、面の個性を主色の 4 色だけに限り、全面に 1 つの世界(機体のマーキング)を通すことを決めた。目標は「面が違っても、同じ持ち主の道具に見える」だった。

2026-11-27 に、本人が次のように裁定した。それぞれのページの目的が個別具体的なので、共通のテーマを持つことをやめる。共通にしてよいのは、デザインプロセスの哲学だけ。

実物を確かめると、共通のテーマの強制は、検査のコードより文書に厚い。

- `config/web/` の検査(`web_variables`・`web_components`・`web_specimen`)が見るのは、正本 1 ファイルの自己整合で、各面に共通のテーマを強いる検査ではない。
- 各面に複写を強いる仕組みは `design-pin` だが、`design-pin.toml` に書いた面だけが対象で、複写の範囲は面が宣言する。
- 共通のテーマを面に求める記述は、`docs/agents/personal-web-app.md` の「画面の作り方」と、`config/web/PRODUCT.md`・`DESIGN.md`・`.impeccable/` の文書にある。impeccable は、これらを読んで面の見た目を作る。
- 世界を実際に取り込んだ面は、見本ページのほかに無い。複写している面も、世界を足す前の版の値のままである。

## Decision

### D1: 面は、共通のテーマを持たない。出発点は、採ってよく、採らなくてよい

`config/web/` の `variables.css`・`components.css`・`specimen.*`・`DESIGN.md` は、**出発点**として残す。面が採るなら、従来どおり `design-pin` で区間を固定して複写する。採らない面は、pin を持たず、自分の `PRODUCT.md`・`DESIGN.md` で見た目を決める。面ごとに root を分け、impeccable の `new-work` で世界を選ぶ(impeccable は 1 つの root に 1 つの世界を置く)。

### D2: 共通に残すのは、4 つだけ

1. **工程。** 課題の性質 → 構造(ADR-1711)→ 練習用画面で本人が触って選ぶ → 面ごとに世界を選ぶ → Before と After を本人が判定する。
2. **床。** `page-types.toml` の要件(コントラスト・押す領域・幅 390px の横スクロール・Space で押せる・構造の宣言など)と、`behavior.js`(`saver`・`keyguard`・`viewstate`)。床は、役割の名前に依らず、描画した HTML の測定(`visual_diff.py audit`)が担う。
3. **状態の色の意味。** 成功・誤り・注意の意味は変えない。色だけで状態を伝えない。
4. **通信の床。** 第三者の配信元から書体・スタイル・スクリプトを読み込まない(ADR-1677 D6 の理由: 開くたびに第三者へ要求が飛ぶ状態を作れなくする、CSP を閉じた面と同じ規則にそろえる)。書体の選択は面ごとで、自前のサイトから配信する Web フォントは使ってよい。

### D3: 出発点の検査は、出発点の自己整合だけを見る

`web_variables`・`web_components`・`web_specimen` は、出発点が閉じた役割の集合と、明暗の両方のコントラストを満たすことを、これまでどおり検査する。面に、この集合を強いない。

### D4: 文書の主張を、D1・D2 に合わせる

`config/web/PRODUCT.md` の原則 2(「面が違っても同じ持ち主の道具に見える」)と、避けたい見た目の「面ごとに別物に見える」を外す。`DESIGN.md`・見本ページの面の brief は、「全面に通す世界」でなく「出発点の世界」と書く。標準の「画面の作り方」は、「各面が複写して pin する」を「採る面は複写して pin する」に改める。

## 先行例との対比

- D1(共通のテーマを持たず、面ごとに世界を選ぶ): impeccable の `reference/doctor.md`(`projectRoots`・`workspace-context-inherited`)と SKILL.md の「Refinement preserves; redesign replaces」(取得 2026-11-27)。差分は、上流は 1 つの root に 1 つの世界を置く前提で、ここは面ごとに root を分ける形にする。
- D2(床と、見た目の同一性の分離): デジタル庁, ローカルデザインシステム(ADR-1677 の Context に引用。「初期値として設定されたデザイントークンは、特定の外観を規定するものではなく、編集の起点として位置づけています」)(取得 2026-11-27、ADR-1677 経由)。差分は一致。DADS 自身が、初期値を編集の起点とする。ADR-1677 D4 は、その編集を主色の 4 つに限っていた。ここは限りを外す。
- D3(出発点の自己整合の検査): ADR-1685・ADR-1687(`web_variables`・`web_components`)。差分は一致。検査の範囲を、出発点に限ると明記するだけ。

## Consequences

- 各面は、取り込みの義務を持たない。出発点を採るか、自分の世界を選ぶかは、面が決める。`design-pin` は、採る面の複写を固定する仕組みとして残る。
- `web_variables` の閉じた役割の集合は、出発点の性質になる。面ごとのテーマが、この集合を使う義務は無い。
- 「面が違っても同じ持ち主の道具に見える」は、目標でなくなる。本人が、面ごとの目的で見た目を決めるので、面の間で見た目が似ることも、似ないことも、違反ではない。
- 世界を引き直す面は、impeccable の `new-work` を、面ごとの root で回す。root の分け方は、各面のリポジトリの決定に任せる。

## Alternatives considered

- 共通の骨格(役割の名前・尺度)は残し、世界だけを面ごとにする: 骨格が共通だと、役割の集合の外の色や尺度を面が使えず、面ごとの目的に見た目を合わせる自由を、骨格が縛る。本人が「全部変えるべき」と裁定した。
- 世界(機体のマーキング)を、1 つの面(裁定ページ)の専用に残す: 本人が、世界を残さず、面ごとに選び直すと裁定した。出発点の世界として、見本ページに残す。
