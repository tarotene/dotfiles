# ADR-1256 — worklog に mail kind を足し、読んだメールの裁定結論を vault に残す

- Status: Accepted
- Date: 2026-10-29
- Issue: No-Issue(メールをまとめて読み裁定するセッションが、結論の記録を残さず、次のセッションが同じスレッドを読み直す、という運用上の穴を埋める依頼から始まった)
- Amends: ADR-998(`worklog` の kind の閉語彙を 6 つから 7 つにする。D1〜D5 の他の決定は変更しない)

## Context

メールを読んで裁定する作業(返信の下書き、断る判断、通知への判断、予定やフィルタ規則への反映)は、
セッションの終わりに結論が残らない。Gmail に残るのは下書きとラベルの状態だけで、「読んだうえで何もしないと
決めた」「断ると決めた」「予定に反映した」は、どこにも書かれない。次のセッションは、同じスレッドを最初から
読み直して、同じ裁定をやり直す。

一方、`worklog` の SessionStart の規範(ADR-998 D4)は、「既存の記録(Gmail の下書き・PR のマージ状態・
カレンダー)から導けること」を書かないと定めている。この規範は保つ。`mail` が残すのは、導けないもの —
本人の裁定の結論と、それがどのスレッドのものかを指す出典の id — だけである。メールの本文・件名・相手の名前・
アドレスは、Gmail に残っているので、ここには書かない。ADR-998 の vault は Git の外にあるが、Obsidian の
LiveSync でスマホに同期される。メールの中身を置く場所にはしない。

`worklog` は、vault の当日ノートへの書き込みの口(日次ノートの設定の解決、flock、読み戻して同じ行になる
ことの検査、同じ行を重ねない冪等性)を既に持っている。

## Decision

### D1: kind `mail` を足す

`Kind::Mail`(`mail`)を閉語彙に足す。kind は 7 つ(`reply|deadline|task|pr|found|stuck|mail`)になる。
書き込み口は `worklog add mail "<本文>"` で、新しい CLI は作らない。`list --kind mail` は既存の
`--kind` の絞り込みがそのまま使える(CLI の表面は増やさない)。

本命: `worklog` の kind の追加(書き込み口、ロック、読み戻しの検査、冪等性を再利用する)。
対抗馬: メール専用の CLI を新設し、vault に別の節や別のファイルを持たせる。vault の書き込み口(日次ノートの
解決、flock、読み戻しの検査)を 2 つの実装が持つことになり、単一正本を崩す。
既存手段: 拡張 — `crates/worklog` の `add`。
軸: 還元 — 書き込み口が既にある仕事のために、同じ仕事をする口を増やさない。

### D2: 本文の文法は `<処分>: <要旨> [<媒体>:<id>]`、コードが検査する

`worklog add` は、`mail` の本文がこの形でなければ書かずに止まる(`validate_mail`)。

- 処分、要旨、出典の印の 3 つで 1 行。出典の印は末尾に置き、直前に空白を 1 つ置く。
- 要旨は結論だけ(相手は組織・サービスの名前か種類、何を決めたか)。120 文字まで。

軸: 表現不可能 — 文法に合わない行を書けなくする(自由記述と事後の lint にしない)。

### D3: 処分は 5 つの閉語彙

- `read`: 読んだ。何もしない、または既に片付いている。
- `draft`: 返信の下書きを作った。
- `pass`: 断る、または返さないと決めた。
- `decide`: 通知に対する判断を決めた。
- `apply`: 正本(予定のデータ、フィルタ規則など)に反映した。

媒体は `gmail|linkedin|lapras|none`。

軸: 表現不可能 — 処分と媒体を型の外へ出さない。

### D4: 個人情報の混入を、コードで書けなくする

要旨に `@`(全角を含む)、`http`(大文字小文字を問わない)、角括弧を含められない。アドレスと URL の転記を
拒否し、角括弧の拒否で出典の印と区別できない本文を防ぐ。`mail` には `owner/repo` の参照を付けない
(`--ref` や `--repo` を渡すと止まる。作業ディレクトリのリポジトリも自動では付けない)。

要旨にある相手の名前そのものは、機械では見分けられない。規範(`docs/agents/worklog.md`、SessionStart の
注入文)が「相手は組織・サービスの名前か種類」と書き、書き手が守る。ここは検出できない、と認める。

軸: 表現不可能(アドレス・URL・参照)と検出のみ(人名)。後者は、実体のある名前の辞書を持つ代償が、
漏れの防止に見合わない。

### D5: 出典の id が冪等の鍵

`add` の「同じ kind・本文・参照の行は重ねない」(ADR-998 D1)に、新しい仕組みは足さない。出典の印が本文に
含まれるので、同じスレッドに同じ処分と同じ要旨を書き直しても重ならない。同じスレッドでも処分が違えば別の行に
なる(`draft` の後に `apply` が来る、など)。`mail` は参照を持たないので、作業ディレクトリが違っても、
同じ行は重ならない。

次のセッションは、`worklog list --kind mail --since <日付>` の出力から id を引き、記録済みの処分と同じ処分の
スレッドを飛ばす。

軸: 還元 — 冪等性の仕組みを増やさず、既存の重複判定に乗せる。

### D6: 件数の集計の行は媒体 `none`

特定のスレッドを指さない行(例: 「約 N 件を読んだ」)は、媒体 `none` で id を付けない `[none]` と書く。
`none` に id を付けることと、`none` 以外で id を省くことは、どちらも止まる。自動通知の大量の差出人など、
スレッドごとに書く価値の無いものは、この 1 行にまとめる。

軸: 表現不可能 — id の有無と媒体の組み合わせを閉じる。

## 先行例との対比

- D1: 先行例は ADR-998 D1〜D3(`worklog` が vault の書き込み口と kind の閉語彙を持つ決定)。出典: dotfiles, `docs/adr/998-worklog-vault-daily-note.md`(取得 2026-10-29)。差分: 同じ。kind を 1 つ足すだけで、口は増やさない。既存手段: 拡張。軸: 還元。
- D2: 先行例は、閉語彙と検査器で語彙の外を書けなくする型(カレンダーの握手の語彙を JSON の正本とし、検査器で縛る)。出典: dotfiles, `docs/adr/1242-calendar-handshake-spec.md`(取得 2026-10-29)。差分: 同じ型。握手は遷移の語彙で、こちらは 1 行の本文の文法。検査器は仕様記述でなく Rust の 1 つの関数。軸: 表現不可能。
- D3: 先行例は ADR-998 D2(kind を型(列挙)で閉じる)。出典: dotfiles, `docs/adr/998-worklog-vault-daily-note.md`(取得 2026-10-29)。差分: 同じ。本文の中の語彙(処分と媒体)にも同じ手を使う。軸: 表現不可能。
- D4: 先行例は ADR-998 D4 の規範(会社の業務の中身、機密、既存の記録から導けることを書かない)。出典: dotfiles, `docs/adr/998-worklog-vault-daily-note.md`(取得 2026-10-29)。差分: 散文の規範だった禁止事項のうち、機械で判定できる部分(アドレス、URL、参照)を、書き込み時の検査にする。昇格の理由は、メールの本文は個人情報を含みやすく、転記の誤りが取り消せない(Obsidian の LiveSync でスマホに同期される)ため。軸: 表現不可能と検出のみ。
- D5: 先行例は ADR-998 D1 の重複判定。出典: dotfiles, `docs/adr/998-worklog-vault-daily-note.md`(取得 2026-10-29)。差分: 同じ判定。出典の id を本文に含めることで、判定の鍵を増やさない。軸: 還元。
- D6: 先行例なし。探した範囲: dotfiles の `docs/adr/`、`docs/agents/worklog.md`、`crates/worklog`(取得 2026-10-29)。外部の文献は調べていない(未確認)。軸: 表現不可能。

## 却下した案

- メール専用の CLI を新設する。D1 のとおり、書き込み口を重複させる。
- 要旨に人名の辞書で検査をかける。D4 のとおり、辞書の維持が漏れの防止に見合わない。
- スレッドの件名やメールの抜粋を記録する。メールの中身は Gmail にあり、vault に複製すると個人情報が増える。

## Consequences

- 次のセッションは、メールを読み直さずに、記録済みのスレッドを `worklog list --kind mail` で引ける。
- `mail` の行は vault にあり、LiveSync でスマホに同期される。本文は結論と id だけなので、読んでも
  メールの中身は分からない。要旨に相手の名前を書けてしまう点は検出できない(D4)。
- 書き漏れは検出しない(ADR-998 の Consequences のとおり)。
- 既存のノートの `mail` でない行は、読み出しで変わらない。`mail` の kind を持たない旧バイナリが
  `[mail]` 行を読むと、kind の無い行(memo)の本文として読む。
- `inbox-adjudication` の skill は、報告のあとに `worklog add mail` で記録し、処理の前に
  `worklog list --kind mail` で記録済みのスレッドを飛ばす。
