# ADR-1000 — 待ちのある軽い人手タスクも、連鎖ごと先に予定へ入れる

- Status: Accepted
- Date: 2026-10-25
- Amends: ADR-829(D1 の「1 回で完結する」を Issue の単位に適用する。D3 の「`blocked_by` が 0 のものだけ出す」と、D4 の「着手可能になった日のうちに」を、待ちのある Issue も対象にする形へ改める。軽さの 4 条件、D2 のラベル、owner 判定は変更しない)
- Issue: No-Issue(`/grill-me` セッションでの本人の依頼から始まった。依頼は「ブロック関係によってつながっているからと言って小さい粒度のタスクが一つ一つ片付くまで予定を入れないというのはイケてないし、今後はそうならないようにしたい」)

## 執行点

- `crates/issue-index/src/lib.rs` — 軽い人手タスクの節に、待ちのある Issue も出し、`(待ち N 件)` を添える(この PR で変更)。
- `crates/issue-index/tests/selftest.rs` — 待ちのある Issue が出ること、待ちの無いものが先に並ぶことの検査(この PR で変更)。
- `crates/issue-index/tests/expected/handoff-human-mixed.stdout` — 注入文の期待出力(この PR で変更)。
- `config/claude/skills/handoff/SKILL.md` — §1 に「1 Issue = 1 回の作業」、§7 に「待ちがあっても待たない・連鎖は最後の段から逆算する」を書いた(この PR で変更)。
- `config/claude/skills/pr-description/SKILL.md` — §6 に、払い出した Issue が軽い人手タスクなら同じセッションで予定化まで進める手順を足した(この PR で変更)。

## Context

軽い人手タスクの予定化は、ADR-829 が「着手可能(`blocked_by` が 0)になった日のうちに」と定めた。ところが、人手の作業が 2 回に分かれる依頼(家での実測のあとに、現地の工房で印刷して判定する)で、次の型が起きた。実測だけを予定に入れ、印刷は「この枠に含めない」と書く。実測が片付くまで、印刷の予定は入らない。

この型には 2 つの害がある。

- 外部の承認や受付期間のある作業(工房の予約は承認制で、開始の 14 日前から受付)は、待つほど枠が遅れる。
- 予定に入れる役目のセッションが、前段の片付いた日に、後段を予定へ入れ忘れる。予定に指されない Issue を拾う仕組みが、この領域に無かった。

また、実測と印刷は別の回の作業なのに、1 つの Issue に入っていて `handoff:light`(「1 回で完結する」)が付いていた。軽さの定義から外れていた。

## Decision

### D1: 軽い人手 Issue は「1 Issue = 1 回の作業」にそろえ、段の順序は `blocked_by` で表す

2 回以上の作業を持つ Issue は、回ごとに分ける。人の作業の前後にある AI の作業も別の Issue(`handoff:ai`)にして、待ちでつなぐ。

### D2: 待ちのある軽い人手 Issue も、起票した日のうちに予定へ入れる

連鎖は、最後の段の日時を先に決め、前の段をそこから逆算して、同じセッションでまとめて予定に入れる。Issue を払い出したセッションが、予定化まで進める。issue-index は、待ちのある軽い人手タスクも「(待ち N 件)」付きで出す(`handoff:ai` の節は、従来どおり待ちの無いものだけを出す)。

### D3: 日付は予定データだけが持ち、Issue には書かない

Issue に最短着手日を書いて自動でカレンダーへ出す案は採らない。このリポジトリを含む公開リポジトリの Issue に、個人の予定が載る。予定データが別にあるので、日付が 2 か所になり、食い違う。承認制の予約は、空き枠の当てはめと申請を通らないと予定にならない。予定と Issue のつながりは、予定データ側が Issue への参照として持つ。

## 先行例との対比

- D1: ADR-829 D1(軽いの定義「1 回で完結する」)をそのまま採り、定義から外れていた Issue を分ける側に倒す。差分: 一致。
- D2: ADR-829 D3 は `blocked_by` が 0 のものだけを出し、待ちが解けてから予定化する。ここで改める。差分: 異なる。待ちの前段の日付が決まっていれば後段の日付は決められ、承認制の予約ほど待つと枠が遅れるため。
- D3: 予定データを正本とし、Issue を参照にとどめる考え方は、私的な person-state リポジトリ側の ADR(`docs/adr/` の予定の付随作業の ADR)の D4 と同じ。差分: 一致。この ADR の対応する決定は、そのリポジトリの別の ADR が持つ。

## 却下した案

- **Issue に最短着手日を書き、全リポジトリの Issue を読んでカレンダーへ自動で出す案。** D3 のとおり。
- **待ちが解けてから予定化する案(現状)。** 上の 2 つの害が残る。
- **issue-index が、待ちのある Issue の予定の有無まで検査する案。** このリポジトリは公開で、非公開の予定データを読めない。検出は、予定データを持つリポジトリ側の机の手順が担う。

## Consequences

- SessionStart の「軽い人手タスク」の節が長くなる。最大 10 件のうち、待ちの無いものを先に並べる。
- 連鎖の段の日付が動いたとき、後段の予定を動かす作業が要る。動かし忘れの検出は、この ADR では扱わない。
- 予定に入れ忘れた Issue の検出は、予定データを持つリポジトリ側の机が担う。このリポジトリには検出が無い。
