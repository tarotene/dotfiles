# ADR-0000 — 未裁定のメール項目を閉じた状態機械で表し、必ず終端に入ることを形式検査する

- Status: Accepted
- Date: 2026-10-30
- Issue: No-Issue(メールをまとめて読んで裁定したあと、未裁定の項目が HTML のページに並んだだけで、その後の状態を追う仕組みが無く、裁定が戻らなければ黙って残る、という運用上の穴を埋める依頼から始まった)
- Amends: ADR-1256(`mail` kind の D2・D3・D5 を改める。D1・D4・D6 は保つ)

## Context

ADR-1256 は、読んだメールの裁定の結論と出典の id を、`worklog` の `mail` kind で vault の当日ノートに残した。
残すのは「処分した結論」で、「まだ終わっていない」を表さない。たとえば `draft` を書いたあと、
その返信が送られたのか、見送られたのかを追えない。実際に、メールを一括処理した日に、本人の裁定を待つ項目
(判断の表の 20 件、返信の下書き 3 件など)が HTML のページに並んだだけで、裁定は閲覧したブラウザの
localStorage にしか残らず、記録に戻ったのは 1 件だけだった。

求めるのは、未裁定の項目が状態をたどって**必ず終わる**(取りこぼされない・重複しない)ことの保証である。
少なくとも次の 3 つの性質を、形式で検査する。

- 安全性: 終端の状態からは戻らない。同じ項目は 2 つの終端に入らない。
- 活性: すべての項目は、いつかは終端に入るか、本人への再通知で未了に戻る(無期限に黙って残らない)。
- 冪等性: 同じスレッドを読み直しても、項目が重複しない。

ノートは本人も Obsidian で編集でき、LiveSync で複数の機体とスマホに同期される。書き込みは、複数のセッションと
複数の機体から、遅れて合流する。

## Decision

### D1: 項目の状態は保存せず、`mail` 行を出来事として畳み込んで決める

新しい台帳は作らない。`worklog` の `mail` 行を出来事とみなし、同じ鍵の行を日付・時刻・ノート内の順にたどって
状態を決める。終端の状態は吸収的で、終端の後の出来事は書かれず、読むときは食い違いとして数える。

本命: なし — 白紙から 3 案を比べた結果で、先に決めていない。
対抗馬: Gmail 専用の別の提案キュー(追記専用の JSON Lines に状態の欄を足す)。同じ評価軸(媒体をまたげるか、
出典の ID で同一視できるか、機体をまたいで見えるか)で劣る。そのキューは Gmail 以外へ広げない裁定を持ち、
ID は乱数でスレッドと結び付かず、置き場は機体ごとである。
外した候補: 未裁定項目専用の新しいファイル — 感触で外した(書き込み口とロックが 2 つになる気がした)。分析ではない。
既存手段: 拡張 — `crates/worklog` の `add`。
軸: 還元 — 書き込み口(日次ノートの解決・flock・読み戻しの検査)が既にある仕事のために、同じ仕事をする口を増やさない。

### D2: 状態・出来事・遷移・期限の表は JSON 1 枚を正本にし、書き込み口と仕様が同じ表を読む

`config/agents/mail-lifecycle/vocabulary.json` に、状態(未了 `awaiting`・`decided`、終端 `closed`・
`dismissed`・`stale`・`superseded`)、出来事 9 語(`read`・`ask`・`draft`・`decide`・`apply`・`pass`・
`remind`・`move`・`stale`)と各遷移、時間の決まり(7・7・3 日)を置く。`worklog` は `include_str!` で埋め込み、
許されない遷移の行を書かずに止める。Quint の仕様は検査のたびに `spec/vocab.jq` で同じ JSON から生成する(写しを
コミットしない)。仕様が起こす遷移がすべて語彙にあること(`s6`)と、語彙の遷移がすべて起こせること(`cov<i>`)を
両方向で検査する。

軸: 表現不可能 — 単一正本で、書き込み口と仕様の表がずれることを許さない。

### D3: 状態は未了 2・終端 4 に絞る

`detected` と `proposed` は `awaiting` にまとめる。推奨と下書きを作ることと本人に見せることは同じセッションで
起き、「読んだがまだ見せていない」を別の状態にしても、本人の判断に使える情報が増えないため。途中で落ちた場合は
「記録を先に書き、下書きを後で作る」順序で取りこぼしを防ぐ(記録にあって下書きが無ければ、次の机で作り直す。
活性 `l3` で検査する)。裁定済みで反映がまだの `decided`、終端の `superseded`(別の追跡先へ移した。移し先が必須)を足す。

軸: 表現不可能。

### D4: 項目の鍵は「スレッド + その項目を開いた受信」とし、同じスレッドの未了は常に 1 つ

鍵は `<媒体>:<スレッド>/<受信>`。受信は Gmail ならメッセージ ID、メッセージごとの ID が取れない媒体は画面に出る
受信日時を分まで。スレッドだけを鍵にすると、終端のあとに相手から新しい受信が来たとき、終端から戻せずに追えない。
逆に、終端のあとは新しい項目として開ける形にすると、同じメールを読み直しただけで重複して開き、冪等性を保証できない
(`worklog` は Gmail を読めず、新しい受信かどうかを確かめられない)。受信まで鍵に含めれば、読み直しは同じ鍵
(記録済み)、新しい受信は新しい鍵(新しい項目)になる。新しい受信を `read`・`draft`・`ask` で開くとき、
同じ命令の中で古い未了を先に `move`(移し先 `to:mail:<新しい鍵>`)で移す。未記録の鍵への `pass` では移さない
(本人が新しい受信を見送っても、古い未了の判断は残す)。受信の新旧は、画面の受信日時は字句順、Gmail のメッセージ ID は
長さ、字句順で比べる(Gmail の ID が時刻順に増えることは確かめていない)。

軸: 表現不可能。

### D5: 7 日無動きで `remind`、さらに 7 日か期限超過で `stale`。`stale` の前に必ず `remind`

`worklog mail sweep` が、最後の出来事から 7 日たった未了、または期限の 3 日前の未了に `remind` を書く。
`remind` が今日より前にあり、さらに 7 日たつか期限を過ぎた未了に `stale` を書く。実質的な出来事は時計を数え直す。
`remind` と `stale` は `sweep` だけが書く(`add` は拒否する)。返事の無い項目は最長 14 日で終端に入る。本人に一度も
知らせずに機械が閉じることは無い(`s4`)。期限のある作業を「やる」と決めたら、カレンダーの期限の予定か Issue に移して
`superseded` にするのが既定で、以後の追跡は移し先の仕組みが担う。

軸: 検出のみ — 時間の経過は表現不可能にできず、`sweep` が検出して書く。

### D6: 合流の規則を畳み込みに置き、終端の行の手削除は機体ごとの控えで検出する

複数の機体が LiveSync で遅れて合流しても状態が一意になるよう、畳み込みの規則を決める。最初の終端が勝つ。
同じ鍵の 2 つ目の開く出来事は読み直しとして無視する。同じスレッドに未了が 2 つ並んだら、受信の古い方を移したと
みなす(遅れて届いた古い受信は、開いた直後に自分が移される)。控えにある鍵への開く出来事は、記録済みにする
(読み直しで消された終端が未了に戻るのを防ぐ)。さらに、`add` と `sweep` は終端の行を書いた後に、機体ごとの控え(追記専用の JSON Lines)にも鍵と本文を書く。
`check` は、控えにあるのにノートに同じ終端が無い鍵を「終端の行が消えた」と出し、`sweep` はその項目を再通知しない。
別の機体で書かれた終端は、その機体の控えにしか載らず、その機体の `check` でだけ見つかる(限界として認める)。

先行例の「受理した最後の印を控え、語彙に無い書き換えを見つける」と同じ型である。差し戻しはせず、本人に見せる。

軸: 検出のみ — 追記専用の記録の外にある操作は防げない。

### D7: 仕様と実装の一致を、仕様の軌跡の再生で確かめる

Quint の仕様の探索(`quint run`)が出す軌跡(ITF。nix の check `mail-lifecycle-itf`、種を固定)の各状態にある、
機体ごとのノートの行の写しを、`worklog` の統合試験 `itf_replay` が実装の畳み込みに通し、項目ごとの状態と食い違いの数が
仕様の畳み込みと一致することを確かめる。握手の仕様は実装との突き合わせを持たなかったので、ここで足す。
この突き合わせは、実装が仕様と違う規則を持っていた 2 か所を実際に見つけた(`pass` で古い未了を移すか、遅れて届いた
古い受信を移す向き)。

軸: 検出のみ。

### D8: 一括モードも、Gmail で返せるスレッドは返信形式の下書きまで作る

`inbox-adjudication` の一括モードは、日次モードと同じく、Gmail で返せるスレッドを元のメッセージへの返信形式
(`replyToMessageId`)で下書きにする。HTML のページは、Gmail の外の媒体の下書きと判断の表にだけ使う。
ページの裁定は固定の 1 枚のページの Artifact の db に保存し(保存するのは鍵と裁定の語だけ)、次のセッションが読んで
`worklog` に書く。記録を先に書き、下書きを後で作る。

軸: 還元 — 日次モードに既にある手順を、一括モードにも使う。

## 先行例との対比

- D1: 先行例は Martin Fowler, "Event Sourcing", 2005-12-12 https://martinfowler.com/eaaDev/EventSourcing.html (取得 2026-10-30)。「状態の変化をすべて出来事の列として残し、列から状態を組み立てる」。差分: 一致。出来事の置き場は vault の当日ノートで、書き込み口は ADR-998・ADR-1256 の `worklog`。
- D2: 先行例は ADR-1242 の握手の語彙と仕様 `docs/adr/1242-calendar-handshake-spec.md`、`config/agents/calendar-handshake/spec/vocab.jq`(取得 2026-10-30)。差分: 異なる — 握手は検査器が語彙を読むだけだが、ここでは書き込み口(`worklog`)自身も同じ表で行を拒否する。
- D3: 先行例は、Gmail 専用の提案キューの墓石(未了か、1 つの解決のどちらか)と、機械が書く `stale`・`superseded` の追補(非公開のリポジトリにあり、ここには出典を書けない)。差分: 異なる — 1 段の墓石に、裁定済みで反映待ちの `decided` と、再通知の `remind` を足す。
- D4: 先行例は ADR-1256 D5(出典の id が冪等の鍵)。差分: 異なる — スレッドだけでは終端後の新しい受信を追えず、終端後の再開を許すと読み直しで重複するので、受信まで鍵に含める。
- D5: 先行例は GitHub, `actions/stale` の README https://github.com/actions/stale (取得 2026-10-30)。`days-before-stale`「マークするまでの無動きの日数」、`days-before-close`「stale を閉じるまでの無動きの日数」、更新で stale の印が外れる。差分: 一致 — 警告の印、猶予、閉じる、の 2 段の型。期限の 3 日前の `remind` を足す。
- D6: 先行例は ADR-550 の追補と ADR-1242(重複実行・途中の失敗の模型。会社側が最後に受理した印を控えて差し戻す)。差分: 異なる — 握手は CAS とロックで書き込みを直列にするが、vault は LiveSync で後から合流するので、合流後の畳み込みの規則で状態を一意にする。差し戻さず、見せる。
- D7: 先行例なし。探した範囲: この dotfiles の `docs/adr`・`docs/agents`・`crates` で Quint・ITF・軌跡の再生を探した(取得 2026-10-30)。外部の文献(Quint の ITF の文書)は実装の初めに読んで確かめる。
- D8: 先行例は `config/agents/skills/inbox-adjudication/SKILL.md` の日次モード(`replyToMessageId` の返信形式の下書き)(取得 2026-10-30)。差分: 一致。

## 却下した案

- Gmail 専用の別の提案キューに状態の欄を足す。D1 のとおり、媒体をまたげず、ID が結び付かない。
- 未裁定項目専用の新しいファイルを置く。書き込み口とロックが 2 つになる。
- `detected` と `proposed` を別の状態にする。D3 のとおり、本人の判断の材料が増えない。
- 鍵をスレッドだけにする。D4 のとおり、終端後の新しい受信を追えない。
- 終端の行の手削除を保証の範囲外と書くだけにする。消すと未了に見えて再通知されるだけで、終端の復活が見えない。控えで検出する。
- 機械が閉じない(`stale` を使わず `remind` を繰り返す)。答えの無い項目が無期限に残り、活性が「終端か再通知」に弱まる。

## Consequences

- 未裁定の項目は、答えが無くても最長 14 日で終端に入る。`stale` で閉じた項目は、朝の机が本人に 1 回知らせる。
- `worklog add mail` の文法が変わる(出典の印が `<スレッド>/<受信>` になり、`due:`・`to:` を持つ)。ADR-1256 の旧い
  文法の行は 2026-10-30 より前のノートにだけあり、畳み込まない(`list` では読める)。
- 検査は nix の check で、表の 1 行が 1 derivation。語彙・仕様・`worklog` が変わった PR と main への push で回す。
- 限界: 別の機体で書かれた終端の手削除、控え自体の削除、要旨に書かれた人名は検出できない。
